What Should Embodied Agents Remember?
Benchmarking and Evaluating Memory
Modality for Embodied Agents
Junxiang Wang1,2†, Yuchen Liu1,3†, Yi Wu1, Guofei Chen1, Nir Pechuk2,
Tao Chen1, Zackory Erickson2, Yuzhe Qin1 & Tianyu Li1
1Dexmate, 2Carnegie Mellon University, 3Purdue University
†Work done during an internship at Dexmate.
Memory allows large language model (LLM) agents to use past experience, often stored as textual
records, when responding to requests. For embodied agents that control robots, visual and spatial
observations introduce a broader choice of memory modalities, affecting both the information available
for subsequent tasks and the model inference costs of constructing and using memory. We introduce
MeMoREval, a benchmark for studying this problem through a controlled experience-request protocol.
Agents first experience a sequence of events without knowing the subsequent tasks, and subsequently
they use memory to respond to information and action requests without receiving new observations.
The benchmark comprises 53 tasks across four simulated indoor environments and measures task
success alongside the inference costs of memory construction and use.
Our reference evaluations
reveal that storing frames outperforms storing generated descriptions at lower write-time inference
cost for the primary model, while storing frames with scene graphs achieves the highest aggregate
task success for every tested model. Extensions to accumulated experience, selective frame retention,
and visual input to memory writers demonstrate how the benchmark accommodates further memory-
design investigations.
Two physical-robot demonstrations establish the feasibility of applying its
protocol beyond simulation.

1 Introduction
A coding agent investigating a bug may uncover facts about a codebase that remain useful long after the
immediate fix. Memory systems preserve such findings beyond the model’s current context (Chhikara et al.,
2025; Xu et al., 2025; Packer et al., 2023; Shinn et al., 2023; Wang et al., 2025b). For large language model
(LLM) agents that control robots, what is worth preserving extends to camera frames, object locations, and
whether physical actions succeeded. This experience can be retained as textual descriptions, raw images,
structured spatial records, or combinations of these forms, and the choice affects both what survives and
what memory costs.
A textual record might note that several mugs were on a counter while omitting the colors needed to later
retrieve a particular mug. Generating a description requires selecting what to mention before the future
task is known, and task-relevant details may be discarded. A stored camera frame retains visual details for
interpretation once the task is known, while a structured spatial record makes object locations and relations
directly available.
Decisions to remember certain information are particularly important for embodied agents because recovering
forgotten information can require considerable physical action. A coding agent can often rediscover a fact
by inspecting an available codebase again or inspecting an earlier version of the codebase, which incurs
additional computation and latency, but the memory lapse is largely invisible to the user.

To study which forms of retained evidence best support subsequent recall and action, we introduce MeMo-
REval, a controlled Evaluation protocol and benchmark for studying Memory Modalities of Robotic embodied
agents. We distinguish the memory modality, which determines the form of retained evidence, from the mem-
ory backend, which organizes that evidence and makes it available to the agent. Our study addresses three
questions: (RQ1) How do memory modalities affect success on information and action requests across task
categories and models? (RQ2) How do these modalities trade off task success against write-time and read-
time inference cost? (RQ3) How can MeMoREval inform memory-design decisions for deploying embodied
agents?
Our evaluation protocol constructs each task from two phases. In the experience phase, the robot follows
a scripted sequence of events while the memory module records its observations. In the request phase, the
agent starts from a fresh context and uses memory to answer information requests and plan action requests,
as a robot would when a user poses a request. Plans are executed without returning new observations, so
the agent cannot compensate for missing memory by searching again, which would reward exploration ability
rather than memory. Experience phases can also be stacked to evaluate memory over longer histories.
We instantiate this protocol in 53 simulated tasks across four simulated indoor environments and seven
categories of remembered information. MeMoREval supports textual records, generated image descriptions,
camera frames, scene graphs, and their combinations. Using common recorded observations and a fixed agent
implementation, we compare different memory configurations on task success as well as model inference costs,
as both write-time and read-time costs are candidates to be optimized in embodied agent design.
Our reference evaluations show that storing camera frames with scene graphs achieves the highest aggregate
task success for every tested model. For the primary model, archiving frames achieves higher success and
lower write-time inference cost than generating descriptions, while also yielding the lowest read-time inference
cost per successful request. The benefits of individual modalities vary across models and task categories,
demonstrating the value of evaluating representations together with the models that use them.
We further examine deployment-oriented variants that accumulate experience across tasks, let writers select
which frames to retain, or provide images to writers during memory construction. These variants preserve the
benchmark’s evaluation structure while extending the design choices under study. The resulting differences
in task success, retention rates, and inference costs illustrate how MeMoREval can support investigations of
memory organization, evidence selection, and writer inputs. Two demonstrations on a physical robot further
establish that the protocol and memory interfaces can be instantiated using camera observations and an
annotated spatial map.
We situate the memory-modality question within prior work on LLM and embodied agents and their eval-
uation (§ 2), then establish the agent model and memory terminology needed to study it (§ 3). We then
introduce the design of our evaluation protocol and its instantiation in MeMoREval (§ 4). Our experiments
address the three research questions and demonstrate the protocol on a physical robot (§ 5).
Our contributions are:
• A controlled memory evaluation protocol for embodied agents that separates experience from subsequent
information and action requests, supports accumulated histories, and measures write-time and read-time
inference costs.
• MeMoREval, a benchmark of 53 tasks across four simulated environments, with configurable memory
modalities and backends and complementary demonstrations on a physical robot.
• Reference evaluations across memory modalities, models, and backends that characterize trade-offs be-
tween task success and inference cost and identify opportunities for improving evidence retention and
access in deployed embodied agents.

2 Related Work
Memory for LLM agents. Agent memory systems organize retained experience in different ways: MemGPT
pages information between the context window and an external archive (Packer et al., 2023), Mem0 extracts
and updates facts (Chhikara et al., 2025), A-MEM links evolving notes (Xu et al., 2025), Reflexion and
Agent Workflow Memory distill feedback and reusable procedures (Shinn et al., 2023; Wang et al., 2025b),
and filesystem memories let agents read and reorganize files through generic file tools (Zhou et al., 2026).
Benchmarks such as LoCoMo and LongMemEval chiefly test recall across long conversations (Maharana
et al., 2024; Wu et al., 2025), while MemLens and MemEye evaluate whether memory systems preserve
visual evidence across extended multimodal interactions (Ren et al., 2026; Guo et al., 2026).
We study
the corresponding design choice for embodied agents, comparing memory modalities with the agent and
observations held fixed and repeating the comparison across memory backends.
Memory for embodied agents. Object-centric scene graphs are widely used for robot mapping and plan-
ning (Gu et al., 2024; Wang et al., 2025a), so we include them as one storage modality alongside text,
generated descriptions, and frames. Other systems combine scene graphs with images (Saxena et al., 2025)
or record changing state through text and spatio-temporal relations (Zhang et al., 2026; Gorlo et al., 2026a;
Ma et al., 2026). Retrieval and indexing methods improve the efficiency and accuracy of multimodal mem-
ory (Anwar et al., 2025; Long et al., 2026; Hu et al., 2026) and are complementary to the choice of what
to store. Surprise-gated memory addresses which observations to preserve (Gorlo et al., 2026b); we examine
this selection question by comparing writer-selected image retention with archiving every frame.
Embodied benchmarks with memory demands. Household benchmarks test long-horizon embodied interac-
tion (Shridhar et al., 2020; Li et al., 2023; Yang et al., 2025), but memory failures there are confounded with
exploration, planning, and manipulation ability. Memory-focused evaluations test question answering (Ma-
jumdar et al., 2024; Ginting et al., 2025), memory-dependent action (Yadav et al., 2025; Kwon et al., 2026),
or both (Zhang et al., 2026), typically by comparing complete memory systems or agents. When the stored
modality does vary, other factors vary with it: in OpenEQA, for example, caption- and scene-graph-based
agents use a language model, whereas frame-based agents use a vision-language model (Majumdar et al.,
2024). We design our protocol so that the stored modality is the main variable. Within each backend, the
main memory conditions share the same recorded observations, agent, and writer input, and descriptions and

3 Preliminaries: LLM-Based Embodied Agents and Memory
We consider LLM-based embodied agents in which a language or vision-language model selects physical skills
for a robot. The interaction loop resembles that of a coding agent: the model receives a task and observations,
calls a tool, and uses the returned feedback and updated observations to decide the following action. Each
tool corresponds to a physical skill, such as navigating to a room, grasping an object, or opening a drawer,
executed by a separate robot controller so the model chooses actions without generating motor commands.
This scheme of wrapping robot capabilities as LLM-callable tools is also used by other works (Wang et al.,
2026; Flexion Team, 2026). Observations include camera images, detected objects and their locations, user
messages, and tool feedback. They may reach the model directly, or information from visual and spatial
sensing may be converted into textual records. The observation depends directly on the robot’s current state
and perception. For example, opening a drawer reveals its contents, while moving to another room removes
previously visible objects from view.
We treat memory as an external module that the agent uses through tool calls (Packer et al., 2023). The agent
is the model together with its current context. At each step it infers the next tool call from its context, and
information that leaves the context persists only if the memory module retains it. The memory module holds
all persistent state and records observations, either through a writer, a model that processes observations
into memory records, or by archiving artifacts such as camera frames directly. It makes stored information
available through context supplied to the agent and retrieval tools for particular records or artifacts, which
the agent uses to answer questions or plan actions (Figure 1). We refer to the agent as the reader when
it uses stored information in this way. The writer and reader are functional roles and may use the same
underlying model, as in our experiments. Some memory configurations require no writer, such as a transcript
that stores observations verbatim.
We characterize the memory module by two properties. The memory modality is the form of retained evidence,
such as textual records, camera frames, or structured spatial records. The memory backend is how memory
is organized and retrieved, for example as a rolling transcript or interconnected notes. A single backend can
support multiple memory modalities, for example by organizing textual entries that reference stored camera
frames, generated descriptions, or scene-graph snapshots.
4 MeMoREval: Evaluation Protocol and Benchmark
We introduce MeMoREval, a benchmark for evaluating memory modalities in robotic embodied agents. We
first describe its evaluation protocol, including task composition and measured performance metrics, such
as task success and inference costs (§ 4.1), and then discuss the simulation environments and tasks that
instantiate it (§ 4.2).
4.1 Evaluation Protocol
To evaluate how stored memory supports later decisions, we divide each task into two phases (Figure 1):
experience, during which the agent observes events and constructs memory, and request, during which it uses
that memory to respond to a user without receiving new information.
Experience. In deployment, experience comes from the robot’s ordinary operation, such as carrying out an
earlier request (Figure 1). In the benchmark, the robot instead executes a scripted sequence of actions while
the memory module records the resulting observations and action outcomes. These actions and surrounding
events provide information needed later: the robot may observe a mug being placed inside a cabinet before it
is closed, or hear a user identify which of several mugs is theirs. The agent has not yet received any requests,
so the memory module must retain information before knowing which details will matter. The experience

Request. The request phase begins with a fresh agent context containing no observations from the experience
phase. The agent receives a request that requires it to recover some information from its experience through
the memory module without receiving new observations. Requests are of two types. Information requests,
such as asking which cabinet contains a mug, test whether the agent can recover the relevant information
from memory. Action requests, such as retrieving the mug, test whether the agent can use that information
to act. For action requests, the agent submits a complete plan of skill calls, which the robot executes without
returning observations or allowing the plan to be revised. This open-loop execution prevents the agent from
compensating for missing memory by exploring the scene, for instance by opening cabinets until the mug
appears. Within a task, information requests are issued before action requests. Each request starts from a
fresh context containing only the request and the name of the robot’s current room, which facilitates initial
planning without supplying relevant past observations.
Stacked tasks.
Separating experience from requests allows tasks to be stacked: the experience phases of
several tasks are concatenated into a longer history, followed by all information requests and then all action
requests.
Before each action request, the simulator is restored to its state at the end of the combined
experience phase, so each plan is evaluated from the same physical state without interference from earlier
plans. Stacking tests whether earlier information remains available as experience accumulates, approximating
the longer histories encountered in deployment. Each component task retains its original grading criteria,
allowing the construction of longer-horizon tasks without redesigning individual ones.
Outcomes and cost.
Success for an individual task is defined as whether the agent correctly responds to
all requests of the task, and for a stacked composite task, it is measured as the fraction of component
tasks succeeded.
We measure model inference cost separately for memory construction and use.
Write-
time cost accrues during the experience phase as the memory module processes observations, for example
by summarizing text or describing images. Read-time cost accrues during the request phase as the agent
queries memory and produces an answer or plan. Write-time cost is incurred before knowing downstream
requests, while read-time cost arises only when responding to requests. Hence, write-time cost scales with
the number of actions taken by the agent, and read-time cost scales with the number of requests issued to the
agent. For a deployed embodied agent, both costs are highly relevant as robots could take frequent actions
in short intervals (e.g., moving through a home through a sequence of navigation skill calls) and could be
issued with requests frequently as well. Actual distribution of the two types of cost is determined by the
exact application scenario, and therefore we report the two costs separately. To include failed attempts, we
also report read-time cost per successful request.
4.2 Benchmark Environments and Tasks
Environments and robot. MeMoREval instantiates the protocol in the Genesis simulator (Genesis Authors,
2024) with four indoor environments adapted from pre-generated SceneSmith scenes (Pfaff et al., 2026): an
office, photography studio, home, and clinic, each with seven to nine rooms and 200–300 objects. See Figure 2
for snapshots during example tasks in all four scenes. The simulated robot is a Dexmate Vega 1 bimanual
mobile manipulator, which the agent controls through skills that navigate the robot to different places, open
and close furniture, and pick and place objects. These skills cover common navigation and manipulation

Task categories and construction.
MeMoREval contains 53 tasks across seven categories of remembered
information: object location, spatial configuration, appearance binding, set aggregation, user preference,
occluded state, and skill outcome (Table 1). These categories describe the information that must be remem-
bered, rather than which memory modality is expected to perform best. Each experience phase consists of a
scripted tour of the environment, followed by events such as an object being moved, a container being opened,
or a user expressing a preference. We also construct a stacked composite task from 10–11 component tasks
for each environment. Appendix B provides the individual tasks and composite construction.
Grading.
All requests are graded deterministically.
Information requests are checked against reference
answers of a specified type, such as a region, object, count, or set. Action requests are checked against
task-specific predicates on the final simulator state, such as whether the target object is held or rests on the
required surface.
Observations and representations.
We construct agent observations to reflect information available during
robot operation: camera images provide visual evidence, localization and mapping provide object locations
and relations, and interactions provide user instructions and action outcomes. The benchmark exposes this
information through visual, spatial, and textual observation streams.
Textual observations report user messages, skill feedback, and currently detected objects, including their
categories, articulation states, and support and containment relations. They omit color and texture, leaving
camera frames as the source of appearance information. Visual observations are camera frames annotated
with bounding boxes and integer object identifiers, which the agent also uses to refer to objects in tool
calls. Spatial observations are scene-graph snapshots whose nodes store object identifiers and world-frame
3D positions, while edges record support and containment relations (Gu et al., 2024; Werby et al., 2024;
Zhao et al., 2026). These snapshots contain no appearance attributes and do not explicitly encode ordinal
or viewpoint-dependent relations. In simulation, detections and spatial records are derived from simulator
state restricted to observed objects. § 5.3 describes a physical instantiation using camera observations and
an annotated spatial map.
Given these observations, a memory module can retain textual records, generate image descriptions, archive
camera frames, or preserve spatial snapshots. The choice of memory modality determines how the robot’s
experience remains available for later requests. Description generation and other transformations of obser-
vations are part of memory construction.

5 Experiments
5.1 Experimental Setup
Memory conditions. Our main comparison varies the evidence archived for later retrieval while holding the
memory writer’s textual input fixed. For a given backend, task, and seed, the six main conditions share the
textual memory constructed from the common observations in § 4.2. The text condition retains only this
memory. The frames condition additionally archives the annotated camera frames, while frames+graph also
archives scene graph snapshots. To test whether textual descriptions of camera frames can replace storing
frames themselves, we further design the conditions of desc@64, desc@256, and desc@1024, each archiving
generated descriptions of recorded frames at the indicated token budget.
Descriptions are generated in
separate calls using the same model as the writer and agent, from the annotated frame and the textual
observation of the same step. Like frames, they are stored verbatim for the agent to retrieve without passing
through the writer. Stored frames, descriptions, and scene-graph snapshots are indexed by the experience
step at which they were recorded. Each backend appends this step to every memory entry it renders, and the
agent retrieves artifacts by passing step numbers to the retrieval tool of its condition. Frame and description
retrieval return the stored artifacts, while scene-graph retrieval returns textual records of the requested objects
and their relations. The agent is allowed to make up to five retrieval calls before submitting a response to
a request. At most 20,000 characters of textual memory are rendered into the agent’s context per turn.
Retrieved frames, descriptions, and scene-graph records do not count toward this limit.
Memory backends.
We evaluate the memory conditions above across five backends that organize memory
differently. A transcript retains a rolling history without an LLM-based writer, and a wiki writer maintains
named pages through append and rewrite operations. We further adapt three published memory systems
to the shared interface and our embodied setting, A-MEM (Xu et al., 2025), Mem0 (Chhikara et al., 2025),
and ObsMem (Zhang et al., 2026). All writers receive the same observations and instructions on what to
remember, and all backends share the memory-context limit and artifact retrieval described above.
Reference conditions.
In addition to the five memory backends, we implement two control conditions that
bypass memory construction.
The no-memory condition tests performance without memory, while full-
information supplies hand-authored textual facts sufficient for each task.
Deployment-oriented variants. The single tasks under the six main conditions form a controlled comparison:
experience is short, the writer sees only textual observations, and artifact storage is automatic.
Actual
deployment of embodied agents could benefit from some relaxations, and we evaluate three of them. First,
every main condition also runs on the four stacked composite tasks (§ 4.1). Second, because a deployed
memory writer would have camera images at hand, sighted variants of frames and frames+graph that also give
images to the writer test whether interpreting images during memory construction brings additional benefits
over direct archival. Third, because archiving every frame grows storage with the length of deployment, a
selective-storage variant of frames lets the memory writer decide whether to archive each frame using only
the textual observations. The writer does not inspect the image, and only retained frames remain retrievable.
Models and runs. The main experiments use Gemini 3.7 Flash. With this model, we evaluate the six main
memory conditions across five memory backends on all 53 single tasks and conduct the deployment-oriented
evaluations, each across three seeds.
To assess whether the relative performance of memory conditions
depends on the model, we also evaluate GPT 5.6 Sol and GLM 5.3 Flash on all single tasks, using the six
main conditions and three backends (transcript, wiki, and A-MEM) with one seed. Both control conditions
are evaluated once per task at a single seed. All models run at temperature 0, and each run uses the same
underlying model for the writer, describer, and agent wherever these roles are present.
Cost accounting.
We report inference cost in weighted tokens, Tin × Pin/Pout + Tout, where Tin and Tout
are the numbers of input and output tokens and Pin and Pout their per-token prices. Input tokens include
image tokens and output tokens include reasoning tokens. Weighted tokens therefore equal cost divided by
the output-token price, so they are proportional to cost within each model. Because tokenizers and prices
differ across models, we compare costs only across conditions within a model. Write-time cost covers writer
updates and description generation during experience and is reported per experience step. Read-time cost
covers all model calls in the request phase and is reported per attempted request and per successful request.

Figure 3 compares task success against memory cost for Gemini 3.7 Flash, averaged across the five memory
backends and three seeds. Error bars show the minimum and maximum across seeds. We first examine the
effect of memory modality on information and action requests, then its effect on inference costs, and lastly

Controls.
Without memory, the agent solves 3 of the 53 tasks; with full-information memory, it solves all
53. Every task is therefore solvable when the relevant facts are explicitly available as text. The following
comparisons examine how effectively the tested memory representations preserve evidence that the agent can
retrieve and use.
5.2.1 RQ1: How does memory modality affect task success?
Storing descriptions of camera frames achieves task success from 56% to 60% as the description budget grows
from 64 to 1024 tokens, compared against 39% without any descriptions and 70% if storing the frames directly
(Figure 3a). Since descriptions and frames are archived independently of the writer and retrieved through
the same mechanism, the description gap therefore does not arise from a memory writer further summarizing
or omitting the generated descriptions and instead reflects what information the different modalities store
and how effectively the reader uses them.

5.2.3 RQ3: What do deployment-oriented variants show about memory design?
We next examine the deployment-oriented variants introduced in § 5.1: accumulated experience, selective
image retention, and visual input to the memory writer. These variants extend the main modality comparison
to practical memory-design choices while retaining the benchmark’s experience-request structure and grading
criteria.
Accumulated experience.
Figure 6 shows that memory backends respond differently to longer histories.
Transcript degrades substantially under stacking, because its rolling history exceeds the shared memory-
context budget, truncating earlier observations and their retrieval cues from the reader’s context. The other
adapted backends exhibit different responses to accumulated experience, suggesting that memory organization
and retrieval influence how useful evidence remains accessible as histories grow. These results motivate further
investigation of the underlying memory design.
Selective image retention.
Archiving every observed frame causes storage to grow with experience. Selec-
tive retention therefore requires deciding which observations may support requests that are not yet known;
recovering omitted evidence may later require additional physical interaction. Under the same selection in-
struction, the tested writers retain 8-55% of frames, with lower mean task success than automatic archival
for each backend (Figure 6). The differing retention rates and performance changes expose the balance be-
tween reducing archival volume and preserving useful evidence, motivating retention policies suited to each
backend’s memory organization.
Visual input to the writer.
Giving the writer access to camera images does not consistently improve task
success (Figure 6). Because the reader can already inspect archived frames, visual interpretation by the
writer may offer additional value primarily through better memory entries or retrieval cues. The inconsistent
success gains suggest that the tested writers do not reliably realize this benefit.
Changes in write-time
cost further show that visual input affects the memory-construction process even when downstream success
remains similar (Appendix A).

5.3 Real-World Instantiation
We deploy our memory evaluation protocol on a physical Dexmate Vega 1 bimanual mobile manipulator,
matching the simulated embodiment, using existing controllers for navigation and manipulation. We construct
a 3D map using SLAM and manually annotate objects and semantic relations, including support relations,
to obtain scene-graph records. Visual observations come from the robot’s head-mounted camera, with object
segmentation performed using SAM 3 (Carion et al., 2025).
We design two demonstrations focused on memory of object arrangements. In the first, the robot discards a
soda can and should subsequently retrieve the fruit that had been beside it (Figure 1). In the second, the
robot moves a lemon to another table, and should then recall that its original plate was orange, followed by
retrieving the apple that had been to the lemon’s right.
In the two demonstrations, the robot correctly used its memory and completed both deliveries without
human assistance. We used wiki as the memory backend, using the frames+graph memory modality. These
demonstrations establish that the protocol and memory interfaces can be instantiated on a physical robot
using camera observations and a manually annotated spatial map, providing a concrete basis for future
comparisons of memory configurations in physical environments.
6 Conclusion
We present MeMoREval, a benchmark for evaluating memory in embodied agents through a controlled
experience–request protocol, which tests whether retained observations support subsequent recall and action,
while measuring inference costs separately for memory construction and use. Our reference evaluations show
that memory modality affects both task success and inference cost, with benefits varying across models and
task categories. For the primary model, retaining camera frames achieves higher success than generating
descriptions at lower write-time inference cost, while adding scene graphs further improves success at higher
read-time cost.
Deployment-oriented variants demonstrate how the benchmark supports investigating additional memory-
design choices. Accumulated experience affects backends differently, and selecting frames from textual obser-
vations reduces archival volume with losses in task success. Giving images to the writer does not consistently
improve success, although it can reduce write-time cost for some backends. These findings motivate studying
how memory organization, retention decisions, and writer inputs interact. Two physical-robot demonstra-
tions instantiate the protocol using camera observations and an annotated spatial map, showing that the
benchmark’s protocol design can support evaluations beyond simulation. By providing common experiences,
interfaces, and grading, MeMoREval offers an extensible experimental basis for developing memory systems
for embodied agents.
