## 摘要
大型语言模型（LLM）正日益融入具身机器人规划，但标准基准主要评估理想环境下的端到端任务完成情况，因而难以揭示执行链各环节的故障来源。我们提出 Alpha，这是一个用于仿真环境中 LLM 驱动的操作任务的系统化故障注入与鲁棒性评估框架。Alpha 在感知（传感器延迟）、执行（抓握滑移）、运动学（目标不可达）和规划（规划器输出损坏）环节注入经过校准的故障，并评估这些故障并发出现时的情况。为区分物理层面的脆弱性与规划器敏感性，我们提出一种匹配评估方法：在由 150 个回合构成的平衡矩阵中，使用相同的随机种子、几何设置和安全标准，将一个 LLM 智能体（通过 Ollama 运行的 Llama-3）与一个确定性的 Scripted Oracle 规划器进行配对比较。在整个矩阵中，Oracle 的成功率为 64.0%（48/75），LLM 的成功率为 44.0%（33/75）（配对 McNemar 检验 p = 3.01 × 10^-4）。至关重要的是，排除规划器输出损坏这一情况后，两种规划器在所有物理和运动学条件下的表现完全相同：成功率均为 55.0%（33/60），且不存在不一致配对（McNemar 检验 p = 1.00）。这表明，物理执行器滑移、运动学可达边界以及感知信息过时，对确定性控制器和 LLM 规划器的影响相同。性能差距完全由规划器输出损坏所致（Oracle 为 100%，LLM 为 0%），这将问题定位于从提示到 JSON 的序列化与验证接口，而非认知推理能力不足。我们还审计了 169 次历史试验，以确保结果透明。

## Abstract
Large language models (LLMs) are increasingly integrated into embodied robotic planning, yet standard benchmarks primarily evaluate end-to-end task completion in nominal environments, obscuring failure origins across the execution stack. We present Alpha, a systematic fault-injection and robustness-evaluation framework for LLM-driven manipulation in simulation. Alpha injects calibrated faults across perception (sensor lag), actuation (grip slip), kinematics (unreachable targets), and planning (planner-output corruption), alongside concurrent conditions. To separate physical vulnerabilities from planner sensitivities, we introduce a matched methodology pairing an LLM agent (Llama-3 via Ollama) against a deterministic Scripted Oracle planner across a balanced 150-episode matrix under identical seeds, geometries, and safety criteria. Across the matrix, the Oracle achieves 64.0% (48/75) success while the LLM achieves 44.0% (33/75) (paired McNemar p = 3.01 x 10^-4). Crucially, excluding planner-output corruption, performance across all physical and kinematic conditions is identical: 55.0% (33/60) for both planners with zero discordant pairs (McNemar p = 1.00). This demonstrates that physical actuator slip, kinematic reach boundaries, and perceptual staleness affect deterministic controllers and LLM planners equivalently. The performance gap is driven entirely by planner-output corruption (100% Oracle vs. 0% LLM), isolating the prompt-to-JSON serialization and validation interface rather than a cognitive reasoning deficit. We also audit 169 historical pilot attempts for transparency.

## 1. 核心问题与整体含义

论文关注的核心问题是：**具身机器人在执行任务失败时，如何判断失败究竟来自物理环境与机器人本体、感知信息、运动学限制，还是 LLM 规划及其软件接口？**

现有具身任务评测通常关注正常环境中的端到端成功率。这样的指标难以定位故障来源，可能把夹爪打滑、目标超出机械臂可达范围等物理限制，误归因于 LLM 的推理能力不足。为此，论文提出 Alpha，一个用于仿真操作任务的系统化故障注入与鲁棒性评估框架，并通过与确定性脚本规划器进行种子匹配的对照，分离环境故障与规划接口故障。

论文的核心含义是：**评估具身 LLM 不应只看总成功率，还应按执行链路注入故障、记录故障位置，并使用匹配基线判断故障是否为 LLM 特有。**在这项实验中，LLM 与脚本规划器的整体成功率差异并非来自物理故障下的表现，而主要来自 LLM 输出经 JSON 序列化和校验时的脆弱性。

## 2. 方法论

### 核心思想

Alpha 将机器人执行过程划分为多个操作边界，在这些边界注入可控故障，并以相同实验条件比较：

- **LLM 规划器**：通过本地 Ollama 运行的 Llama-3，生成结构化操作计划。
- **Scripted Oracle 规划器**：读取场景中的真实物体坐标，直接生成确定性的抓取与放置轨迹。

两者共享相同仿真场景、随机种子、物理参数、任务设置及安全监控规则。比较的重点是：同一物理条件下，两个规划器是否在相同回合成功或失败。

### 故障类型与关键细节

论文注入四类单点故障，并设置一种并发故障条件：

1. **F1：传感器延迟（感知层）**
   - 从观测历史缓冲区返回较早的场景状态。
   - 请求延迟由公式  
     \[
     \tau_{\text{lag}} = 0.10 + 1.40I \quad \text{秒}
     \]
     确定，其中强度 \(I\in\{0.33,0.66,1.00\}\)。
   - 由于历史缓冲区只有约 0.5 秒，实际延迟在各强度下均饱和于 0.5 秒；观测到的物体位置偏差约为 2.5 厘米。

2. **F2：抓握滑移（执行层）**
   - 在物体被抓取并开始抬升时，以概率触发滑移：
     \[
     P_{\text{slip}} = 0.10 + 0.85I
     \]
   - 滑移概率仅在每次抬升事件中评估一次，避免逐仿真步重复抽样导致滑移概率被人为放大。
   - 触发后削弱或移除夹持约束，由仿真中的接触摩擦与重力决定物体是否掉落。

3. **F3：不可达逆运动学目标（运动学层）**
   - 将末端执行器目标沿外向方向偏移：
     \[
     \delta_{\text{reach}} = 0.03 + 0.27I \quad \text{米}
     \]
   - 偏移使目标超出机械臂的可达范围。
   - 由于各强度下成功率均为零，论文还测量物体最终位置与放置区域中心之间的连续距离误差。

4. **F4：规划输出损坏（规划／序列化层）**
   - 以概率  
     \[
     P_{\text{corrupt}} = 0.20 + 0.80I
     \]
     删除 JSON 中的关键字段或破坏字符串语法。
   - 损坏内容进入 Pydantic 校验；校验失败后返回空动作计划，阻止错误轨迹发送到机器人控制器。
   - Scripted Oracle 直接生成内存中的对象，不经过 JSON 序列化，因此不受该故障影响。

5. **并发故障**
   - 同时施加中等强度的 F1 传感器延迟与 F2 抓握滑移。

### 执行流程与安全监控

典型执行流程为：仿真场景生成与观测 → 注入感知延迟 → 规划器生成动作 → 对 LLM 输出进行 JSON 校验并可注入损坏 → 对运动学目标注入偏移 → 执行抓取与抬升并可注入滑移 → 记录遥测并进行安全监控。

安全监控器以 **240 Hz** 检查机械臂接触与工作空间状态。接触力阈值为 3000 N，并通过连续 15 个仿真步的时间去重窗口，将高频重复扫描合并为持续安全事件。监控结果用于识别越界和碰撞等事件。

## 3. 实验设计

### 任务与场景

- **仿真平台**：PyBullet，使用无图形界面的 DIRECT 模式。
- **机器人**：7 自由度 Franka Emika／KUKA IIWA 机械臂，配平行夹爪。
- **任务**：从桌面抓取一个红色方块，并放入指定放置区域。
- **放置区域中心**：\((0.6, 0.35, 0.65)\) 米；论文报告的成功判据为进入目标区域（文中出现半径 0.05 米及 0.08 米边界阈值的表述）。
- **单回合上限**：1260 个仿真步，即约 5.25 秒模拟时间。

### Benchmark 与对比方法

这不是使用外部标准数据集的实验，而是作者在 PyBullet 中构造的**单一合成操作 benchmark**。总计 150 个回合，由两种规划器各执行 75 个：

| 实验条件 | 强度／设置 | 每种规划器回合数 |
|---|---:|---:|
| 无故障基线 | \(I=0\) | 10 |
| F1 感知延迟 | 低、中、高 | 每档 5 |
| F2 抓握滑移 | 低、中、高 | 每档 5 |
| F3 不可达 IK | 低、中、高 | 每档 5 |
| F4 输出损坏 | 低、中、高 | 每档 5 |
| F1+F2 并发故障 | 中等强度 | 5 |

LLM 与 Scripted Oracle 在每个匹配回合中使用相同场景种子、物体初始位置、物理参数与故障设置。主要评估指标包括任务成功率、放置距离误差、故障或安全事件，以及输出校验拒绝情况。

- 主要包含无故障基线、四类故障各三档强度，以及一种并发故障条件。

## 6. 主要结论与发现

1. **整体结果存在显著差异**：Scripted Oracle 成功率为 64.0%（48/75），LLM 为 44.0%（33/75）；配对 McNemar 检验 \(p=3.01\times10^{-4}\)。
2. **排除 F4 后，物理、感知与运动学条件下表现一致**：两种规划器均为 55.0%（33/60），没有不一致配对，McNemar 检验 \(p=1.00\)。
3. **F1 的实际延迟受缓冲区限制**：请求延迟虽随强度增加，但实际延迟均饱和在约 0.5 秒；由此产生的 2.5 厘米位置偏差没有影响成功率，两种规划器均为 15/15 成功。
4. **F2 导致随强度增加的成功率下降**：两种规划器在匹配种子下发生滑移的回合相同；低、中、高强度的经验滑移率分别为 40%、60%、80%，对应成功率分别为 60%、40%、20%。
5. **F3 使两种规划器在所有强度下均无法完成任务**：成功率均为 0%；连续放置误差揭示了偏移程度的差异，但由于每格仅 5 次且仿真高度确定，不宜过度解释细微差异。
6. **F4 完全解释了整体成功率差距**：Oracle 为 15/15 成功，LLM 为 0/15；LLM 输出被损坏后，Pydantic 校验拒绝并返回空计划。
7. **安全监控呈现故障定位作用**：报告的越界事件只出现在 F3；改变去重窗口并未改变持续事件的计数。

## 7. 优点

- **故障分类覆盖执行链多个边界**：将感知、执行、运动学和序列化故障分别建模，便于定位失效来源。
- **采用匹配对照而非只报总体成功率**：同种子、同场景的 Oracle 对照有助于识别哪些失败并非 LLM 特有。
- **将接口故障纳入具身鲁棒性评估**：把提示到结构化动作之间的序列化与校验纳入测试，体现真实系统的软件边界风险。
- **使用连续指标补充二元成功率**：F3 下任务成功率已全部为零，放置距离误差仍能提供部分退化信息。
- **安全监控和遥测较为细致**：监控频率、力阈值、工作空间和事件去重机制均有明确说明，并对去重窗口做了敏感性检查。
- **披露历史试验及排除原因**：将外部 API 基础设施中止与正式实验分开，降低未报告失败或选择性纳入的疑虑。
- **区分“任务失败”与“安全失败”**：F4 的 schema 拒绝会安全地阻止错误动作，而非让损坏计划直接控制机械臂。

## 8. 不足与局限

- **任务与场景覆盖有限**：仅有单一 PyBullet 桌面抓取放置任务，无法验证多物体、长程规划、动态环境、遮挡或现实接触条件下的表现。
- **模型覆盖有限**：仅评估一个 Llama-3 本地模型，不能据此推广到其他开源模型、闭源模型或视觉—语言—动作模型。
- **样本量较小**：每个故障强度单元仅 5 个回合，导致单元级置信区间较宽，强度趋势的统计把握有限。
- **F1 严重程度未真正拉开**：历史缓冲区只有 0.5 秒，三档请求延迟实际都饱和于同一水平，因此该实验没有充分测试更长延迟的影响。
- **F4 的结论范围较窄**：它测试的是输出语法和 schema 校验失败，不是语义错误、计划质量下降或模型推理鲁棒性。
- **Oracle 基线不等同于一般确定性控制器**：Oracle 直接读取仿真真实状态，绕过 LLM 的序列化接口；这种设计有利于隔离接口问题，但也使其与现实可部署系统的感知条件不同。
- **故障注入方式较理想化**：注入规则可控且明确，但现实硬件故障、传感器延迟和通信错误可能更复杂、随机且相互作用更强。
- **资源报告不完整**：没有给出 GPU、CPU、内存等硬件配置，限制了推理成本复现与计算效率比较。
- **结果适用范围有限**：论文的结论应理解为对该仿真任务、模型和故障实现的证据，不宜直接外推为“LLM 在物理故障下普遍不存在推理缺陷”。
