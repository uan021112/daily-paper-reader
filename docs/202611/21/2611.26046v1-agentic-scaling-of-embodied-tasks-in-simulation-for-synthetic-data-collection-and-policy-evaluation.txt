Abstract
Scaling embodied interaction data requires a broad col-
lection of usable tasks, yet specifying and validating each
task instance remains costly. We present AgenticTask, an
agent-based framework that expands existing task collec-
tions under human intent. Its central representation links
interaction requirements to object and part bindings, scene
and robot configurations, initial conditions, and comple-
tion criteria.
A task-generation agent reuses interaction
structure to construct supported variations and revises in-
compatible configurations using validation feedback.
A

1. Introduction
Training general-purpose embodied policies requires large-
scale and diverse interaction data, yet existing datasets re-
main insufficient to support robust generalization across
tasks and environments.
Human-driven data collection
alone is unlikely to bridge this gap. Simulation provides a
scalable alternative for generating synthetic demonstrations,
systematically evaluating learned policies, and enhancing
their generalization across diverse tasks and scenarios.
However, scaling embodied task generation in simula-
tion remains hindered by two fundamental challenges: scal-
able task specification and efficient autonomous execution.
Despite advances in automated 3D modeling and simula-
tion engines, defining diverse tasks requires jointly reason-
ing over task objectives, scene configurations, interactive
objects, and simulator capabilities. Automated execution
presents further challenges: teleoperation is labor-intensive,
scripted approaches lack scalability, and policy-based meth-
ods suffer from a circular dependency between policy train-
ing and data collection.
Recent work has explored large language models
(LLMs) for automating robotic task and data genera-
tion. GenSim2 uses multimodal and reasoning models to
generate tasks and demonstrations [10], while GENMA-
NIP translates task descriptions into task-oriented scene
graphs [4]. SAGE and RoboGene further incorporate tool
use and feedback into scene construction and task refine-
ment [27, 30]. These advances demonstrate the potential
of language models to translate high-level requests into
task proposals.
However, constructing usable tasks re-
quires more than generating descriptions or code: candi-
date tasks must be instantiated, checked against the envi-
ronment, and revised when incompatibilities arise. These
requirements motivate an agent-based approach that con-
nects model reasoning with resource retrieval, simulation
tools, and feedback-driven decisions throughout task con-
struction and execution.
Yet equipping an agent with tools does not by itself en-
sure usable task generation and execution. During genera-
tion, object and scene variations require consistent updates
to physical targets, initial conditions, and success criteria,
together with checks of physical validity and robot compat-
ibility. During execution, the agent must ground task plans
in actionable parts, scene geometry, and robot-supported
skills. These challenges call for a shared representation that
connects task requirements to physical entities, with valida-
tion feedback guiding task repair and geometric information
supporting action selection.
To address these challenges, we present AgenticTask,
an agent-based framework for expanding task collections
through two specialized agents. The task-generation agent
translates human intent into structured task requirements,
retrieves compatible resources, and constructs variations
supported by the simulator.
Construction and validation
feedback guide revisions to permitted configurations while
preserving the intended interaction.
The task-execution
agent grounds the resulting task in robot-supported skills
using object bindings, part information, and scene geome-
try. It updates action choices from execution feedback and
checks completion against the task’s original success con-
ditions, providing concrete evidence of task usability.
A hierarchical task representation connects the two
agents.
Semantic specifications identify the interaction
requirements and permitted variations; instantiated task
records bind these requirements to objects, parts, initial con-
ditions, and success predicates; geometric scene graphs de-
scribe the entities and relations needed for checking and ac-
tion grounding. This representation gives task construction,
validation, and execution a consistent reference as objects
and scene configurations change.
Using RoboCasa as a testbed [20], we construct the
AgenticTask collection, comprising 16,450 saved task
instances.
Our experiments characterize construction
throughput, physical screening, and the cost of feedback-
guided revision. Execution results and four successful tra-
jectories demonstrate usability across several interaction
types, while failure analysis identifies obstacles in action
selection, task–robot compatibility, and runtime integration.
Together, these results characterize both the productivity of
task expansion and the practical requirements for using the
generated collection.
Our contributions are threefold:
1. An agent-based framework for task-collection expan-
sion. AgenticTask uses human intent to guide task con-
struction across compatible objects and scenes, and cou-
ples generation with execution-based usability testing to
support embodied interaction-data collection.
2. A hierarchical task representation connecting gener-
ation and execution. Semantic requirements, object and
part bindings, and geometric relations provide a shared
basis for constrained task variation, feedback-guided re-
vision, and robot skill grounding.
3. A task collection and an empirical study of its con-
struction and usability.
The AgenticTask collection
contains 16,450 saved task instances in RoboCasa. Our
study characterizes construction productivity, physical
screening, execution outcomes, and failure patterns that
inform further task and system refinement.

3. Method
Expanding a task collection requires preserving the in-
tended interactions while specifying how each new instance
can be realized and checked. During construction, changes
to physical entities must remain consistent with the task in-
struction, initial conditions, and success criteria. During ex-
ecution, these task-level requirements must be grounded in
contact regions, geometric parameters, and robot-supported
actions.
We address both challenges by organizing con-
struction and execution around a shared task record, sup-
ported by a hierarchical representation and two specialized
agents. The generation agent constructs task variants within
supported configuration spaces and revises them using val-
idation feedback. The execution agent uses the same entity
bindings and geometric records to select skills and test task
completion. Both agents use GPT-6 Astra with separate in-
teraction histories; simulator and robot tools provide con-
struction, checking, and control operations. Figure 3 links
task generation and execution testing through the shared
task record.
3.1. Hierarchical Task Construction
A task variation can preserve the intended interaction while
changing the entities that realize it. For example, placing a
cup into a sink retains the source–destination relationship,
but a different cup or kitchen layout changes the relevant
bindings and geometry. Generating these elements inde-
pendently can leave the instruction, simulator configuration,
and success predicate referring to different entities.
We
therefore separate reusable interaction requirements from
instance-specific bindings and geometric states, while ex-
plicitly linking the three levels (Fig. 2). Given a human
request u, source tasks T0, assets A, environments E, and
a robot profile R, the resulting representation supports both
task construction and execution. The robot profile specifies
available skills, gripper and motion limits, and permitted
base motion.
3.1.1. Semantic Task Specification
Task expansion requires distinguishing variations that pre-
serve the requested interaction from changes that redefine
the task. We express this distinction through a shared se-
mantic specification:
I = (K, H, V).
(1)
Here, K specifies interaction families, H contains require-
ments that must be preserved, and V defines permitted vari-
ations and their ranges.
Source tasks supply interaction
roles and, for composite tasks, prerequisite relations. In
the cup-to-sink example, the source and destination roles
and the placement goal remain fixed, while compatible cups
and kitchen layouts may vary. Sharing I across instances al-
lows the generation agent to expand the collection without
redefining its requirements for each candidate. It also pro-
vides a reference for checking whether a repair preserves
the requested task.
3.1.2. Asset and Scene Construction
Instantiating a task requires binding its interaction roles,
initial conditions, and completion criteria to concrete sim-
ulator entities. Categories narrow the available resources,
while functional parts identify the entities that can fulfill
each role. For cup placement, the movable object and desti-
nation must resolve to a specific cup and sink interior. Their
configuration is organized within a shared task record:
τ = (k, B, E, P0, G, C, ℓ).
(2)
The record contains the interaction template k, role-to-
entity bindings B, scene and robot configuration E, ini-
tial conditions P0, completion predicate G, execution con-
straints C, and instruction ℓ. Bindings resolve roles to simu-
lator objects, parts, joints, or regions, so that the instruction
and predicates refer to the same physical targets. The scene
and robot configuration E provides the physical setting in
which the requirements P0, G, and C are interpreted. When
a bound entity changes, the associated conditions and in-
struction are updated to refer to that entity while preserving
the requirements in I. This links object and scene variation
to a fully specified task instance.

3.2. Task-generation Agent
As shown in Fig. 3(a), the generation agent expands a
shared task specification into concrete instances within the
capabilities of the available simulator and robot. It uses I to
preserve the requested interaction and a supported config-
uration space to select how that interaction is instantiated.
Construction tools resolve those choices into task bindings,
initial states, and geometric records. Checking feedback
then identifies configurations to revise while keeping the
task requirements fixed.
Capability-constrained task instantiation.
Before con-
struction, the agent retrieves task capability profiles and
compatible resources. Categories guide resource selection,
while part descriptions identify candidates for the required
interaction roles. A task profile specifies the available tem-
plate and supported variation parameters. Together with I,
it defines the permitted configuration space ΩI. At attempt
r, the agent selects a configuration using the construction

proposals tied to the capabilities of the underlying environ-
ment.
Feedback-conditioned revision.
When construction or
validation fails, repeating a proposal without using the fail-
ure evidence can reproduce the same incompatibility. The
agent conditions its next revision on the diagnostic stage,
affected entities, and checking evidence, while restricting
changes to V and the supported task profile. For a place-
ment task, an incompatible object or layout can motivate
another permitted configuration; changing the destination
goal merely to obtain acceptance would violate H.
Revision preserves fixed task requirements and un-
changed configuration fields.
The native constructor re-
builds each revised configuration, after which the required
checks are rerun and the history remains associated with
the original candidate. Generation terminates when the re-
quested collection is obtained, the candidate or retry bud-
get is exhausted, or the requirements cannot be supported.
This design directs configuration edits toward identified in-
compatibilities. Section 4.3 examines the resulting trade-off
between additional saved tasks and revision cost.

3.3. Task-execution Agent
Executing a generated task requires translating its bound
roles and completion criteria into concrete contacts, motion
parameters, and skill transitions. Figure 3(b) shows how the
execution agent uses the received task record, current ge-
ometry, and robot-supported skills to make these decisions.
It restores the saved task state and keeps the definition,
goal, constraints, and action/retry budgets fixed. A separate
model context selects actions from observations and tool
feedback, while an independent checker determines task
completion. Execution thus tests whether the generated task
supports the specified interaction under the original comple-
tion criteria.

Task-preserving interpretation of execution traces.
The shared task record supplies a stable reference as the
physical state changes. The binding map identifies the ob-
ject, functional part, or destination region used by a skill;
current geometry supplies its actionable pose; and the lo-
cal postcondition determines whether the next transition can
proceed. Grasping an object, rotating a control, and pushing
a door therefore use different contact and motion parame-
ters while retaining the same division between task require-
ments and robot actions. For a composite task, complet-
ing one local postcondition permits further action selection
without redefining the final task goal. The traces in Sec. 4.5
illustrate this progression through object placement, artic-
ulated control, door closure, and sequential arrangement.
Intermediate views explain how the task is attempted, while
the independent rollout check establishes its completion.
4. Experiments and Analysis
We examine task construction, diagnostic repair, and robot
execution. Successful cases connect the representation to
concrete interactions, while failure analysis identifies ob-
stacles to broader task usability.
4.1. Setup and Task Collection
We instantiate our framework using RoboCasa tasks and as-
sets, producing a collection of 16,450 saved task instances.
Atomic tasks involve one reference skill, while composite
tasks combine multiple skills under a fixed decomposition.
Figure 4 summarizes the collection through 72 merged dis-
play groups and the distribution of scene composition.
Construction statistics include retries, and saved records
are deduplicated by task and version identifiers. Execution
tests restore each task’s initial state and retain its original
goals and constraints.
4.2. Task Generation and Physical Screening
Table 1 reports 16,450 saved task instances from 20,323
construction attempts, corresponding to a saving yield of
80.94%. The collection includes 1,630 instances saved af-
ter repair. Over 98.52 elapsed hours, the pipeline produces
166.97 saved instances per hour, demonstrating sustained
task-collection expansion across repeated construction and
revision cycles.
Physical screening retains 62.26% of all construction at-
tempts. The difference between saving yield and screening
yield shows that producing a task package and satisfying its
physical requirements are distinct stages. This result sup-
ports the explicit selection stage in Sec. 3.2.1: construction
provides candidate instances, while screening selects those
satisfying the configured checks.
Among categorized construction losses, worker failures
account for 3,441 attempts, compared with 339 duplicate
rejections and two size-limit violations. Construction re-
liability is therefore the dominant observed source of lost
output. These results identify complementary directions for
improving productivity: reducing construction interruptions
and avoiding repeated proposals.
4.3. Effect of Diagnostic-guided Repair
Table 2 compares resampling with diagnostic-guided repair
under fixed task requirements and checking conditions. Re-
pair increases saving yield from 96.5% to 97.2%, while
time per saved instance rises from 21.6 to 23.3 seconds and
reported model calls increase from 0.12 to 0.31.
The results reveal a yield–cost trade-off.

terpreting the feedback and reconstructing revised config-
urations introduce extra cost. Repair therefore provides a

4.4. Execution-based Usability and Failure Analysis
Approximately 38% of executed tasks are completed under
their original goals and constraints, as checked by Eq. 8.
These successful rollouts demonstrate that generated task
instances can support robot interaction through the shared
task representation and execution interface. Table 3 ana-
lyzes unsuccessful runs to identify the main obstacles to
broader task usability.
Agent-related
execution
difficulties.
Agent-related
cases form the largest diagnostic category, accounting
for 12% of all executed tasks in the atomic group and
26% in the composite group. The associated difficulties
concern planning, grasp selection, tracking, and recovery.
Their prevalence identifies action selection and execution
feedback as major improvement targets for the execution
agent in Sec. 3.3.
Task–robot compatibility.
Cases assigned to task-design
issues account for 12% of all executed tasks and are concen-
trated in the composite group. They highlight potential mis-
matches involving object dimensions, grasp configurations,
reachability, and motion clearance. These cases guide re-
finement of the generation-stage compatibility checks. Di-
agnosis should consider the available interaction parts and
permitted actions: an oversized object body, for example,
may still admit a feasible grasp through its handle.
Runtime reliability.
Interface-related interruptions ac-
count for 2% and 10% of all executed tasks in the atomic
and composite groups, respectively. These outcomes iden-
tify task restoration, API interaction, and control integration
as additional factors affecting end-to-end completion.
The diagnosis links agent difficulties to skill selec-
tion and recovery, suspected design issues to compatibil-
ity screening, and interface interruptions to restoration and
control reliability. Execution thus supplies both successful
usability examples and feedback for task construction.

4.5. Successful Execution Cases
Figure 5 presents four successful tasks spanning object
placement, articulated control, door closure, and sequen-
tial arrangement. Together, they illustrate how the shared
task representation supports different interaction structures:
entity bindings identify the targets, geometric information
parameterizes actions, and task predicates determine com-
pletion.
Object placement.
In Fig. 5(a), the robot grasps a peach
from the counter, transfers it to the sink, and releases it in-
side the destination region. The execution connects the ob-
ject and destination roles in Sec. 3.1.2 to concrete grasping
and placement actions. Separating grasp completion from
the placement goal allows the agent to continue beyond ob-
ject acquisition and verify that the intended destination has
been reached.
Articulated control.
Figure 5(b) shows the robot estab-
lishing contact with an appliance knob and rotating it to the
target setting. Unlike free-object placement, this task acts
on a constrained functional part. The case illustrates how
part bindings and part-relative geometry specialize the ex-
ecution interface to articulated manipulation, with comple-
tion checked against the corresponding task condition.
Door closure.
In Fig. 5(c), the robot pushes the door,
repositions its end effector, and establishes another contact
before completing closure. The sequence illustrates execu-
tion under changing geometry: as the door moves, subse-
quent actions use the updated articulated state. It connects
the geometric-state updates in Sec. 3.1.3 with the feedback-
driven skill transitions in Sec. 3.3.
Sequential arrangement.
Figure 5(d) shows consecutive
placement of an avocado and an onion on a board. The
agent maintains separate object bindings across the two op-
erations and checks the final arrangement against the overall
task goal. This case illustrates the distinction between com-
pleting an individual skill and completing a composite task:
the first placement advances execution, while the full task
requires both object roles to be satisfied.
Across these cases, consistent task requirements guide
varied contacts, motion parameters, and skill sequences,
connecting generated definitions to robot actions across ob-
jects and interaction types.
4.6. Diagnostic Inspection of Generated Tasks
A separate inspection of 400 generated samples examines
task-verification obstacles. The sample contains 151 atomic
and 249 composite instances across 302 task classes. Ta-
ble 4 reports continuous execution witnesses for 34 atomic
and one composite instance, with the remaining cases cate-
gorized by their primary observed blocker.
The two groups exhibit different bottlenecks.
Execu-
tion probing is the largest category among atomic samples,
affecting 68 instances. For composite samples, semantic
and action adaptation dominates, affecting 127 instances,
including 76 requirement-parsing and 26 goal-logic adapta-
tion cases. This pattern indicates that broader verification of
composite tasks depends strongly on support for their goal
expressions and action structure.
Interface and restoration issues affect a further 20 atomic
and 43 composite samples.
The priorities are broader
composite-task adaptation and reproducible restoration.
5. Limitations
The task collection inherits the coverage and accuracy of
available assets, category/part annotations, and simulator
interfaces. Physical and robot-compatibility checks estab-
lish the configured conditions within their search budgets;
complete solvability requires additional evidence. Execu-
tion outcomes depend on the model, skill library, robot,
and retry budget, making task-versus-solver attribution un-
resolved for some unsuccessful trials. Explicit 3D inputs
support grounded decisions in simulation, while deploy-
ment with uncertain real-world perception remains outside
the present study.

6. Conclusion
We presented AgenticTask, an agent-based framework for
expanding embodied task collections under human intent.
A shared task representation connects interaction require-
ments, physical entity bindings, and completion criteria, al-
lowing generation and execution to operate on the same task
definition. On RoboCasa, the framework produces 16,450
saved task instances at 166.97 instances per elapsed hour.
Physical screening selects candidates satisfying the config-
ured checks, while successful executions demonstrate task
usability across object placement, articulated manipulation,
and sequential arrangement.
The experiments reveal complementary opportunities for
improving task-collection productivity. Diagnostic repair
increases saving yield at additional construction cost, while
construction failures identify reliability as a major source
of lost output.
Execution analysis directs improvements
toward grounded skill selection, task–robot compatibility
checks, and runtime integration. By connecting task con-
struction with execution evidence and diagnostic feedback,
AgenticTask provides a practical foundation for expanding
task resources for embodied interaction-data collection.
