## 摘要
扩大具身交互数据规模需要广泛收集可用任务，但对每个任务实例进行指定和验证仍然代价高昂。我们提出 AgenticTask，这是一种基于智能体的框架，可在人类意图指导下扩展现有任务集合。其核心表示将交互要求与物体及部件绑定、场景与机器人配置、初始条件和完成标准关联起来。任务生成智能体复用交互结构来构建受支持的变体，并根据验证反馈修订不兼容的配置。任务执行智能体使用相同的绑定关系和几何记录来选择机器人支持的技能，并依据原始任务标准检查是否完成。在 RoboCasa 上，该框架构建了 AgenticTask 任务集合：在 20,323 次构建尝试中保存了 16,450 个任务实例，每经过一小时可保存 166.97 个实例，其中 62.26% 的构建尝试通过了设定的物理检查。执行智能体完成了约 38% 的评估任务，成功案例涵盖物体放置、关节式物体操作和序列排列。诊断分析指出，构建可靠性、动作选择、任务与机器人兼容性以及运行时集成是需要优先改进的方面。总体而言，这些结果展示了任务集合扩展能力，并提供了经测量的构建效率和具体的执行证据，为后续具身智能交互数据采集奠定了基础。

## Abstract
Scaling embodied interaction data requires a broad collection of usable tasks, yet specifying and validating each task instance remains costly. We present AgenticTask, an agent-based framework that expands existing task collections under human intent. Its central representation links interaction requirements to object and part bindings, scene and robot configurations, initial conditions, and completion criteria. A task-generation agent reuses interaction structure to construct supported variations and revises incompatible configurations using validation feedback. A task-execution agent uses the same bindings and geometric records to select robot-supported skills and check completion against the original task criteria. On RoboCasa, the framework builds the AgenticTask collection, saving 16,450 task instances from 20,323 construction attempts at a throughput of 166.97 saved instances per elapsed hour, with 62.26% of construction attempts passing the configured physical checks. The execution agent completes approximately 38% of evaluated tasks, with successful cases spanning object placement, articulated manipulation, and sequential arrangement. Diagnostic analysis identifies improvement priorities in construction reliability, action selection, task-robot compatibility, and runtime integration. Together, these results demonstrate task-collection expansion with measured construction productivity and concrete execution evidence, providing a foundation for subsequent interaction-data collection for embodied AI.

- **研究背景：**单靠人工采集难以充分扩展交互数据；仿真虽有规模化潜力，但自动生成的任务可能与可用资产、模拟器接口或机器人能力不兼容。仅生成任务描述或代码，并不能保证任务能够实例化、执行和验证。

- **工作定位：**重点在于扩展和筛选仿真任务实例，并展示初步执行证据；并未直接证明这些任务能提升某个已训练策略的性能，也未完成真实机器人迁移验证。

## 2. 方法论

### 2.1 核心思想

AgenticTask 由两个协作但职责分离的智能体组成：

1. **任务生成智能体：**将人类意图转化为结构化要求，在模拟器支持的配置范围内生成任务变体；根据构建和检查反馈修正不兼容配置，同时保持任务核心要求不变。
2. **任务执行智能体：**使用任务实例中的对象与部件绑定、几何信息和机器人能力，选择并参数化机器人技能；执行后由独立检查器依据原任务目标和约束判断是否成功。

两者通过共享任务记录衔接，避免生成阶段、执行阶段对目标对象或成功标准的理解不一致。

### 2.2 分层任务表示

论文将任务分为三个相互关联的层次：

- **语义规格**：记为 \(I=(K,H,V)\)。其中，\(K\) 表示交互类别或任务族，\(H\) 表示必须保留的要求，\(V\) 表示允许变化的因素及范围。例如，“把杯子放进水槽”中，源—目标关系和放置目标应保留，而杯子实例和厨房布局可以变化。
- **绑定任务实例**：记为 \(\tau=(k,B,E,P_0,G,C,\ell)\)。它记录任务模板、任务角色到具体对象或部件的绑定 \(B\)、场景与机器人配置 \(E\)、初始条件 \(P_0\)、成功谓词 \(G\)、执行约束 \(C\) 和自然语言指令 \(\ell\)。
- **几何场景图**：记为 \(G_{\text{geo}}=(V_{\text{geo}},E_{\text{geo}},X)\)。节点表示对象、部件和交互区域；边记录部件归属、关节连接、支撑或包含等关系；属性保存位姿、尺寸、关节状态等几何与物理信息。目标关系与观测到的当前关系分开表示，以便根据实际状态检查任务完成情况。

### 2.3 任务生成与验证流程

- 根据人类意图、源任务、可用资产、环境和机器人配置，确定允许的任务配置空间 \(\Omega_I\)。
- 生成智能体从该空间选择候选配置，交由模拟器原生构造器实例化；由模拟器返回构建结果、实体绑定及错误诊断。
- 对候选任务执行预设检查，包括任务定义和角色绑定、资产与场景一致性、初始化几何和部分机器人兼容性检查。
- 检查状态分为通过、失败或未知。只有**所有预先指定的必需检查均通过**的任务才被接受；未知结果不会被当作通过。
- 若检查失败，智能体依据失败阶段、受影响实体和诊断证据，修改允许变化的配置，再重新构建和检查。修订不得放宽固定任务要求或机器人约束。
- 论文明确指出，物理检查的覆盖范围有限；例如，部分任务仅实现了任务包身份检查和基本对象—水槽绑定检查，机器人可行性探测仍不完整。因此，通过检查不等于已经证明任务一定可执行。

### 2.4 执行与成功判定流程

- 恢复任务保存的初始状态，按任务绑定定位对象、交互部件、目标区域及障碍物，并结合机器人状态和当前几何选择技能。
- 技能请求包含交互实体或接触部位、几何参数、执行前提条件以及局部完成条件。几何工具用于生成抓取和接近位姿；机器人适配器在动作下发前检查能力、前提和规划可行性。
- 执行过程中根据状态变化刷新几何信息，智能体可据反馈重新选择技能、重新规划或恢复执行。
- 局部技能完成不等于整项任务完成。独立检查器根据完整轨迹是否满足原任务的成功条件和执行约束判定整体成功；因此，执行失败本身也不能直接证明任务在物理上不可行。

- **充分性评价：**
  - 对“能否规模化构建任务、筛选部分候选、并执行部分实例”这一工程可行性问题，实验提供了有量化数据的初步证据。
  - 对方法相对优势、跨环境泛化或训练收益，证据不足。缺少与其他任务生成系统的全面对比，也缺少覆盖多个模拟器、机器人形态或真实环境的实验。
  - 论文未提供系统的消融实验，无法分别判断共享任务表示、验证机制、反馈修复或技能执行模块对总体表现的独立贡献。
  - 修复策略比较显示了产出与成本的权衡，但文中未充分展示该比较在不同任务类型、检查条件或随机种子下的稳定性。
  - 因此，结果更适合解释为**单一环境中的系统构建与诊断性评估**，而非广泛的基准性能结论。

## 6. 主要结论与发现

- AgenticTask 在 RoboCasa 上通过 20,323 次构建尝试保存了 **16,450 个任务实例**，每小时保存 **166.97 个**。
- 按论文报告的口径，**62.26% 的构建尝试通过配置的物理检查**。保存率与检查通过率并不相同：保存任务不代表一定通过物理检查，更不等于已经成功执行。
- 诊断引导修复将保存率从 **96.5% 提高至 97.2%**，但每个保存任务的时间从 **21.6 秒**升至 **23.3 秒**，报告的模型调用量从 **0.12**升至 **0.31**。
- 执行代理在评估任务中完成约 **38%**。成功轨迹表明，框架能够覆盖物体放置、关节式操作和多步顺序安排等交互类型。
- 失败诊断显示，动作规划、抓取选择、跟踪与恢复能力是重要障碍；另有任务与机器人兼容性以及接口、状态恢复等运行时问题。
- 对 400 个任务的独立检查还显示：原子任务较突出的问题是执行探测不足；复合任务则更多受到任务语义和动作结构适配不足的影响。

## 7. 优点

- **生成与执行使用共同表示**：将语义要求、实体绑定、几何状态和成功标准关联起来，降低任务变体中对象、指令和判定条件不一致的风险。
- **明确区分“允许变化”和“必须保留”**：修复候选时允许替换兼容对象或场景，但不应通过改变目标来换取检查通过，有助于保持任务语义。
- **将验证反馈纳入生成循环**：失败诊断可以指导有针对性的修订，而不是无条件重复采样；论文还量化了修复带来的产出和成本变化。
- **执行成功由独立检查器判定**：不仅依赖智能体自述或单个技能的局部完成条件，而是回到原任务目标及约束验证完整轨迹。
- **报告工程性指标与失败类型**：同时提供构建耗时、保存率、筛选率和执行诊断，使系统的可扩展性与薄弱环节比只展示成功案例更清楚。

## 8. 不足与局限

- **物理与机器人兼容性检查覆盖不完整**：论文承认机器人可行性探测仍是部分实现。检查通过只能说明配置满足已实现的检查项，不能保证无碰撞、可达或能成功操作。
- **执行成功率有限且归因不确定**：约 38% 的执行完成率说明当前执行能力仍有较大提升空间。失败可能来自任务配置、智能体规划、技能库、机器人能力或运行时接口，论文也指出其中一些原因难以明确区分。
- **环境与任务覆盖有限**：实验集中在 RoboCasa 和厨房场景，尚未证明可迁移至其他模拟器、不同机器人形态或真实世界。
- **缺少策略训练收益验证**：论文以合成数据采集和策略评估为应用动机，但没有证明使用这些任务训练后能提升学习策略的性能，也没有报告策略间的标准化比较。
- **比较与消融较少**：除重采样和诊断修复外，缺乏与代表性任务生成系统的直接对照，也未系统拆解各模块贡献，因而难以确定增益来自哪项设计。
- **人工与模型依赖仍存在**：任务定义、资产和部件标注、任务模板、机器人配置及预设检查都影响结果；框架扩展能力受这些资源覆盖和准确性约束。
- **复现信息不完整**：论文未明确提供 GPU、系统硬件、提示词与模型版本等完整细节；文末也说明研究模型的精确版本和提示词将随完整实验记录。因此，成本复现和结果复现仍有不确定性。
- **结果适用范围需要谨慎理解**：任务构建吞吐量衡量的是保存任务数，不等于物理可接受任务数或成功执行数；成功轨迹是示例，不能替代总体成功率统计。
