Abstract
Composing an editable 3D scene from images requires an
asset for each object and a layout that places the assets.
3D generation and CAD retrieval now supply the assets, but
layout still lacks a general solution: scene generation meth-
ods couple it with generation, and pose estimators handle
one object at a time and need true-size CAD models, depth,
or iterative refinement. We present X-3DComposer, a feed-
forward model that predicts the layout separately from asset
generation. Given one or more images of a scene, the ob-
ject masks, and an asset for each object from any source, it
jointly predicts the rotation, translation, and per-axis scale
of all objects in a single forward pass of about one sec-
ond. The key idea is to treat objects as views: renders of
the assets are processed together with the scene images by
a multi-view geometry model adapted from VGGT-Ω, and
each object pose follows in closed form from the cameras
predicted for its renders. Camera intrinsics, camera poses,
and depth are optional inputs. When the meshes produced
by five scene generation methods are kept fixed and only
their layout is replaced, the layouts of X-3DComposer are
more accurate than the native layouts of these methods.
Compared with the stand-alone layout model SceneMaker,
it reduces the scene-level Chamfer distance by 52% on In-
doorMix, our test set from six indoor datasets, and by 28%
on 3D-FUTURE.

CAD retrieval can provide exact or similar CAD models.
This paper studies the other half of the problem, scene
layout: given the assets, estimate the pose and scale of each
one so that the composed scene matches the images.
Existing methods fall into three groups (Fig. 1).
The first group consists of scene generation meth-
ods [5, 18, 27, 31, 50], which output a layout together with
the object geometry. This layout is a by-product of genera-
tion and cannot be applied to assets from other sources. The
second group takes a CAD model as given. Object pose
estimators [25, 49] handle one object at a time, assume a
true-size CAD model, often require depth, and refine each
pose by render-and-compare. CAD alignment methods [12]
also estimate scale, but they too treat each detected object
independently. The third group consists of stand-alone lay-
out models [28, 39, 56], which separate layout from gener-
ation but rely on iterative sampling, dense correspondences,
or per-scene optimization; most accept only a single image.
A general layout method should accept assets from any
source and place all objects jointly, in a single forward
pass, from one or more views. None of the methods above

meets all of these requirements. Multi-view geometry mod-
els [43, 44] already do this for cameras: they predict the
cameras of any number of views in a common frame at
once. We observe that layout can be cast as the same task
by treating objects as views. We render each asset from a
few viewpoints with known cameras in its own frame and
feed the renders to a multi-view geometry model together
with the scene images. The model predicts a camera for
every view in a common scene frame. Each render camera
is then known in the asset frame and predicted in the scene
frame, and the object pose follows from the two in closed
form. All objects are thus placed jointly, without sampling
or optimization, and since the model needs only renders of
an asset, it applies to any asset. Predicting a camera for each
view is also the pretraining task of these models, which lets
us start from the pretrained VGGT-Ω[44], keep its archi-
tecture, and add few parameters.
Whole scenes raise further difficulties. The model must
know which object each render belongs to, even when ob-
jects look identical, so each object is assigned an identity
embedding that links its masks, its crops from the scene im-
ages, and its renders. Generated or retrieved assets often
differ in proportions from the real objects, and we therefore
predict one scale per axis. The input also varies from one
image to several, with or without camera intrinsics, cam-
era poses, and depth. We treat these as optional geometric
conditions. Our contributions are as follows:
• We present X-3DComposer, a feed-forward model that
predicts the layout of all objects (rotation, translation, and
per-axis scale) in a single forward pass of about one sec-
ond, given any number of scene images and assets from
any source.
• We extend camera-based pose prediction [4, 37] from sin-
gle objects to whole scenes: the crops and renders of all
objects are fed as extra views to a multi-view geometry
model adapted from VGGT-Ω, with identity embeddings
and optional geometric conditions, and the object poses
are read out in closed form from the predicted cameras.
• With the meshes fixed and only the layout changed, our
layouts are more accurate than the native layouts of five
scene generation methods, and our scene-level Chamfer
distance is 52% lower than that of SceneMaker [39] on
our IndoorMix test set and 28% lower on 3D-FUTURE.
2. Related Work
Compositional 3D scene generation and reconstruction.
One line of work generates the geometry of several objects
together with their layout. MIDI [18] and SceneGen [31]
generate all objects of a scene jointly, while SAM 3D [5]
and its multi-view extension MV-SAM3D [27] generate a
mesh for each object and predict its rotation, translation,
and scale. FIRE3D [50] also outputs the objects together
with their layout. Such a layout applies only to the assets
generated with it. Our model does not depend on a partic-
ular generator. Another line of work first obtains the assets
and then solves for the layout.
CAST [54] places each
generated object in the scene point cloud with an alignment
model and refines the poses by optimization under physics
constraints.
Given a single image, SceneMaker [39]
samples the object poses iteratively from a pose model
conditioned on object geometry.
Mira-Scene [41] and
Easy-3Dfy [56] solve for the transformation from dense
correspondences between the object and an estimated point
cloud, and Lucida [36] adjusts the poses iteratively with a
vision-language model. SPOON [28] handles uncalibrated
multi-view input by guiding the pose sampling of SAM 3D
with a VGGT-Ωreconstruction, followed by per-scene op-
timization. Pano3DComposer [37] feeds object crops and
asset renders to VGGT and predicts a transformation with
per-axis scale for each object separately, from panoramic
input. These methods handle one object at a time or rely on
iterative procedures, whereas our model places all objects
in a single forward pass.
CAD alignment and object pose estimation.
Single-
image CAD alignment methods [11, 12, 24] retrieve a CAD
model for each detected object and align it to the image, and
recent methods [1, 7] solve for pose and scale from feature
correspondences between the image and the CAD model.
Methods for 6-DoF pose estimation of novel objects as-
sume a true-size CAD model. MegaPose [25] and Founda-
tionPose [49] use render-and-compare, GigaPose [33] uses
templates and feature correspondences, and AlignPose [32]
refines poses over multiple views. Closest to our approach
is PoseGAM [4]. Initialized from VGGT, it treats renders
of the CAD model as views with known cameras, regresses
the camera of the query image, and derives the 6-DoF ob-
ject pose from it. In contrast, we place all objects jointly
and predict per-axis scales, and thus need no true-size CAD
models.
Multi-view
geometry
models.
DUSt3R
[47]
and
MASt3R [26] regress point maps directly from image
pairs, and VGGT [43] predicts the cameras, depth, and
point maps of multiple images in a single forward pass.
Later models such as π3 [48], Depth Anything 3 [29], and
VGGT-Ω[44] follow the same paradigm.
Pow3R [19],
MapAnything [21], and OmniVGGT [34] additionally
accept camera intrinsics, camera poses, or depth as optional
inputs. These models reconstruct the scene as a whole and
have no notion of individual objects; we keep their task and
optional conditions and add objects as extra views.

3.2. Objects as Views
Background:
multi-view geometry models.
VGGT-
Ω[44], the successor to VGGT [43], predicts a camera and
a depth map for every input image in a single forward pass,
with all cameras expressed in the camera frame of the first
image. Each image is encoded into patch tokens by a DINO
encoder, and one camera token and several register tokens
are prepended. The tokens of all images pass through alter-
nating frame-attention and global-attention blocks. A cam-
era head then regresses the camera of each image from its
camera token, and a dense head predicts depth.
Representing objects as views.
We do not feed the as-
set geometry to the model. Instead, we render each asset
and treat the renders as extra views. The pretrained model
already takes images as input, so its ability to relate views
carries over to relating an asset to the scene, and no 3D en-
coder has to be trained from scratch.
Three types of views.
The model takes three types of
views as input (Fig. 2):
• Scene views: the S scene images.
• Object crops: c square regions around each object, cut
from the full-resolution scene images. Scene views are
downsampled before entering the model, and the crops
restore the detail that small objects lose.

3.3. Network
Backbone and trainable parameters.
We build on
VGGT-Ωand keep its architecture. The trainable parame-
ters (Fig. 2) are (i) the output branch of the camera head, (ii)
LoRA [17] on the query and value projections of the frame-
and global-attention blocks and of the attention blocks in the
camera head, and (iii) the condition encoders and identity
embeddings introduced below; all other weights are frozen.
The output layers of the new modules are zero-initialized,
so training starts from the output of the pretrained back-
bone. The camera head outputs a 9-dimensional camera en-
coding per view. We add three dimensions for the per-axis
log-scale ℓ, used only for the renders.
Identity embeddings.
Identical objects cannot be told
apart by appearance, so each crop and render must be tied
to its object explicitly. We keep a set of learnable identity
embeddings and assign one of them, ei, at random to each
object of a scene. An embedding thus only distinguishes
the objects within a scene and carries no other meaning. In
every view, the identity vector of patch u is the sum of the
embeddings of the objects whose masks overlap the patch,
weighted by the overlap:

Condition encoders.
For a view with intrinsics and a
camera pose, the camera parameters are encoded by an
MLP and added to the camera token, and the Pl¨ucker ray of
each pixel is embedded by a convolution and added to the
patch tokens. With intrinsics only, the rays are computed in
the view’s own camera frame. A depth map is embedded
by a second convolution and added to the patch tokens. The
render cameras Li,m are always known and are encoded in

Symmetry, grounding, and physics.
Objects that are
symmetric about the vertical axis, such as round tables and
vases, have several equally correct poses. We detect such
symmetries for each asset offline and train with the equiv-
alent label closest to the current prediction. A grounding
head, used only in training, takes the camera token of each
crop and render and predicts which scene-view patches its
object occupies. This encourages the model to link crops
and renders to their objects in the scene. We also apply
two physics constraints to the layout that is read out, pe-
nalizing penetration between objects and the offset of floor-
supported objects from the floor.
Training data and sampling.
Training requires scenes
with 9-DoF object annotations. We combine several sources
in a common format: synthetic indoor scenes [9, 10, 22,
23, 35, 51, 57], real scans from ScanNet++ [55] with anno-
tated CAD models [3, 38], and single-view images [10, 40].
We oversample scenes that contain several instances of the
same asset, so that the model must rely on the identity
embeddings to tell them apart. We also randomly replace
the asset of an object with an asset of similar shape from
the same category and adjust the labels accordingly, which
mimics assets that do not exactly match the object. Since
the geometric conditions are optional at inference, each
training sample is given a random subset of them. The num-
bers of scene views, objects, and renders per object are also
drawn at random, so one model covers all input settings.

4.2. Layout Prediction for Generated Assets
This experiment tests whether a stand-alone layout model
places a set of assets more accurately than the method that
generated them.
We use five scene generation methods:
MIDI [18], SceneGen [31], FIRE3D [50], SAM 3D [5], and
MV-SAM3D [27]. MIDI, SceneGen, and SAM 3D take a
single view, MV-SAM3D takes several views, and FIRE3D
supports both. Each method generates the meshes of all
objects in the scene views, together with its native layout.

4.5. Ablations and Analysis
Design choices.
All variants in Table 4 are trained on 3D-
FRONT with the same shortened schedule and evaluated
there with ground-truth intrinsics and depth. Trained from
random initialization, the model fails under this schedule
(single-view F-S 40.7 vs. 90.8). Without identity embed-
dings, and hence without the masks, F-S falls to 71.7: the
embeddings are needed to tie crops and renders to their ob-
jects in general, not only when objects look identical. The
object crops give a smaller but consistent gain (single-view
CD-S 9.49 vs. 11.88). The grounding head helps with multi-
view input (CD-S 3.92 vs. 4.94) and has a mixed effect
with single-view input. Without the physics constraints, the
scene metrics are slightly better, but the percentage of pen-
etrating objects rises from 7.9% to 10.1%.
Mismatched assets and identical objects.
Assets from
retrieval or generation rarely match the object exactly, and
a scene may contain identical objects. We test both cases in
Fig. 6. Re-texturing an asset barely changes the predicted
pose (a), and replacing it with another asset of the same cat-
egory makes the model adapt the pose to the new shape (b).
For two identical objects, swapping their identity embed-
dings swaps the two assets (c), which shows that the model
follows the identity embeddings.
Views, renders, and runtime.
More scene views im-
prove accuracy at little extra cost.
From one to eight
views, the time per scene grows by less than 0.2 s. More
renders per object raise F-S and IoU-B slightly (see the
supplementary material). In Table 5, our model takes about
1 s per scene, and the three baselines take 5.8–7.5 s.
5. Conclusion
We presented X-3DComposer, a feed-forward model that
composes a 3D scene from given assets by predicting their
layout. Its key idea is to treat objects as views: with asset
renders as extra views, layout becomes camera prediction,
a task that pretrained multi-view geometry models already
solve well. Our experiments show that layout need not be
8


tied to asset generation. On the same meshes, our layouts
are more accurate than the native layouts of five scene
generation methods. Without depth input, our scene-level
Chamfer distance is 52% lower than that of SceneMaker
on IndoorMix and 28% lower on 3D-FUTURE. As the
model needs only asset renders, it can be combined
with any generator or retrieval system.
Our model has
limitations. It requires object masks as input and is trained
and tested only on indoor scenes.
It is also sensitive to
inaccurate geometric conditions, and its physics con-
straints reduce penetration without guaranteeing physically
plausible layouts. Predicting the masks within the model
and extending it to other scene types are left for future work.

A. Implementation Details
Backbone.
The backbone is the 1B-parameter VGGT-Ω
model. It has a token width of 1024 and alternates 24 frame-
attention blocks with 24 global-attention blocks; five of the
global-attention blocks attend only to the camera and reg-
ister tokens. As in the original model, the resolution of a
scene view depends on its aspect ratio, and every scene view
has about 4162 pixels (for example, 416×416 or 304×560).
For frame attention, views are batched by resolution.
New modules.
The ray encoder is a convolution of stride
16 on the 6-channel Pl¨ucker rays, followed by a linear layer
that maps to the token width. For a view with intrinsics
but no camera pose, two learnable “camera pose unknown”
vectors are added, one to its camera token and the other
to each of its patch tokens. The depth encoder is a second
convolution of stride 16, applied to the logarithm of the nor-
malized depth and a validity mask. The camera encoder is
an MLP that maps the field of view and the world-to-camera
rotation (as a quaternion) and translation to the token width.
There are 64 identity embeddings of dimension 64, so one
forward pass handles at most 64 objects. In addition to the
patch-wise identity vectors of Eq. (5), the camera token of
each crop and render receives the embedding of its object.
The output layers of the ray and camera encoders, the two
“camera pose unknown” vectors, the linear projections of
the identity vectors, and the three log-scale outputs added
to the camera head are zero-initialized. The convolution of
the depth encoder has no bias and starts from small ran-
dom weights; it adds nothing to the tokens of views without
depth input.

Training samples.
We describe the sampling of the final
model (Sec. E); the differences for the main-paper model
are given at the end. Each sample is given intrinsics with
probability 0.8. When intrinsics are given, camera poses
and depth are each given independently with probability
0.5, so each of the five combinations of conditions has prob-
ability 0.2. At each step, we draw the number of scene
views S (1 to 10) and of objects N (1 to 12) from a fixed
set of combinations, and the number of renders per object
M from {1, 2, 3, 4, 6, 8}. Each object gets one crop from
each scene view in which the long side of its input mask is
at least 64 pixels; if there are more than three such views,
the three with the longest sides are kept. A crop whose box
side is at least 336 pixels is used at 336 × 336, the others at
256×256; the renders of an object with a 336-pixel crop are
also 336 pixels, and the other renders are 256 pixels. The
batch size is set by a budget of about 56k tokens per GPU,
and all samples of one step have the same number of views
at each resolution. In the multi-view sources, any two scene
views a and b of a sample satisfy

Renders are composited onto a uniform gray background,

or two 256-pixel crops per object (one at inference), one to
five renders, and about 28k tokens per GPU and step.
Optimization.
We use AdamW (β1 = 0.9, β2 = 0.95,
weight decay 0.05) with gradient clipping at a norm of 1.
The peak learning rate is 2.5 × 10−5 for the new modules
and 5×10−6 for the LoRA weights (rank 32) and the output
branch of the camera head. The learning rate is warmed up
linearly for 500 steps and then decays with a cosine sched-
ule to 1% of its peak. Training uses 8 GPUs and runs for
about 200k steps.
B. Training Data
All data are converted to one format. Each scene stores the
images, object masks, and cameras of its views and, where
available, their depth, and each asset is rendered in ad-
vance from 32 viewpoints in its asset frame. We render the
3D-FRONT rooms with Blender from several viewpoints
along a walkable trajectory in each room and take the la-
bels from the layout files. The other synthetic scenes come
from HSSD, InternScenes, MolmoSpaces, SAGE, and Sce-
neSmith; we convert their labels from the object transforma-
tions that each source provides. For ScanNet++, we use the
DSLR images together with the ShapeNet [3] CAD mod-
els and the pose annotations of SCANnotate++ [38]. These
CAD models differ in proportions from the real objects, and
we take the per-axis scale of each object from the annota-
tions. The single-view images are real photos from Pix3D
and rendered scenes from 3D-FUTURE. For the asset re-
placement of Sec. 3.4, the substitute is the asset of the same
category with the most similar shape; during training, an
object that has a substitute is replaced by it with probability
0.5. Table 6 lists the sources.

C. Evaluation Details
Test data.
IndoorMix consists of 400 single-view scenes
and 224 multi-view scenes with 2, 4, 8, or 12 views. On
the scenes evaluated in Table 1, the single-view scenes of
IndoorMix have 4.5 target objects on average and the multi-
view scenes 4.8, with at most 8 in both; the scenes of 3D-
FUTURE have 3.6. About 12% of the IndoorMix scenes are
real scans from ScanNet++, and a further 11% of the single-
view and 20% of the multi-view scenes come from the
part of InternScenes that is reconstructed from real scans.
The MolmoSpaces scenes come from its ProcTHOR part.
Multi-view scenes must have co-visible views: we connect
two views if at least 1% of the ground-truth depth points of
one are visible and unoccluded in the other, or if both show
the same target object with at least 100 pixels each, and we
keep a scene only if its view graph is connected, which re-
moves 10 of 234 candidate scenes. This rule only selects
test scenes and does not change the input of any method.
Each comparison is computed on the scenes for which every
compared method returns the poses of all objects; Table 7
gives the number of scenes per dataset.
Overlap with training data.
The IndoorMix scenes are
held out from training, but all six datasets are among our
training sources, whereas most baselines were trained on
at most one of them. MIDI and SceneMaker were trained
on 3D-FRONT, so some of our 3D-FRONT test rooms may
be in their training sets. The training data of FIRE3D in-
clude SAGE, InternScenes, and SceneSmith scenes and 3D-
FUTURE assets and therefore also overlap with our test
datasets. The 3D-FUTURE test set uses the same CAD
models as 3D-FRONT, and some of them also appear in
the 3D-FUTURE training images, on which both SceneGen
and our model are trained.

Panoramic input.
The test data are 42 houses of 3D-
FRONT: the 12 houses of the Pano3DComposer test split
that are not in our training data, and 30 further held-out
houses that are in neither the training nor the test split of
Pano3DComposer. With one panorama, each capture po-
sition is a sample; with two panoramas, a sample consists
of two capture positions in the same room. The six per-
spective views of a panorama share its center; they are 60◦
apart in yaw, are pitched 15◦downward, and have a field
of view of 72◦. Their intrinsics and relative camera poses
follow exactly from this arrangement; since the views share
one camera center, these poses fix no unit of length. The
relative camera pose between two panoramas is unknown,
and our model accepts camera poses only for all views or
for none, so for two panoramas we report only the settings
without conditions and with intrinsics. Two panoramas give
12 scene views, more than the maximum of 10 used in train-
ing. Among the six views of the first panorama, the one
in which the most objects are visible is used as the first
scene view; this choice depends only on the input masks.
Pano3DComposer estimates depth and the relative camera
poses of the panoramas with its built-in Depth Anything 3.

E. Extension to Generic Objects
The main-paper model is trained and tested on indoor
scenes, where most assets are furniture. To test whether
the approach carries over to other kinds of objects, we con-
tinue training the main-paper model with generic-object
data added to the training set: the physically based ren-
dered (PBR) training images of BOP [16] (T-LESS [15],
HomebrewedDB [20], HOPE [42], HANDAL [13], YCB-
V [53], and LINEMOD [14]), tabletop scenes that we gen-
erate by physics simulation with objects from GSO [6] and
ShapeNet [3], and real images from GraspNet-1Billion [8]
and YCB-V. In the last part of this training, these data make
up 19% of the training samples (11.5% BOP renderings,
6.0% tabletop scenes, and 1.5% real images). The archi-
tecture and the training objective are unchanged, and the
samples are drawn as described in Sec. A. We call the result
the final model; it is used only in this section. As in the
main paper, the inputs include ground-truth object masks.
Comparison on real photos.
Figure 10 compares the fi-
nal model with FoundationPose [49] and PoseGAM [4] on
real photos from the HOPE validation set. The photos are
not in the training set, but their objects were seen in training.
Each photo contains 12 to 21 objects, whereas a training
sample contains at most 12. All three methods are given the
same inputs (listed in the caption); as in Table 2, our model
uses the given sizes in place of its predicted scales, and the
rotations and translations are its own predictions. On the
photos shown, our results are visually similar to those of
FoundationPose, which renders and refines each object iter-
atively, whereas PoseGAM, which uses no depth, errs more
along the viewing direction. Unlike FoundationPose, our
model uses no test-time optimization, and unlike both meth-
ods, it gives the poses of all objects in one forward pass.
F. Limitations and Failure Cases
All our experiments use ground-truth object masks; the ef-
fect of predicted masks remains untested. The main-paper
model is trained and tested only on indoor scenes; generic
objects are covered in Sec. E.
Orientation of cameras and objects. The cameras of the
indoor training data are never rolled far about the optical
axis. In our tests, rolling the camera by 180◦lowers the
accuracy sharply, and objects lying on their side or upside
down are placed less accurately.
Reference frame. As in the backbone, all outputs are ex-
pressed in the camera frame of the first scene view, so the
result depends on which view comes first. In Fig. 11(a), the
six views come from one panorama: they share one camera
center, differ by large rotations, and no object is visible in
the first view; the predicted object rotations have large er-
rors. This is why the first view of the panorama experiments
is chosen from the input masks (Sec. C).
Geometric conditions. The model is sensitive to inac-
curate geometric conditions (Table 2). In Fig. 11(b), the
intrinsics estimated by MoGe-2 are inaccurate, and distant
objects float above the floor.
Small objects. A scene view has about 4162 pixels, so
small distant objects cover few pixels; the crops compensate
only in part.
Physical plausibility.
The physics constraints reduce
penetration between objects but do not guarantee physically
plausible layouts.
