# CRAFT: A Robot-Agent Harness with Scope-Aware Adaptation 

Peng Zhang, Jiawen Wang, Cheng Xue and Jochen Renz Australian National University 

{peng.zhang, jiawen.wang, cheng.xue, jochen.renz}@anu.edu.au 

Abstract 

A robot may know how to move an object yet still need to learn where it belongs. When a person rejects a placement, the robot must decide whether the correction applies only to that situation or expresses a broader rule. We study this problem in CRAFT (Contextual Requirement Adaptation with Frozen Tools), a framework for learning local requirements without retraining robot skills. It records physical success separately from whether an action meets the requirement. Our scope ladder uses memory when an action has already been judged in a nearly identical situation. Elsewhere, it combines memory, explicit rules and a learner for requirements beyond those rules, weighting their predictions by how well they predicted earlier feedback. Controlled studies show gains over correction memory alone in utility, which rewards acceptable actions and charges for mistakes and questions. In camera-grounded robot simulations, the ladder asks fewer questions than language-model agents with persistent memory, but some of those agents take fewer wrong actions and succeed more often after requirements change. All execution failures and timeouts remain in the evaluation. These results support combining specific memories with broader rules, while leaving reliable adaptation to changing requirements unresolved. All evidence comes from simulation with generated requirements and simulated feedback. 

# 1 Introduction 

Consider a robot bringing a glass of water to someone working at a table. It sets the glass beside a laptop, near the table’s edge. The person says, “Not there.” Should drinks be kept away from the laptop, or away from the edge? Both rules explain the objection. Once the laptop is moved to the centre of the table, they disagree about whether the original spot is acceptable (Figure 1). We call this the correction’s reach : the situations to which it should apply. A correction interpreted too narrowly allows the same mistake in a new scene; one interpreted too broadly rules out acceptable actions. This problem arises when a robot has usable physical skills but must learn unstated requirements at the site where it operates. Skill libraries and robot-agent harnesses make it possible to reuse existing controllers [Hu et al., 2026]. Memory and rules offer different ways to use that feedback. Memory can recall what happened in a similar situation. A rule can extend the lesson to unfamiliar objects or layouts. Each has a weakness: similar-looking scenes may require different actions, and a rule may be inferred too broadly or applied incorrectly because perception is noisy. We study this choice in CRAFT (Contextual Requirement Adaptation with Frozen Tools). CRAFT is a robot-agent framework that keeps physical skills fixed while allowing the method that learns local requirements to change. It separates whether a motion succeeded from whether the chosen action was acceptable. Compared methods receive the same kinds of observations, feedback and opportunities to ask questions; each learns only from the outcomes of its own actions. Within CRAFT, we propose the scope ladder . If an action has already received feedback in a nearly identical situation, memory decides. Otherwise, the ladder combines predictions from memory, an explicit set of possible rules, and an additional learner for requirements those rules cannot express. Each predictor is weighted by how well its past predictions matched the feedback that followed. This gives specific experience priority where it applies and allows broader rules to guide decisions elsewhere. The arbitration rule combines established memory, rule-learning and weighting techniques. Existing systems already learn reusable preferences from corrections or maintain revisable user and scene memories [Zha et al., 2024, Wang et al., 2026b]. Our focus is the choice between specific memories and broader predictions when feedback consists of sparse yes/no verdicts. We evaluate the method in controlled studies and in a continuing service that carries experience across robot jobs.

Harnesses around frozen policies. Persistent memory and revision around frozen robot policies are established directions. CarryOn [Wang et al., 2026b] is particularly close at the system level: it combines revisable user and scene memories with a frozen VLA, proactive shielding, recovery skills and reflection. Lasting preferences are extracted from dialogue; explicit revisions replace or remove profile entries, and observations trigger scene-memory updates. CRAFT builds on this use of persistent, revisable memory. We ask how sparse action verdicts should generalise when they leave the intended requirement and its scope unstated. Our paired comparison evaluates the ladder against an adaptation that retains CarryOn’s native memory stores, write/delete operations and context policies under our shared verdict-feedback interface (Section J); it does not evaluate CarryOn’s shielding and recovery. Harness VLA [Zhang et al., 2026] turns a frozen VLA into a retryable contact-rich primitive alongside analytic primitives, and keeps task-specific traces and global success rules and failure models extracted from its own exploration. The RoboHarness of Li et al. [2026] retrieves success and failure precedents by CLIP similarity for a VLM orchestrator that diagnoses failures and selects interventions. A distinct RoboHarness, by Huang et al. [2026], orchestrates heterogeneous policies using capability descriptions and execution memory; its Memory Bridge addresses incompatible states at policy handoffs without joint retraining. RoboArchitect [Wu et al., 2026] has a coding model revise the harness around a frozen policy from rollout traces, retaining lessons for later executions. These works address overlapping deployment problems through different feedback and control interfaces. CRAFT uses these established components through contracts that let adaptation methods be swapped under equal information, with execution and acceptability reported separately. HALO [Hu et al., 2026] illustrates the skill layer such a harness can use. It learns whole-body humanoid skills (walking to named objects, sitting, crawling, pushing boxes) solely from data synthesised in procedurally generated homes, then transfers them zero-shot to unseen rooms. Its VLM orchestrator chains skills from a spoken request, retries failed steps and may ask the operator. The reviewed version plans from the current instruction and camera frame, describes its orchestration as relatively simple, and reports no memory of a person’s statements across requests. HALO provides the kind of frozen skills CRAFT assumes; learning a correction’s reach is a separate problem. 

Learning preferences and rules from few examples. TidyBot [Wu et al., 2023] summarises a person’s example placements into general rules with an LLM and applies them to unseen objects. SYNAPSE [Modak et al., 2025] synthesises preferences as programs in a neuro-symbolic language over images, from demonstrations paired with explanations, and generalises well out of distribution; it does not handle preferences that change over time. Hypothesis Search [Wang et al., 2024b] has an LLM propose natural-language hypotheses, implement them as Python and keep those that reproduce the given examples; hypothesis refinement [Qiu et al., 2024] finds LMs better at proposing rules than at applying them. NeatNet [Kapelyukh and Johns, 2021] learns a latent preference vector from many users’ arrangements. These methods learn from demonstrations or example sets; our setting supplies online yes/no verdicts for physically completed actions, with budgeted full-menu labels during commissioning and optional queries. Our rule level follows Bayesian concept learning over a grammar [Goodman et al., 2008]. Comparators include an LLM rule writer inspired by Hypothesis Search (an 8B model and, on six streams, a frontier model), a VLM in-context learner and Popper [Cropper and Morel, 2021]. A separate integrated pilot compares against a frontier agent combining retrieved instances, editable rules and its own execution history (Section 6.5). 3How far a correction reaches. DROC [Zha et al., 2024] is a close correction-learning comparator: an LLM distils language corrections into plan- and skill-level knowledge. Its plan-level implementation retrieves relevant constraints semantically; task-category and visual retrieval also support object grounding and skill reuse. It explicitly studies generalisation of preferences and constraints, which overlaps with CRAFT’s learning objective. CRAFT tests prequential arbitration between predictors under sparse verdict feedback. DROC’s described modules do not use that arbitration rule. ExpeL [Zhao et al., 2024] likewise uses both its extracted insights and its recalled trajectories, in text domains. Recurrent Summary Memory (RSM) [Wang et al., 2026a] compresses interaction history into a fixed-size recurrent summary for in-context reinforcement learning; CRAFT studies when feedback from past actions should apply to new situations. Lee et al. [2026] address reach directly: a language model edits a robot’s task features after each language correction, with an explicit operation that generalises a specific feature to the correction’s intent. In their work an LM decides how far a correction reaches; in ours each level’s weight depends on how well it predicted earlier verdicts [Freund et al., 1997, Herbster and Warmuth, 1998], and we measure prospectively when each level should decide. Earlier, Bajcsy et al. [2018] inferred which feature a physical correction targets and Bobu et al. [2018] acted conservatively when the hypothesis space could not explain a correction; our open level plays that role for rules outside the grammar. 

Asking for help. Uncertainty-triggered queries are standard in active learning [Settles, 2009] and in planners that ask when unsure [Ren et al., 2023]. APRICOT [Wang et al., 2024a] keeps LLM-proposed candidate preferences from demonstrations, updates a Bayesian belief from yes/no answers and chooses questions by information gain. We use an uncertainty band for asking. We did not compare it with APRICOT; a tested scope-aware question selector did not improve performance (Section F). 

Safety constraints from feedback. A VLM can turn language feedback and images into constraints for an online reachability filter [Santos et al., 2025]; sparse “unsafe” flags can define a nearest-neighbour region of likely failures via conformal prediction [Feldman et al., 2025]; and an LLM can ground fixed safety rules into temporal-logic specifications that guard a plan [Ravichandran et al., 2026]. We tested the reach question under asymmetric harm once; that study failed its validity check (Section F), and we make no safety claim. 

Open-world adaptation and evaluation. NovPhy [Pinto et al., 2024] evaluates how agents detect and adapt to novel physical conditions. Pinto et al. [2022] argue that open-world evaluation should measure both the timeliness of novelty detection and the quality of adaptation. CRAFT examines how sparse verdict feedback helps identify acceptable actions as requirements change around fixed robot skills. NAPPING [Xue et al., 2023] adapts a trained reinforcement-learning policy only where it stops working, by learning adaptation principles for those regions; the harness’s correction memory (NAPPING-mem) and its staleness rule are derived from it. Freezing an analysis plan before data exist [Nosek et al., 2018] is uncommon in robot learning. We adopt it for every confirmatory study and report all outcomes. 

# 3 Problem and setting 

3.1 Learning a correction’s reach 

Returning to the household example in Figure 1, suppose the robot can place a glass of water beside a laptop near the table’s edge, or in a clear space in the middle. The household’s rule is to keep 4drinks away from the laptop, but this rule has not been stated to the robot. It places the glass beside the laptop, and the person says, “Not there.” The placement succeeds physically but violates the requirement. The robot receives no explanation and no verdict about the unchosen location. Both “keep drinks away from the laptop” and “keep drinks away from the table’s edge” fit this feedback. On the next delivery, the laptop has moved to the middle of the table. The original spot is now away from the laptop but still near the edge. Under the first explanation, that spot is acceptable; under the second, it remains unacceptable. The household rule has not changed, only the layout. The robot must decide whether the earlier rejection still applies. This is the question of a correction’s 

reach .Each delivery is a job, the observed table arrangement is its context, and the candidate placements form the action menu. We formalise these repeated decisions as follows. A stream is a sequence of T jobs at one site. At job t the robot observes a context xt (an RGB-D image of the scene) and a menu At of admissible actions. The actions differ in one role : which object to move, or which target to put it on. Actions are drawn from the declared skill menu, but execution can fail; the requirement determines whether an action is acceptable under a site requirement that nobody stated. A hidden rule r maps each context to its acceptable set r(xt) ⊆ A t, which may be empty. On each job the provider either executes one action at ∈ A t or holds off. Under the feedback level used throughout (F1), this defines a contextual partial-monitoring problem: the provider observes the bandit label yt = [ at ∈ r(xt)] only for the single action it executed, while holding off and failed executions return no verdict, and nothing is revealed about unexecuted actions a̸ = at.In the decision-level studies, T = 40: the first four jobs supply full-menu commissioning labels and the remaining 36 are scored with net utility

Every learner fixes a reach implicitly. Nearest-neighbour memory extends a verdict to a local ball around ( xt, a t) in visual feature space; a rule learner extends it across every pair ( xt′ , a ) that shares the predicates of its surviving hypotheses. Because perceptual facts are noisy and rules may fall outside any fixed grammar, no single reach dominates across a stream. The problem is to arbitrate online, from sparse bandit verdicts, which reach to trust for each candidate action. The decision-level providers use frozen features and perceived facts derived from RGB-D, public menu names, an object catalogue and a declared grammar. 3.2 The CRAFT harness 

CRAFT runs repeated, authorised jobs at one site with independently developed skills. It verifies progress, retains experience and permits bounded adaptation, without making any memory or learning algorithm a runtime dependency. Each component has a defined authority (Figure 2). A deployment service admits jobs, and a task runner owns each job’s goals, verified progress and budgets. Planner and adaptation providers propose actions; a supervisor controls dispatch, physical custody, deadlines and cancellation. Independent verifiers supply the evidence for progress. Declared site rules live in a rule store and bind every provider equally: a learned proposal cannot relax a declared constraint, and a physical success cannot remove a prohibition. 

Contracts that make providers comparable. In the architecture, a provider receives a 

DecisionContext (fresh public evidence, site cues, goals, declared constraints, the qualified actions and its own factual history), returns a DecisionProposal (execute, observe, wait, ask for help or finish, with a reason and the cost it charges), and later receives a FeedbackRecord in which the 

execution effect , the acceptability of the action and the whole-task verdict are separate fields, each TRUE, FALSE or UNKNOWN. A single failure bit would not tell a learner whether the motor, the destination or the remembered rule was wrong; keeping them apart lets a requirement learner ignore execution failures instead of learning false rules from them. The feedback contract fixes what a provider may learn, here the F1 level above. Asking a person is a separate, charged channel. 6Information boundary. For the selector providers in the initial repeated-context, new-context and component studies, three tests ran before any test output: a canary test (private fields replaced by sentinel values must leave every decision bit-identical), a static import check (provider modules cannot import the label generator, rule evaluator or bank loader) and a prefix-invariance test (decisions up to job t must not change when everything after t is randomised). Later providers had study-specific checks; we found no evidence of label leakage, but coverage is not uniform (Section A). 

What is implemented. The supervisor, skill registry, native backends, task runner and deploy-ment service exist as bounded prototypes. The main confirmatory studies use a decision-level driver. The initial closed-loop demonstration launched a fresh simulator for each job. The continuing-service pilot uses the same task runner, supervisor and deployment service for both providers, retaining native state throughout each stream. Section A gives the details. 

# 4 The scope ladder 

For every menu action a, each of three predictors estimates the probability pc(a | xt) that a is acceptable. The ladder determines how to combine these predictions. 

4.1 Perception and three predictors 

Perceived facts. A probe trained on separate scenes reads, for each catalogue object, whether it is present, its colour and its tabletop position from a frozen vision backbone [Shukor et al., 2025]; kind and movability come from fixed name tables. We write ft for the resulting fact vector and 

zt for the pooled, normalised visual/depth features using the same backbone. The integrated R1 pilot replaces this probe with a shared segmentation/depth frontend and its own disjoint feature normalisation; the learner equations are unchanged (Section G). 

Rule level G. A hand-written grammar H enumerates rules over perceived facts in five families: attribute (colour or kind), spatial (nearest, farthest, leftmost, rightmost), occupancy (no movable object within radius ρ of the target), presence (one rule if a cue object is present, another otherwise) and composite (a primary rule with a distance threshold and a spatial fallback), about 1,800 rules per site. When new and repeated situations are interleaved, evidence from new contexts can give rule inference enough weight to overrule memory on an exact repeat, even when the probe facts ft are wrong. Decision and asking. Every provider shares one decision layer: take a⋆ = arg max a p(a | xt), and hold off if p(a⋆ | xt) < 0.5. A provider with the right to ask uses an uncertainty band [Settles, 2009, Ren et al., 2023]: ask if 0 .25 < p (a⋆ | xt) < 0.75 and a question is left. The same channel, budget, cost and rule apply to every arm that may ask. Algorithm 1 summarises one job (a diagram is in Section E, Figure 6). 

4.4 Staleness rule 

The harness’s correction memory, derived from NAPPING [Xue et al., 2023], has a staleness rule: when an unacceptable verdict arrives for action a, it removes earlier acceptable records of a with the same perceived-fact key. Added to the ladder’s memory, it targets the case where a remembered “yes” was recorded under a rule that has since changed; it did not fire in the evaluated fixed-rule patterns A and O. It is a separate variant, tested in the staleness study without asking.

Decision-level sites and scenes. Each site is a rendered tabletop scene composition [Liu et al., 2023] with 50–75 contexts. Rules and acceptable sets come from a generator over the grammar’s five families. On test sites the perception probe reads presence with about 97% accuracy, colour with about 99% (70% on assets whose colour was swapped) and position with a median error of about 4 cm. 

Regimes and patterns. In regime N every job shows a new context; in regime R, 20 contexts are drawn 40 times, so about 62% of jobs repeat a context. Pattern A (primary) is a fixed rule from one of the generator’s families; C is as A, but the rule changes without announcement to another rule of the same family at job 20; E is as A with 20% execution failures, which return no feedback; and O is a fixed rule from separately written forms that the full grammar cannot express on true facts (out of grammar). In A, C and E the family that generated the stream’s rule is removed from the provider’s grammar, including every rule that nests it, so the provider never holds the true rule; in O it has the full grammar. 

Arms. kNN-mem : kNN correction memory on the same frozen features, with k and recency weighting chosen on development sites per regime; it is the standard site-scoped retrieval baseline that any method must beat. NAPPING-mem : the harness’s NAPPING-derived correction memory; its distance threshold was computed from the test sites’ perceived facts before the streams ran (no labels), a transductive exception that favours this baseline. Pre-registration. A confirmatory study tests a pre-specified claim. An author approves its protocol, code and analysis plan before they are frozen and hashed (SHA-256), before any outcome data exist. Each online confirmatory study used 150 fresh sites built after the freeze with a new seed, excluding near-duplicates of earlier sites, and evaluated once. Success or failure is determined by conditions set in advance; deviations are logged before outputs are read, and a failed study is never reclassified as successful. A development study uses sites already used in development (100 in most, 30 in the later model comparisons); it has a written plan with interpretation criteria, but supports no confirmatory claim. A study whose pre-set validity check fails is reported as “not a result”. Section D summarises the evidence; the complete study ledger is retained in the project archive. 

Decision-level statistics. The unit is the site. We report the mean over sites of per-stream net utility over the 36 scored jobs, and 95% bootstrap confidence intervals over sites with 2,000 resamples [Efron and Tibshirani, 1993]. Contrasts are paired by site. Non-inferiority margins were set in each protocol. 

Where the studies run. Confirmatory and development studies run providers in a study driver at the decision level: perception runs on rendered scenes, but actions are not executed physically, and feedback comes from the generator. The initial closed-loop demonstration and the continuing-service comparisons execute native simulated actions. Their populations and outcomes are reported separately; the pilot is not another replication of the 150-site studies. 

Continuing-service frontier comparison. Six paired streams each contain four commissioning and 20 scored jobs per method: 288 assignments, 120 scored per method. A fixed-pelvis R1 pushes one of three or four visible items from a six-object catalogue. Layouts, object subsets and a white cue vary; three streams keep their requirement and three change it without announcement. Each method retains its robot, service and learner state within a stream; external object setup is logged every job. The unchanged deployment service, task runner, supervisor, camera frontend and frozen push skill serve both providers. A prospective skill screen passed 14/16 with both failures retained. The comparator is gpt-6.1-sol at medium reasoning with retrieved examples, editable rule notes and its own event ledger. It uses the same public fact representation and inquiry rule as the ladder, with 20 scored calls per stream and a 60-second call deadline. Both receive four full-menu commissioning queries and at most three optional queries per stream. Ordinary F1 labels follow only physically completed actions. One physical attempt is allowed per job. All failures and timeouts remain in the assigned-job denominator. Source, controller, model, normalisation, assignments and protocol were frozen before evaluation. Section G gives the full protocol and accounting. The primary pilot endpoint is accepted task completion: independently verified physical effect, acceptable chosen action and service-verified original goal. Wrong dispatches, completed wrong actions, execution failures, queries and setup costs are separate endpoints. A wrong dispatch may also fail physically. The six purposively specified stream pairs provide descriptive evidence of integrated performance. They do not support a powered superiority or non-inferiority claim, and jobs within a stream are not independent replicates. 10 DROC adaptation follow-up. We additionally evaluate a DROC plan-level adaptation to verdict feedback [Zha et al., 2024], retaining the ladder and custom frontier controls from the first pilot. Its knowledge module distils its own feedback into an append-only constraint bank and selects relevant entries; a separate planning call sees only those entries and the current scene. The same service and six nominal streams are reused, with a new persistent robot/learner per stream. The assignments and historical controls were already exposed, so this is a descriptive follow-up, not a fresh confirmatory comparison. Both model stages share the first pilot’s 60-second decision deadline; interaction and physical budgets are unchanged. Binary verdicts replace language corrections, and a fixed push replaces multi-step planning and skill-code generation. Low-level visual retrieval is not exercised. This tests an explicit adaptation of the published plan-level mechanism, not a full DROC reproduction; Section I details the deviations and accounting. 

Fresh paired CarryOn comparison. A second prospective pilot compares the unchanged ladder with a CarryOn planning-loop adaptation on six fresh scene stream pairs, again with 120 scored jobs per method. It imports CarryOn’s native user/scene memory stores, write/delete operations, context policies and scene-update validator. Sparse verdicts and camera facts replace its native dialogue/image interface; shielding and recovery are outside the common one-push contract. The scene assignments are new, while the six requirement cases are inherited from the frontier comparison. Pair order alternates, and both methods run anew with independent persistent services and identical interaction budgets. Model validity checks and the source freeze precede evaluation. A 60-second whole-decision deadline covers planning and any plan repairs; all failures are retained under the prospective protocol. Section J specifies the retained native components, interface changes and resource limits. 

# 6 Results 

6.1 RQ1: the ladder against correction memory 

The main confirmatory study tested the ladder on 150 fresh sites with four pre-registered conditions, all of which were met (Table 1). Without asking, the ladder beat kNN memory on new contexts by +0 .074 [+0 .042 , +0 .108] (bar ≥ +0 .03, CI > 0), on repeated contexts by +0 .052 [+0 .027 , +0 .079] (non-inferiority margin −0.03; the CI is also above zero), and was not worse out of grammar (+0 .022 [+0 .002 , +0 .044]; margin −0.05). With the same right to ask, it led on new contexts by +0 .051 [+0 .023 , +0 .083], and on repeated contexts by +0 .031 [+0 .007 , +0 .056] (secondary), while asking fewer questions. With matched asking, Ladder+ask took 14% fewer wrong actions than kNN-mem+ask on new contexts and 27% fewer on repeated ones. On repeated contexts both completed the same number of acceptable actions (27.1 of 36): there the gain comes from fewer wrong actions and fewer questions, not from more completions. A pre-registered secondary analysis found a smaller benefit from asking for the ladder than for kNN memory: the gain from asking under the ladder minus the gain under kNN memory is −0.022 on new and −0.021 on repeated contexts, both with CIs just below zero. Asking therefore does not explain the ladder’s lead.

6.4 RQ4: rule changes 

After an unannounced rule change with repeated contexts, the ladder trusts memories recorded under the old rule: without asking, its post-change utility in the main confirmatory study was below kNN memory’s (0.298 vs 0.317); with asking the difference was +0 .001 [ −0.038 , +0 .039], inconclusive. On new contexts, where nothing stale is reused, Ladder+ask led kNN-mem+ask after the change by +0 .167 [+0 .098 , +0 .234] (70 sites). The staleness study tested the staleness rule on the ladder’s memory. It improved post-change utility with repeats by +0 .027 [+0 .015 , +0 .040] (68 sites with a rule change) and changed nothing when the rule was fixed (exactly 0 .000 in patterns A and O: the rule never fired). The pre-registered criterion required a positive CI without a minimum practical effect. The improvement closes about 5% of the post-change gap to the oracle (0.351 to 0.378, oracle 0.883).

# 7 Discussion 

7.1 What did not work 

The negative results help explain the ladder’s design (Section F). Structured rule prior: learned scope embeddings failed to beat simple baselines in two pre-registered studies, motivating an explicit hypothesis space over perceived facts that subsequently met its offline evaluation criteria. 

Specialist memory gate: rule inference without memory lost to kNN memory on streams with repeats (−0.031 on the pooled primary endpoint, failing the pre-set criteria) and missed its criterion without repeats, while a global mixture still lost to kNN on repeats in development; among these variants, gating near-identical instances to memory preserved repetition performance while keeping rule generalisation on new contexts. Perception post-processing: downstream patches on the learner’s side (probe uncertainty, depth localisation, an instance detector) recovered at most +0 .011 of the +0 .131 true-fact gap on new contexts. This suggests that improving the frozen visual representation may be more useful than the tested changes to how the rule learner consumes it. Uncertainty-based asking: a scope-aware question selector did not beat the plain uncertainty band in development, and heuristic post-error asking triggers did not help after rule changes. What remains unsolved: 

rule-level recovery after unannounced changes (a recent-window switch missed its primary criterion in development), adding an 8B LLM as an extra rule level (which reduced reliability in development), and applying the ladder to skill selection where NAPPING already suffices. Three studies failed their own validity checks and are not results. Before any of this, a line of repair-memory studies in physics simulation could not separate the memories it compared (Section C): with two candidate actions and a handful of distinct situations, there was little structure in where a lesson applied. This motivated the study of reach when choosing actions under unwritten site requirements. 

7.2 Future work 

Physical robots and human feedback. Extending the simulation studies to physical robots would test CRAFT across more skills and with noisy or delayed feedback. The current trials use correct simulated feedback, one fixed-pelvis push skill and external setup. Human studies should 17 compare full-menu labels with single yes/no verdicts and measure time and effort directly, beyond query counts. 

Independent requirements. Larger prospective studies should use requirements authored independently of the learner’s grammar. The current grammar overlaps with the generator’s rule families, and the integrated comparisons reuse six hand-specified cases. Independently authored requirements would provide a stronger test of transfer to unfamiliar sites. 

Learning scope and revising rules. Learning or calibrating the memory gate could extend its current fixed-threshold design. Integrated ablations would test whether the decision-level mechanism findings carry through to execution. Revision after unannounced changes deserves particular attention: stale memories and confident rule predictions can persist, and the frontier agent and CarryOn adaptation performed better after changes than their paired ladder controls. 

Broader comparisons. Prospective paired comparisons should extend the small descriptive studies across frontier configurations and resource budgets. Evaluating fuller DROC and CarryOn systems would complement the present interface adaptations (Sections I and J); fresh paired controls would also replace DROC’s exposed streams and historical controls. A separate service ablation would help distinguish the harness’s contribution from that of the decision provider, since both sides currently use the shared service. 

# 8 Conclusion 

Learning unwritten requirements from sparse verdicts requires deciding how far a correction should reach. CRAFT makes that decision a replaceable provider under a common evidence and feedback contract. The scope ladder gives memory precedence on near-identical labelled situations and com-bines rule, open and memory predictions elsewhere using their past predictive evidence. Controlled studies show gains over correction memory on new and repeated synthetic situations; component comparisons explain the value of arbitration within those populations. A continuing-service pilot connects the learner to camera-grounded execution and a frontier memory/rule agent. Accepted completion is similar, but the ladder asks fewer questions and the frontier makes fewer wrong dispatches; all failures remain in the comparison. A DROC plan-level verdict adaptation adds descriptive evidence on the exposed streams, with 93/120 accepted jobs and higher query cost; it does not establish performance against native DROC. A fresh paired CarryOn planning adaptation accepts 90/120 versus the ladder’s 96/120 and asks more questions, while making fewer wrong dispatches and performing better after changes. Its nine timeouts affect completion, and the changed interface limits generalisation to native CarryOn. The next scientific test is a larger prospective comparison on independently specified requirements, followed by broader skills and physical-robot feedback. Reliable revision after unannounced changes remains an open problem.

A.1 Authority 

Authority is deliberately narrow, and each role belongs to exactly one component: • the deployment service admits and sequences jobs; • the task runner owns one job’s goals, verified progress and budgets; • planner and adaptation providers propose; they cannot dispatch physical commands; • the supervisor owns dispatch, physical custody, deadlines and cancellation; • the native backend owns motor commands and its local stop behaviour; • independent verifiers supply the evidence for progress, which the task runner records. Declared site rules live in a rule store and apply equally to every provider. A learned proposal cannot relax an authoritative constraint, and a physical success cannot remove a prohibition. 

A.2 Three loops 

Native control runs independently of task reasoning and network services and keeps each controller’s own rate and stop behaviour; a cancellation acknowledgement is not treated as proof that the robot has stopped. One bounded job reads fresh evidence, asks the fixed planner for eligible actions, obtains one adaptation proposal, dispatches at most one physical operation, verifies its actual effects, and records progress and factual experience; success is recorded only after the original goal and required constraints are checked. Continuing deployment admits the next job without resetting physical state or erasing experience. 

A.3 Contracts that make providers comparable 

The records below are the architecture’s contracts ( ARCHITECTURE_v1 ); the implemented code uses narrower records, mapped in Section A.5. A provider sees a DecisionContext : fresh public evidence, observed site cues, the original and remaining goals, declared constraints, the qualified actions and the provider’s own factual history. It excludes private condition identifiers, future outcomes and hidden rule revisions. It returns a DecisionProposal (execute, observe, wait, ask for help, finish) with evidence references, a reason and the cost it charges. After execution it receives a FeedbackRecord in which the execution effect , the acceptability of the action under the site’s requirements and the whole-task verdict are separate fields, each TRUE, FALSE or UNKNOWN. A generic failure bit would not tell the learner whether the motor, the destination or the remembered rule was wrong; separating them lets a requirement learner ignore execution failures and avoid learning false rules from them. The feedback contract fixes what a provider may learn. Under the level used throughout this paper (F1), the provider learns the acceptability of the action it actually executed and nothing about actions it did not take; abstentions and failed executions return no acceptability verdict. Asking a person is a separate, charged channel (Section 3). 

A.4 Information-boundary tests 

For the selector modules in the initial repeated-context, initial new-context and component studies (the grammar, open, kNN and mixture providers and the gate), three tests ran before any test output: a canary test (private fields replaced by sentinel values must leave every decision bit-identical), a 22 static import check (provider modules cannot import the label generator, rule evaluator or bank loader), and a prefix-invariance test (decisions up to job t must not change when everything after t

is randomised). Later providers had study-specific tests only: The confirmatory Popper comparison checked class bindings and equivalence on smoke runs. The development study of the corrected Popper configuration checked site separation and the ILP configuration. The ILP provider’s module imports code that also loads evaluator exports, so the static import check does not cover it. We found no evidence of label leakage, but the coverage of these tests is not uniform across providers.

• Implemented as bounded prototypes: the supervisor, the skill registry and native simulation backends; a reusable task runner and an in-memory deployment service (records TaskSnapshot ,

These checks assess the software lifecycle; they do not estimate robot reliability. • Partial: the rule store and the shared experience service. # B A frozen, perception-grounded skill layer 

Adaptation methods are compared above one released skill layer that none of them can change. The layer serves a MuJoCo tabletop scene from the LIBERO suite ( 3-4_104_1 ) with a simulated Franka Panda arm, a 512 × 512 agentview RGB-D camera and 20 Hz operational-space control: a known black bowl and white and blue plates. It supplies five skills ( move_to_target , close_lift ,

reorient_held , transport , lower_release_retreat ). Each uses the current RGB-D image, the camera calibration and robot proprioception, and issues bounded seven-dimensional operational-space intents (translation and rotation increments capped at 10 mm and 50 mrad), under shared per-episode ceilings of 560 actions and 1,200 perception queries. Perception is a disclosed known-appearance colour and shape model with current depth geometry; when an object is not found, the skill abstains. 

Qualification. The layer was frozen and then qualified on ten prospective episodes: five matched initial states, each requested to the white and to the blue plate (3,074 simulator actions and 4,132 grounding queries in total). Eight completed the whole controller sequence and passed independent native checks on placement, no gripper contact, object speed and arm stop. The two failures shared 23 one initial state, in which the bowl-grounding query abstained before any controller action; both stay in the denominator. Eight of ten is a small-sample screen, not a reliability estimate. The release seals 5,947 input files; evaluator poses and contact truth were recorded separately and never reached a controller or provider. 

What the layer does not cover. Other objects, open-vocabulary recognition, broader workspaces and real robots are not qualified. In the initial closed-loop demonstration (Section H), the same bowl-grounding abstention is the main execution failure. 

Separate R1 push adapter. The continuing-service pilot uses a different frozen skill: fixed-pelvis R1 tabletop pushing with camera-derived object positions, inverse kinematics and PD control. Its separate prospective screen passed 14/16. This does not expand the Panda qualification above; its domain, completion checks and retained failures are specified in Section G. 

# C Lessons from repair-memory studies 

CRAFT’s first research question was which repair to reuse after a skill failure. In a physics-simulated container-emptying task with a Panda arm, after a slippery object fails under the nominal grasp, the harness can continue or perform a rim re-grasp. Within each study, every method received the same observations (six fixed grasp features), candidate actions and prescribed discovery attempts, and could learn only from its own executed outcomes. Episodes were reset between encounters. 

No memory was established as better. In a prospective comparison frozen before its run (eight streams with six prescribed discovery trials each, 48 autonomous situations, 672 physics executions), NAPPING completed 40 of 48 tasks and three-nearest-neighbour memory 39 of 48, against an evaluator ceiling of 43; the exploratory paired interval includes zero, which shows no advantage but not equivalence. In a second frozen comparison on a withheld condition (four sequences, two prescribed discovery attempts each), post-change experience mattered (NAPPING 16 of 16 post-discovery slippery queries, versus 0 of 16 for the same memory frozen before the change), and NAPPING and kNN tied exactly on the post-discovery subset (32 of 32 each, no harmful interventions). 

Learned applicability did not improve completion. A learned utility predictor and an applicability gate with support, counterexample and margin checks were tried twice. In a small prospective engineering run (12 matched autonomous cases; 168 policy and 24 evaluator executions) the applicability gate completed 8 of 12 tasks, against 11 for NAPPING and for the utility memory. In a later grouped development replay (retrospective, no new physics, 48 situations) the applicability gate completed 32 of 48 and a benefit-gated memory 34 of 48, against 41 for NAPPING: their evidence gates withheld useful repairs. The ungated benefit memory also completed 41 and did not improve on NAPPING. We did not run a larger prospective comparison. 

Implications for task design. With two candidate actions and a handful of distinct situations, there was little structure in where a lesson applied, and the comparisons did not distinguish the memories. Equal information and retained failures made the comparisons interpretable, but did not make this task informative about correction reach. # F Additional negative results 

These results supplement the design discussion in Section 7.1. Unless identified as confirmatory in Section D, they are development findings. 

Memory and perception. Rule inference without memory had a utility difference of −0.031 against kNN on the pooled primary endpoint of patterns A and C with repeats. Without repeats, Rule+Open missed its criterion, although Mixture passed its own condition (+0 .051) within the failed study. Perception post-processing using probe uncertainty, depth localisation and an instance detector recovered only +0 .011, −0.002 and +0 .002, respectively, of a gap of about 0 .13. 

Asking and rule changes. Scope-aware asking did not beat uncertainty asking; asking after errors or contradicting repeats did not improve recovery. The main study’s larger asking benefit for kNN does not explain these failures. A recent-window learner missed its primary criterion after changes on new contexts ( −0.010 [ −0.046 , +0 .023]) and slightly reduced fixed-rule performance. Its gain with repeats (+0 .048 [+0 .006 , +0 .090]) was a secondary, exploratory result. The staleness rule addresses memory; rule-level recovery remains unresolved. 

Extensions. Adding an 8B LLM rule level cost 0 .039 [ −0.095 , +0 .001] on new contexts and gave no gain out of grammar ( −0.031 [ −0.090 , +0 .011]). A frontier-model version has not been run. For 27 skill choice, the ladder passed an archived-repair check but lost to NAPPING on new decision-level situations; we make no broader skill-choice claim. 

Excluded studies. Three studies failed their validity checks: the initial VLM baseline (79.4% agreement with known verdicts against an 80% threshold), the initial ILP configuration, and the asymmetric-harm safety study, whose Popper tie-breaking depended on the Python hash seed. The first two were corrected in later comparisons, with ILP configured on separate tuning sites. None of the failed studies supports a comparative claim. At tenfold harm cost, no learner beat never acting on new scenes in the invalid safety study; this provides no validated safety evidence.

G.1 Execution and evidence 

Each method/stream had one persistent physics/control worker, supervisor, deployment service and learner for all 24 jobs. Independent streams started separately. The R1 pelvis was fixed; inverse kinematics and PD control moved its arms. Every job included a logged external object setup preserving robot joints, controller targets, worker identity and simulation time. Continuity applies within a stream, not to autonomous replenishment or process-restart recovery. Both providers used colour/shape segmentation and depth backprojection from 640 × 400 RGB-D frames with public calibration. A frozen SmolVLA encoder supplied a 1,984-dimensional vision/connector/depth vector for memory. Standardisation used 16 disjoint development frames; the R1 domain did not reuse the main confirmatory study’s image statistics. The frontier consumed perceived facts and retrieved examples, not raw RGB. Paired streams shared nominal assignments, but images could differ because each robot retained its own history. I.1 Published mechanism and adaptation boundary 

We used the released DROC implementation at commit 33e3571c9efb to specify the plan-level mechanism: replan extracts task and robot constraints; save_plan_info appends numbered entries; retrieve_plan_info selects relevant constraints semantically; the planner then uses those constraints. Our independent implementation preserves that information flow. The constraint bank has no CRAFT grammar, expert weights, near-instance gate or automatic invalidation rule. New entries may explicitly record contradictions to earlier entries. At a scored decision, one model call distils the pending part of the agent’s own interaction history and selects relevant indices from its old and newly appended constraints. A second call receives the current camera-derived facts and only the selected constraints. It has no access to the unselected bank or raw history. This contrasts with the custom frontier comparator, which receives nearest/recent examples, a complete ledger of its own events and editable rule notes. The pending history includes previous plans and factual feedback; no current verdict, hidden rule, future context or other provider’s observations are supplied. The adaptation changes several parts of native DROC. Binary verdicts and explicitly budgeted menu labels replace language corrections; the evaluator never supplies a reason for a verdict. The motor controller is fixed, and each plan chooses one push rather than generating code or replanning a multi-step task. Distillation and semantic selection share one model call, and distillation is delayed until the next scored decision. The shared provider converts action probabilities into a push, question or abstention. Known object identities remove the need for DROC’s optional ambiguous-object visual grounding; low-level DINO/CLIP retrieval and skill corrections are not exercised. The model is gpt-6.1-sol at medium reasoning rather than DROC’s GPT-4. This DROC plan-level adaptation to verdict feedback evaluates the published information flow through our interface. It does not reproduce native DROC under its richer correction interface. 

I.2 Equal interaction contract and exposed controls 

The adaptation uses the unmodified service, provider, controller, camera frontend, normalisation and evaluator from the continuing-service frontier comparison, on the same six nominal streams. Every stream starts a new robot and learner that persist through its 24 jobs. The old ladder and frontier outcomes remain frozen historical controls: they were not rerun concurrently or tuned for this follow-up. The streams were already exposed, and hosted-model and native timing variation are possible. A new source and assignment freeze precedes this implementation’s measured outcomes; it does not turn the exposed assignments into held-out evidence. The four commissioning questions, three-optional-question limit, uncertainty band, one-attempt physical budget, fresh-camera admission and failed-execution suppression are unchanged. There are at most two model calls per scored job, sharing a single 60-second decision deadline; neither stage has a reserved fraction. A failed call is not retried and the job remains a failure. Successfully stored knowledge survives a later planning failure. Calls stop when the reported stream token count exceeds 750,000 before a call; an in-flight call can exceed that threshold. The whole run has a 150-minute cap, including execution and setup. The append-only bank is not capped to match the frontier’s 3,000-character editable notes; compute and memory costs must therefore be reported alongside the shared interaction budget. The original 14/16 physical qualification is reused because the motor and observation contracts are unchanged. Six inherited and four additional CPU checks cover learner equivalence, feedback suppression, public projection, selected-knowledge-only planning, append-only storage, invalid 32 retrieval indices and partial usage accounting. One disjoint, four-call model screen passes spatial induction and contradiction handling before evaluation. No evaluation outcomes are used to tune the prompts. All 144 assigned jobs, including 120 scored jobs, remain in the denominators regardless of failure or non-start. Six streams are the descriptive replication unit; no significance test against the historical controls is planned.

J.1 Native components and adaptation boundary 

CarryOn is a close system-level comparator because it connects persistent user and scene context with execution around frozen policies [Wang et al., 2026b]. We use its released implementation at commit 02c97b80987c : the native UserMemory and SceneMemory stores, update_user_memory and 

update_scene skills, user/scene context blocks, and validate_scene_update_requirement are imported unchanged. User facts can be overwritten by key or explicitly deleted; scene entries replace the last established content of a place. The native user-summary prompt preserves its durability filter and instruction to retract obsolete keys while retaining unaffected facts. No CRAFT expert weights, grammar inference, near-instance gate or automatic contradiction invalidation are inserted. At each scored decision, a summary call processes up to 40 pending events from the agent’s own interaction history and executes valid native user-memory writes or deletions. A separate planning call receives the complete current user and scene memories, current camera-derived facts, and at most ten events from its own dialogue history. Prior execution-status events are excluded from fresh-task planning, following CarryOn’s distinction between dialogue and past physical state. Literal labelled corrections remain dialogue. The planner may also write or retract user facts and update scene memory before returning action probabilities to the common decision layer. A newly observed or changed table snapshot requires a scene write. The native validator rejects a plan that omits it; up to two parser-repair calls share the decision’s original deadline. A valid summary update survives a later planning failure. Every operation and before/after memory snapshot is retained. This remains a planning-loop adaptation , with substantive differences from native CarryOn. Sparse action verdicts and paid menu labels replace rich user dialogue; the evaluator supplies no explanation, new rule or counterfactual alternative outside the declared query. The native durability filter may omit ambiguous feedback from long-term memory; recent dialogue remains available. One known visible tabletop and one push replace multi-step endpoint selection and hidden-object search. The scene-update requirement is extended to changed visible-table snapshots, whose content the planner authors. User summarisation is delayed until the next scored decision rather than running asynchronously after task completion; its orchestration is reimplemented. Camera facts replace raw image input, and gpt-6.1-sol at medium reasoning replaces the native model backend. The full native agent loop, visual judge, shielding, recovery and skill reflection are not executed. This experiment cannot establish performance against that complete system. 

J.2 Fresh pairing, common contract and prospective gates 

The fresh paired CarryOn comparison contains six new scene stream pairs, each with four commis-sioning and twenty scored jobs per method: 288 assigned jobs and 120 scored per method. The scene generator uses a new frozen seed range, and no generated scene matches those in the frontier comparison, its DROC follow-up or the hand-authored validity fixtures. The six requirement cases themselves are inherited from the frontier comparison: fresh scenes are not independently authored requirements or new rule families. Four planned revisits occur within each stream; three streams change requirements without announcement. The same two scheduled execution interruptions are assigned to each method. Pair order alternates between ladder-first and CarryOn-first streams. Both methods start independent empty learners and persistent robot/service sessions. They use the unmodified service, ladder, camera frontend, controller, normalisation, physical/task verifiers and shared inquiry/dispatch rule from the continuing-service frontier comparison. The same four 35 commissioning questions, three optional questions, one physical attempt per job, failed-execution label suppression and fresh-camera admission apply. The original physical qualification is reused because these contracts and assets are unchanged. Object-only external setup is counted; robot state and simulation time persist within streams. Historical frontier and DROC follow-up results are retained separately, not substituted for fresh controls or pooled into this comparison. Eight new and six inherited CPU checks cover native overwrite/deletion and retention, scene replacement, the scene-write gate and repair, public projection, failed-execution label suppression, summary persistence after planning failure, fresh-scene disjointness and parity with the main confirmatory study’s ladder. One disjoint model screen checks explicit preference acquisition/revision with unaffected-fact retention, and spatial acquisition/revision from sparse verdict examples. All four decisions pass in eight calls without tuning or a repeated screen. Protocol and source hashes are frozen before measured observations. CarryOn receives at most four calls per scored decision: summary, plan and up to two parser repairs, all within a single 60-second deadline. Transport failures are not retried. The cap is 80 calls per stream and 480 overall. Calls stop when reported stream input/output tokens exceed 750,000 before a call; an in-flight call can cross the threshold. The global wall cap is 180 minutes. All failures, abstentions, unstarted assignments and incomplete usage receipts remain in their respective denominators. Native memory size is not artificially capped. The primary endpoint is accepted task completion; wrong dispatches, completed wrong actions, interventions, execution failures, model cost and post-change/revisit slices accompany it. The comparison has six paired streams as its units and does not establish superiority or noninferiority.
