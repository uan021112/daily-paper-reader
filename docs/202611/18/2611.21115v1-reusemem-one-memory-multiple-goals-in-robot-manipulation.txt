ReuseMem: One Memory, Multiple Goals
in Robot Manipulation
Yoonseok Kang, Dayeon Jung, Seunghoon Jeon, Wonjib Kim, Dongchul Park*
Chung-Ang University
Abstract
Robots that work alongside people should be able to use what they have seen when new requests arise.
The same experience may later support identifying an object or returning it to its original location, although
these uses were unknown during observation. ReuseMem learns to use one visual memory for multiple
later manipulation goals. It records visual features independently of future goals, retrieves complementary
evidence for each request, and combines it with the current scene through a lightweight action interface.
Retrieval is supervised by how well candidate evidence supports expert-action prediction across different
current states, linking memory selection to its use in manipulation. Repeated visual features are stored once,
and memory computations that remain unchanged during action generation are reused. Experiments on
four simulation tasks and two physical scenarios demonstrate reuse of a common recording across different
requests. With matched action adaptation, ReuseMem improves joint goal completion on the benchmark
tasks by 24.5 percentage points over uniform memory. These findings show that one memory can support
multiple later manipulation goals as the scene changes.
1 Introduction
Memory enables robots to act on information that is no longer visible. In everyday assistance, the same
experience may become useful for several requests that arise only later. An earlier observation may identify an
object, reveal its original location, or establish the order of events. The robot need not know which of these
uses will matter when it observes the scene. This calls for one memory that supports multiple later goals as the
environment changes.
Consider a robot observing the contents and original positions of two cases before they are closed and
relocated (Figure 1). Bringing the case containing a USB drive to a tray requires remembering its contents;
returning it requires its origin. The same experience supplies different facts for different actions. After the
transfer, the case must be grasped from the tray, while its destination still comes from the recorded past.

Memory-augmented policies have advanced historical retrieval and its use in control [1–5]. Persistent
experience systems also reuse past observations for later requests through retrieval and planning [6–9]. Building
on these advances, we ask how the same recorded experience can reliably support different later manipulations.
Success on several tasks with separate histories does not directly answer this question. The relevant unit is a
common experience, whose usefulness must persist across requests that need different evidence and produce
different actions.
Such reuse couples two challenges. The robot must select the past observations needed for each request,
then use them with the current scene to generate an appropriate action. Remembering an object’s identity or
former position does not specify where to grasp it now. Earlier actions can change the scene while leaving
the historical facts valid. Training must therefore connect evidence selection to action under these changing
current conditions.
ReuseMem addresses this problem with a goal-independent Writer, a learned Reader, and a lightweight
action interface. The Writer retains visual features and separate temporal entries without an advance inventory
of objects or relations. The Reader selects complementary observations for each request. Its supervision comes
from comparing how well candidate evidence supports expert-action prediction across different current states
for the same goal. Historical facts remain fixed while the required actions vary. The action interface then learns
from the updated Reader’s selections, combining remembered evidence with current observations through
fusion and low-rank adaptation of a frozen pretrained policy.
Practical reuse also requires controlling storage and response time. Recordings often contain many similar
views, yet their order can distinguish events relevant to later requests. To limit storage, ReuseMem stores
matching visual features once while retaining a separate temporal entry for each observation. To reduce
response time, fixed memory projections are computed once per action-sampling call and reused as the action
is refined, while the policy still reads the selected memory anew at every step.
Four simulation tasks and two physical scenarios evaluate different goals from common recordings, both
independently and in continuous execution. With matched action adaptation, ReuseMem improves joint goal
completion by 24.5 percentage points over uniform memory. Ablations and memory interventions examine
evidence selection and action use, while storage and response measurements assess the cost of reuse.
Our contributions are:
• One memory, multiple manipulation goals. We introduce ReuseMem, a framework that records experience
before later goals are known and reuses the same visual memory for different manipulations as the current
scene changes.
• Action-guided memory learning. We train memory retrieval by comparing how different selections of past
observations support expert-action prediction across current states for the same goal. A lightweight action
interface learns to combine the selected evidence with current observations.
• Efficient memory reuse. We reduce memory storage and repeated computation while retaining the temporal
structure of experience. Repeated visual features are shared across temporal entries, and fixed memory
projections are reused within each action-sampling call.
2 Related Work
Memory for robot control.
Memory augments generalist visuomotor policies [10–13] through visual or
event-based banks [1, 14–16], recurrent states or test-time adaptation [17–20]. Moment tokens, past-action
prediction and action-history denoising provide temporal training signals [5, 21, 22], while ECoMEM builds
instruction-conditioned concept records [23]. HALO guides retrieval with video question answering and
sparse attention [2]. Imprint pretrains multi-stream memory with reconstruction and progress estimation
before policy adaptation; its recurrent variant updates memory independently of language [3]. Mem4Act
combines semantic and perceptual supervision with memory-first training [4]. ReuseMem learns preferences
between explicit evidence selections from expert-action prediction across current scenes, then trains the action
2


interface with the Reader’s deployment selections. MemoryBench, RoboMME and RMBench assess historical
dependence [16, 24, 25]; our evaluation pairs different requests with the same recording.
Experience for later requests.
Persistent memory supports subsequent reasoning, planning and manip-
ulation [6–9, 26]. Scene graphs organize observed objects, locations and interactions [27–30]. MemER
reuses keyframes across successive requests through a high-level VLM that issues subgoals to a low-level
policy, while MessyMem links interaction-updated scene graphs to visual records for VLM planning [6, 8].
MEMORA edits typed records, MEM combines video and text, and PAL stores semantic events and executable
subtasks [7, 9, 26]. These systems establish the value of experience beyond its original task. ReuseMem
focuses on the learned path from retrieved visual evidence to current action generation, using a common
recording to evaluate different manipulation purposes.
Efficient memory and inference.
Compression and caching address different costs. Token Merging reduces
redundancy within visual transformers [31]; NativeMEM compresses historical frame views, and MemBodied
maintains fixed-size recurrent state [17, 32]. MemoryVLA merges similar bank entries [1], while Simple-
MemVLA reuses native-video prefixes during inference [33]. ReuseMem separates shared appearance storage
from temporal occurrences, preserving the order and identity of recorded entries. Its cache covers fixed memory
projections within one action-sampling call, while new observations refresh the action input.

3.1 Memory Bank
The Writer comprises frozen visual encoding, feature sharing, temporal-entry creation and learned causal key
computation. Each observation yields appearance features Ai ∈R16×1024. An appearance pool stores immutable
prototypes ¯Au that multiple temporal entries can reference, avoiding repeated storage of matching features.
Each entry keeps its own frame index, observed metadata, validity, prototype reference pi, and retrieval key.
The Writer finds the nearest prototype by pooled cosine similarity and shares it only when both a similarity
threshold and a maximum per-token distance bound are satisfied. Otherwise it appends a new prototype.
The token-level check preserves locally distinctive observations that a pooled similarity could miss. This
appearance sharing avoids duplicate feature storage while preserving separate temporal entries. Prototypes are
never averaged or overwritten.

and its causal retrieval key are

4 Experiments
4.1 Experimental Setup
The experiments examine whether shared experience supports different later goals, whether reuse survives
changes caused by earlier actions, and what storage and response costs it requires. Four RoboMME-based
tasks [24] cover event-relative placement, temporal order, hidden object identity and transient visual cues
(Figure 6). Each task uses 50 common recordings with two later goals, giving 400 separate goal executions and
200 separate two-request sequences per method. Two SO101 tabletop scenarios each use 20 recordings with
three later requests.
Metrics.
Goal success averages completion over individual requests. All-goal success counts a recording
only if both requests succeed in independent branches restored to the same post-recording world and memory.
Sequence success requires both requests without resetting the scene. All-goal isolates different uses of shared
experience. Sequence additionally tests accumulated execution and changed current states. Physical evaluation
reports the three independent requests, their joint All-goal success, and a separate continuous three-request
sequence. Appendix B.1 defines the metrics and task predicates.
Comparisons.
No-Memory (π0.5) receives current inputs. Uniform-Memory (π0.5) selects 24 evenly spaced
historical observations from the same bank with matched action adaptation. MME-VLA (π0.5) uses released
FrameSamp+Modul weights without retraining. MemER (RoboMME) uses the benchmark reproduction
with remembered images and VLM-generated grounded subgoals. Internal No-Memory, Uniform-Memory
and ReuseMem comparisons match the prepared policy, expert data and action-training budget. Released
external systems retain their native memory and policy interfaces, so their differences reflect complete

4.3 Ablation Studies
The ablations separate learning access to the past from using it in the present (Figure 8). The variant without
retrieval learning keeps the Reader and causal keys at their common initialization while retaining action
adaptation. Single-state supervision forms retrieval preferences from one current state per goal while matching
action-training data and budget. The variant without current fusion bypasses the historical/recent residual.
Current images and modulation adaptation remain available.
Retrieval learning raises All-goal success from 36.5% to 60.5%. Using multiple current states for retrieval
preferences improves on single-state supervision (53.0%). Removing current fusion reduces All-goal success
to 55.5% and Sequence success to 47.0%. Its larger effect on Sequence suggests that finding useful history and
acting on it from a changed scene are distinct learning problems. Appendix B.3 provides the complete ablation
results. Appendix B.4 checks whether selected observations cover the necessary facts and whether removing
those facts disrupts action.

4.5 Efficiency
Figure 10 relates All-goal success to new-request response and retained memory. ReuseMem responds in
175 ms, compared with 163 ms for Uniform-Memory and 1,112 ms for MemER. Response includes the current
input, memory processing, action generation and first-command dispatch. Measurements use an RTX 5090 with
BF16 and batch size one. The complete ReuseMem path adds 12 ms over uniform selection while improving
All-goal success by 24.5 percentage points.
At 2,048 temporal entries with 1,331 appearance prototypes, the retained bank occupies 43.98 MiB rather
than 66.38 MiB with separate per-entry features, a 33.7% reduction. All-goal success is 60.5% with sharing
and 61.0% without it, a difference of one recording out of 200. The saving comes from storing matched
appearances once, while retaining their separate temporal occurrences. Uniform-Memory uses the same shared
bank, making its comparison a test of reading rather than storage capacity.
Within-call caching addresses a separate cost. For a continuing goal, memory projections reduce response
from 174 to 165 ms, a 9 ms saving. New-request response, which includes a fresh retrieval step, is 175 ms.

5 Conclusion
ReuseMem learns to use one visual memory for multiple later manipulation goals. A goal-independent Writer
preserves experience, and learned retrieval and action fusion connect it to the current scene. Experiments show
improved joint goal completion and continued reuse after earlier requests change the environment. Ablations
and memory interventions link these gains to both selecting useful evidence and acting on it. Storing repeated
visual features once and caching memory projections reduce the cost of reuse. Perceptual correspondence,
precise manipulation and the bounded range of histories and goals remain limitations. Broader and longer
interactions are a natural next step. This work connects the value of robot memory to the different actions that
the same past experience can support.

Each recording is committed before its later requests are supplied. Associated goals and current-state variants
remain in the same data split. All methods receive camera observations, robot state, timestamps and the
revealed request. Evaluator annotations such as object IDs, origins, cue intervals and success flags are withheld

B.2 Physical Protocol
The SO101 policy uses the same 18-layer memory-attention and modulation interface, initialized from
MME-VLA. A robot-specific π0.5 state/action interface and memory branch are prepared with SO101 expert
continuations and temporal-coverage history, then frozen for Reader, fusion and rank-eight learning. Prepared
weights, expert-data exposure and preparation budgets are matched across physical memory comparisons.
Visible-target transfer, return and brushing trials assess the underlying motor skills.
Case contents and original positions are observed before the cases are closed and relocated. Transfer
requires the correct closed case to be released in its assigned tray; return requires placement at its recorded
origin. Origins are empty at request revelation. Appearance, content assignment and original layout are
counterbalanced.
For the toy scenario, original side and toy identity are counterbalanced before both toys are gathered in a
tray. The robot relocates the requested toy, brushes its emptied footprint, parks the brush and restores the toy.
Localized brushing is scored by coverage of the recorded footprint and limited contact outside a calibrated
margin. Sweeping both possible origins or the entire desk is rejected. Placement tolerances and execution
deadlines are fixed using visible-target controls. Alternative origin acceptance regions are disjoint. These
regions are used for scoring, not supplied to the policy.

C.2 Memory Accounting
For N entries, U prototypes, F = 16·1024 appearance elements, retrieval width d = 256, value/key element
sizes sv,sk, per-entry metadata m and prototype-reference bytes p, bank storage is
Bshared = UFsv +N(dsk +m+ p)+Blookup +Bwriter,
Bdense = N(Fsv +dsk +m)+Bwriter.
(19)
Here Bwriter is streaming Writer K/V and Blookup is persistent appearance-lookup storage. The default bank
recomputes pooled lookup descriptors, so Blookup = 0. Shared appearances replace per-entry values rather than
being retained alongside them.
With 2,048 entries and 1,331 prototypes, bank storage is 43.98 MiB, compared with 66.38 MiB without
sharing. One MiB is 220 bytes. Policy input and action-time memory K/V need 2 and 9 MiB per call. These
workspaces, model weights and allocator overhead are excluded from retained-bank storage.
