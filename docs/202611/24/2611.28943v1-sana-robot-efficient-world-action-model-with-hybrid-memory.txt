# 1. Introduction 

World action models (WAMs) leverage the world knowledge of video generation models [1, 2, 3] to improve action generation by aligning visual prediction with action prediction [4, 5, 6, 7, 8]. They now match or surpass vision-language-action models (VLAs) [9, 10] on manipulation benchmarks [11, 12, 13], which makes them a strong candidate for the low-level policy that must run stably and safely on edge devices. However, current WAMs cannot yet serve as such a policy, for two reasons. First, video prediction adds a large overhead. Besides the actions, each action chunk requires denoising the far more numerous video tokens over several steps. Without optimization, a single request of our 4.5B model takes about 0.6 s on an RTX 5090, compared with less than 0.1 s for 𝜋 0.5 [10], and a synchronous robot stands still during each request. Second, many manipulation tasks depend on information that is no longer visible, such as the number of completed steps or the position of an occluded object. Existing WAMs either act from the current observation alone [5] or keep only a few sparsely sampled past frames [7, 8], which miss most of the episode and add to the latency as the memory grows. Instead, we present SANA-Robot, a 4.5B WAM trained from Sana-Video 2 [14] that runs in real time on edge devices with a fine-grained, minute-level memory. SANA-Robot is a hybrid linear diffusion transformer. It stacks 8 blocks, each with three Gated DeltaNet (GDN) layers [15] followed by one softmax attention layer. A GDN layer compresses the past into a fixed-size recurrent state, so its cost does not grow with the context. A softmax layer attends to every token exactly, at a cost that grows with the context. This architecture matches the needs of a real-time policy with memory, and we build three core designs on it (Figure 2). 

Unified World Action Model. SANA-Robot is pretrained as one model that plays three roles. As a forward dynamics model (FDM), it predicts the future video caused by given actions and serves as a world simulator for policy evaluation (§9). As a policy, it predicts the actions and the future video from the current observation and drives manipulation (§§6 and 7). As an inverse dynamics model (IDM), it predicts the actions that explain a given video, which makes the video and the actions predicted by the policy more consistent. All three modes share one token sequence of multi-view video, proprioception and actions, and differ only in which tokens are clean conditions and which are noised targets. One network thus learns all three roles from the same data, 19.4K hours from 23 datasets of robots, handheld grippers, simulation and human video (§3). 

Hybrid Memory at Constant Cost. Building on its hybrid architecture, we equip SANA-Robot with a hybrid memory. Attention is causal across action chunks, so each chunk reads the past but never the future. The softmax layers attend to the first frame and to a sliding window over the last few chunks, through which information propagates chunk by chunk. The GDN layers absorb every past chunk into their fixed-size state and thus keep a memory of the whole episode. Both memory types cover the long range, at different granularities (§8.3). During autoregressive generation, SANA-Robot writes each chunk into the memory once and keeps only the GDN state and a rolling KV cache over the sliding window. Every action chunk therefore has the same cost, while the memory spans up to about one minute on RoboDojo. 

Full-Stack Infrastructure. The memory changes both training and deployment, and we design the infrastructure of SANA-Robot around it. For training, the memory must be learned on whole episodes, whose lengths vary widely. We propose multimodal sequence packing with task-balanced ordering, which trains on whole episodes without padding and with a stable task mix in every step (§4.3). Balanced and shuffled data loading further mixes many datasets in every step (§4.1). For deployment, we propose memory RTC for asynchronous execution, which hides the inference latency. It extends real-time chunking [16] to a policy with memory by keeping one memory per execution phase, so that every request reads a memory laid out as in training (§5.1). Fused kernels, CUDA graphs, prefix caching and low-bit GEMMs further reduce the latency by 5.3× to 115 ms per action chunk on an RTX 5090 (§5.2). Together, these components enable closed-loop control at 30 Hz on edge devices. In summary, SANA-Robot is a unified WAM with a hybrid memory that serves as both a policy and an FDM. It achieves state-of-the-art performance on the memory dimension of RoboDojo [11] among models of medium size, and the highest success rates on LIBERO-Plus [13], LIBERO-Pro [17] and LIBERO-Max [18]. As a world simulator, it ranks second on WorldArena [19] and behaves similarly to the real environment on DROID. On real-robot tasks, SANA-Robot demonstrates precise manipulation, long-term memory and real-time control, and outperforms baselines such as 𝜋 0.5 [10] and OpenWAM-𝛼 [5].

# 2. SANA-Robot 

SANA-Robot is a world action model (WAM) that jointly generates future video and robot actions with a single diffusion transformer. 

2.1. Unified World Action Model Architecture. We build SANA-Robot on Sana-Video 2 [14], a hybrid linear diffusion transformer for video generation. Its self-attention layers interleave Gated DeltaNet (GDN) linear attention [15] with gated softmax attention, and separate cross-attention layers inject the text. SANA-Robot keeps this single-tower architecture for low latency: the visual and action tokens are placed in one sequence, without a separate action expert. As shown in Figure 2, the sequence holds the multi-view observation latent 𝑜 , one proprioception token 𝑠 , the future video latent 𝑧 and 32 action tokens 𝑎 , where 𝑠 

and 𝑎 use the unified action space of §3.2. The causal video VAE of LTX-2 [3] compresses the video by 32 × 32 × 8,and 𝑧 encodes the frames of a 32-step chunk at a stride of 4. The full token sequence is 

𝑥 = [ 𝑜 ; 𝑠 ; 𝑧 ; 𝑎 ], (1) where 𝑧 and 𝑎 attend to 𝑜 and 𝑠 but not the reverse. The text prompt states the embodiment type, the action representation, the camera views and the task instruction (§3.2), and every token reads it through the cross-attention layers. 

Positional Encoding. We use the 3D multimodal RoPE (mRoPE) [20] with absolute temporal positions to align the video and action modalities. A 2 × 2 grid in the RoPE coordinates accommodates the varying camera setups of robot data: one or two head or external cameras occupy the top row, and the wrist cameras the bottom row; empty cells are padded. Temporally, all tokens share one physical clock: a latent frame is placed at the time of the frames it encodes, the proprioception at the time of the observation, and each action at its own control step. Video and action tokens that describe the same instant therefore share a temporal position, independent of the frame stride and the control frequency of a dataset. 

Unified Training. SANA-Robot is trained with flow matching [21, 22], and every token 𝑖 carries its own noise level 𝜏 𝑖 

(Figure 2). Clean tokens ( 𝜏 𝑖 = 0 ) serve as conditions, and noised tokens serve as targets that carry the loss. The choice of targets thus selects the conditional distribution that one network models: FDM: 𝑝 𝜃 (𝑧 | 𝑜 , 𝑠 , 𝑎 ), IDM: 𝑝 𝜃 (𝑎 | 𝑜 , 𝑧 , 𝑠 ), Policy: 𝑝 𝜃 (𝑧 , 𝑎 | 𝑜 , 𝑠 ), (2) where every mode is also conditioned on the text prompt. The Forward Dynamics Model (FDM) simulates the video that an action chunk causes, the Inverse Dynamics Model (IDM) recovers the actions that explain a video, and the Policy predicts both from the current observation and proprioception. In the Policy mode, the video and the actions of a chunk share one noise level and are denoised jointly. The loss sums the velocity errors over the target tokens, with the action dimensions that an embodiment lacks masked out (§3.2): 

ℒ = ℒvideo + 𝜆 ℒaction , (3) where we set 𝜆 = 1 . The Policy mode drives manipulation (§§6 and 7), and the FDM serves as a world simulator (§9).

2.2. SANA-Robot Policy SANA-Robot-base. SANA-Robot-base uses the Policy mode of the unified model: it predicts the action chunk 𝑎 𝑐 and the future video 𝑧 𝑐 from the current observation 𝑜 𝑐 and the proprioception 𝑠 𝑐 . Since the conditions do not attend to the noisy targets (Equation (1)), their keys and values are computed once per request and reused across all denoising steps (§5.2). 

SANA-Robot-AR. A policy that sees only the current observation cannot act correctly when the information that determines the action is occluded, out of view, or carried only by the progress of the task. SANA-Robot-AR therefore conditions the policy on the visual history of the episode. Continued Training with Hybrid Memory. SANA-Robot-AR is initialized from the unified model and continues pretraining in the Policy mode with the hybrid memory on all data sources, so that the memory is learned before post-training on downstream data. Since filtering and clip splitting shorten the continuous spans of the data (§3), the training windows span up to 8 chunks. We use chunk-causal teacher forcing: a clean copy of every chunk is written into the memory, while a noised copy, which reads the memory of the chunks before it, carries the loss, so that one forward and backward pass trains all chunks of a window (§4.2). 

# 3. Data Pipeline 

Pretraining a world action model across many robots requires data that is both broad and consistent, so that the model learns knowledge of the physical world that is shared across embodiments. We obtain breadth by collecting 23 datasets of four types: teleoperated robots, handheld UMI devices, simulation and human egocentric video (§3.1). We obtain consistency by converting them into one format (§3.2) and by filtering and balancing them (§3.3). From 23.8K raw hours, the pipeline produces 19.4K filtered hours and 133M training chunks (Figure 3).

3.2. Unified Format 

Mixing these sources requires a common format for video, actions and language. We therefore assign every dataset one of a few frame-rate tiers, map all actions into one space with a shared physical meaning, and give all clips text prompts of one structure. 

Time Base. The datasets are recorded at different frame rates and with unsynchronized streams. We assign each dataset the frame-rate tier (10, 15, 20, 24 or 30 Hz) closest to the median frame rate of its main camera. Sources faster than 40 Hz are downsampled to 30 Hz; all others keep their original frames. Within an episode, the frames of the main camera define the time steps. Every other stream, i.e. , the other cameras and the proprioception, commands and gripper of each arm, contributes its latest sample at or before each time step. Thus no step depends on future measurements, and no value is interpolated. In every tier, a training chunk covers 32 time steps, with 32 actions and 8 video frames at a stride

of 4 after the observation frame. The physical clock of §2.1 accounts for the different durations. Human egocentric video, recorded at 30 Hz, is assigned the 15 Hz tier and therefore plays at half speed, which brings hand motion closer to the speed of teleoperated robots. 

Action Space. All embodiments share one proprioception and action space, which includes absolute end-effector poses, absolute joint positions, and gripper or dexterous-hand values. A per-dimension mask removes the slots that an embodiment lacks from both the input and the loss. Because the same robot may carry different grippers, for real robots we recompute every end-effector pose at the flange from the joint positions with forward kinematics. UMI recordings and human video have no joints and fill only the end-effector and gripper slots; for human video, the wrist poses serve as end-effector poses and a virtual gripper represents each hand. Actions are normalized with embodiment-specific statistics, which all datasets of the same robot share. 

Segment and Recaption. Several datasets contain episodes longer than 10 s that span several sub-tasks, and their global instruction alone does not ground each part of the episode in language. We therefore split such episodes into non-overlapping 10 s clips (the last one shorter) and recaption each clip with a VLM. The text prompt combines the embodiment type, the action representation, the view description and the global instruction, and during training adds the step instruction of the clip with probability 0.5, for example: 

> Embodiment Type: dual-arm YAM robot with parallel grippers. Action Mode: robot_base_eef; end-effector targets are absolute future poses expressed in the robot base frame, joint targets are absolute future targets, and gripper targets are absolute future targets. Observation View: left wrist-mounted camera. Instruction: Zip up the green jacket and leave it on the white tabletop. Current step: Zip up the green jacket.

3.3. Filtering and Balancing 

Raw robot data contain defects that the model should not learn from: sensor glitches, idle periods, unusable frames, and video that does not show the recorded motion. Rather than discarding every episode that contains a defect, our filter removes only the affected time steps and keeps the clean spans in between; it drops an episode entirely only when a defect affects all of it. Overall, filtering keeps 81.5% of the raw hours and 93.2% of the episodes (Table 1). 

Kinematic Validity. Actions that violate the kinematics of the robot indicate recording errors. We check every action against the kinematic model of the robot. We remove actions with invalid joint values, actions whose forward kinematics disagrees with the recorded end-effector pose, and actions whose gripper value lies far outside the range between its 1st and 99th percentiles. 

Motion. Long idle periods add no supervision, and jumps indicate recording errors. We remove idle periods in which the joints and the gripper all stay still for more than 0.5 s, but keep shorter pauses, which are part of how a task is executed. A step whose speed between consecutive actions exceeds the physical speed limits (2 rad/s for joints; 0.5 m/s and 2 rad/s for the end effector) is a jump; we remove it and split the episode there. 

Video Quality. Frames that are too dark, overexposed or of very low contrast show little of the scene. We estimate the brightness and contrast of each frame and remove such frames. 

Video-Action Consistency. A video that does not show the motion described by the actions pairs every action with a wrong observation. Frames whose pixels change significantly while the robot is static, and arms whose largest motion is not visible in any of their cameras, are flagged and skipped in pretraining. We drop an entire episode when its video largely mismatches the proprioception, for example when the video lags behind it. 

Balancing. Sampling in proportion to hours would let a few large datasets dominate training, while some high-quality robot families each hold less than 1%. We therefore balance the data by embodiment and data quality. The weight of a robot family grows with its filtered hours raised to the power 0.7, adjusted by a small family-specific prior that reflects data quality. Within a family, the weight of a dataset grows with its filtered hours raised to the power 0.9. Balancing thus gives small, high-quality families a larger share than their hours alone would. # 4. Training Infrastructure 

Training throughput determines how much data and how many design variants we can afford to train on. We raise it at three points: loading the corpus with a balanced mixture (§4.1), training all chunks of a window in one forward and backward pass (§4.2), and training SANA-Robot-AR on whole episodes of varying length (§4.3). 

4.1. Data Loading Data Storage. We store every dataset as ZIP archives of up to 1,000 episodes each. An episode keeps its camera videos, its proprioception and action table and its metadata as separate files. They are stored without compression, so that a data-loader worker reads them directly from the archive. Episodes are packed in the order of their original keys, so the order of the episodes within an archive follows the source dataset rather than being random. The loader never expands the corpus into individual samples: it indexes the valid start of every training window in the spans kept by the filters (§3.3) and reads a window only when it is scheduled. 

Balanced and Shuffled Sampling. Every window of a dataset should have the same chance of being used, so that each episode contributes in proportion to its length. However, opening archives at random would add RAM and CPU load. We therefore assign each archive to one GPU for the whole epoch, so that only the data-loader workers of that GPU open it. The archives are assigned longest first to the GPU with the fewest scheduled windows, which gives all GPUs nearly the same number of windows. Every GPU then runs the same number of steps. A GPU forms each batch from windows of one dataset with the same camera layout, resolution and horizon, so that no batch needs padding. Each GPU rotates through a pool of its archives, so that each batch mixes windows from many archives. Different GPUs draw on different datasets in the same step, so each global batch mixes many datasets. All GPUs derive the same plan from the random seed and the epoch without communication, which also lets an interrupted run resume at the exact batch where it stopped. 

4.2. Chunk-Causal Teacher Forcing 

SANA-Robot-AR is autoregressive: it predicts an episode chunk by chunk, and each chunk is conditioned on the memory of the chunks before it (Equation (4)). Unlike autoregressive video generation, where each frame is conditioned on the history the model has generated itself [47], robot manipulation is teacher-forced by nature: the memory is written from the observed frames, so the next chunk is always predicted from the real observations. A naive way to train such a policy samples a segment of an episode and supervises only its last chunk, with the earlier chunks serving as memory, so that each forward pass trains a single chunk. We instead train every chunk of a window in one forward and backward pass. Since a diffusion model sees each chunk noised whereas the memory must hold it clean, we place every chunk in the window twice (Figure 4a): a clean stream of the video latents builds the memory and carries no loss, and a noisy stream holds, for every chunk 𝑐 , 𝑜 𝑐 , 𝑠 𝑐 and the noised targets 𝑧 𝑐 and 𝑎 𝑐 , and carries the loss. The attention keeps this layout chunk-causal: in the softmax layers, noisy chunk 𝑐 reads the sink, the last 𝑁 clean chunks before it and its own entries, where 𝑜 𝑐 and 𝑠 𝑐 do not read the targets; in the GDN layers, it reads the state after the sink and the clean chunks before it, and its 𝑜 𝑐 and 𝑠 𝑐 update only a copy of that state, which is discarded after chunk 𝑐 . Each noisy chunk thus computes the same output as the forward pass that predicts it at deployment, and one pass over a sequence about twice as long as the window trains all 𝐿 chunks of the window, which the naive scheme trains in 𝐿 passes over segments of 1

to 𝐿 chunks.

4.3. Variable-Length Causal Training 

For every downstream dataset, we fine-tune SANA-Robot-AR on whole episodes, so that its memory spans the full task as it does at deployment. Each training window is then one complete episode of a single task, and its length varies with the task and the demonstration. In causal training, the windows vary in length, which raises three problems in turn: 1) GPUs with shorter windows wait for the one with the longest at every synchronization, which lowers the model FLOPs utilization (MFU); 2) padding the windows to a common length, the standard remedy, equalizes the GPUs but spends compute on the padding; 3) grouping windows of similar length to reduce the padding unbalances the tasks: windows of similar length often come from the same task, so the task mix of a step deviates strongly from that of the data and the loss fluctuates from step to step. We therefore order and pack the windows so that every step balances the load across GPUs, spends no compute on padding and keeps the task mix of the data. 

Task-Balanced Ordering. We first arrange the windows of an epoch into one queue in which every stretch holds each task near its share of the data (Figure 4b). For each task, we shuffle its windows and lay them end to end on a line from 0 to 1, each window spanning a length in proportion to its number of chunks. Each window is keyed by the midpoint of its span, and the windows of all tasks are sorted by this key. Since all tasks advance along their lines at the same rate, up to any key 𝑥 every task has placed a fraction 𝑥 of its chunks, to within half a window, so every stretch of the queue keeps the task mix of the data, while the order within each task stays random. The packing below considers only the window lengths and the queue order, so every step inherits this balanced mix. On RoboDojo, even the least balanced steps then come close to the task mix of the whole epoch. Compared with length-bucketed padding, the detrended standard deviation of the per-step loss drops from 0.0034 to 0.0018 over steps 2K–6K (Figure 4c). 

Sequence Packing for Load Balancing. Packing aims to give every GPU the same load without spending compute on padding, so that no GPU waits for another when they synchronize and the MFU stays high. Following the queue, we fill each GPU with windows of different lengths up to a fixed budget of chunks per step, as in sequence packing for LLM training [48]. Following the implementation of the variable-length attention of FlashAttention [49], the windows packed on a GPU do not interact: attention, the GDN state and the RoPE positions all restart at every window. On RoboDojo, packing cuts the median step time from 3.95 s to 3.62 s ( 8% ), although each step carries slightly more chunks (Figure 4c).

# 5. Real-Time Inference 

Real-time closed-loop control requires the robot to run stably at its control frequency, 30 Hz in our deployment, without any idle time. This places two requirements on inference. 1) The pipeline must be asynchronous, since in synchronous execution the robot idles during every request (§5.1). 2) Inference must be fast, since a lower latency allows a smaller asynchronous delay, so that each chunk is planned from a more recent observation and asynchronous execution loses less accuracy (§5.2). §5.3 reports the resulting latency on server and edge GPUs. 

5.1. Deployment Pipeline 

In synchronous execution, the policy is requested once per chunk, and the robot executes all 𝐶 actions of the new chunk before the next request; with a control period Δ𝑡 and a per-request latency 𝐿 , each chunk takes 𝐶 Δ𝑡 + 𝐿 , of which the robot idles for 𝐿 . Asynchronous execution [16, 51] removes this idle time by overlapping inference with execution: the request for chunk 𝑘 is submitted at step 𝑡 𝑘 = 𝑘 (𝐶 − 𝑑 ), when 𝑑 actions of the current chunk remain to be executed. As long as 𝐿 ≤ 𝑑 Δ𝑡 , there will be no idle time with the first 𝑑 actions of chunk 𝑘 dropped, and the robot executes the next 

𝐶 − 𝑑 actions (Figure 5b). 

SANA-Robot-AR in Synchronous Execution. The softmax layers maintain a sliding-window KV cache over the sink and the last 𝑁 chunks, and the GDN layers maintain a global KV state 𝑆 over all past chunks. At the start of an episode, the first frame is encoded as the sink latent and prefilled into both. Each request then takes three steps: (i) encoding : the VAE encodes the frames observed during the last 𝐶 steps into a video latent and the current frames into 𝑜 ; (ii) prefill : the video latent is forwarded once and written into the memory, updating the sliding-window KV cache in a FIFO manner and the GDN state by eq. (5), and 𝑜 and 𝑠 are forwarded conditioned on the memory, without being written into it; (iii) generation : 𝑧 and 𝑎 are denoised in 𝐾 steps, conditioned on the memory and the prefilled conditions. Although SANA-Robot-AR uses 𝑁 = 1 by default, the cost of a request is nearly constant in 𝑁 rather than linear in it. Only the 8 softmax layers read the window, from a KV cache filled once per chunk, while the 24 GDN layers keep a state of constant size; from 𝑁 = 1 to 𝑁 = 4 , the latency on RTX 5090 rises by only 2.5 ms in BF16, from 173.3 to 175.8 ms.

5.2. Inference Optimization 

A request runs 𝐾 denoising steps of the 4.5B-parameter backbone, plus the prefill, which for SANA-Robot-AR also writes the last chunk into the memory. In eager PyTorch, a large part of its latency lies outside the GEMMs: in the GDN layers, whose computation runs as a chain of small kernels, in the normalization, rotary and modulation operations around each GEMM, in the video VAE, and in recomputing the conditions in every forward pass. We reduce it with kernel fusion, CUDA graphs, prefix caching and, optionally, low-bit GEMMs; Figure 7b shows the latency of SANA-Robot-AR as they are added one by one. 

Kernel Fusion. We implement fused Triton kernels for the operations outside the GEMMs: 1) each GDN layer runs as a single kernel, and for SANA-Robot-AR one kernel updates the GDN state when a chunk is written into the memory while another reads it; 2) RMSNorm and RoPE of query and key are fused into one kernel; 3) the attention residuals [52], the adaLN modulation and the gated residual connections around each sublayer are fused into one kernel; 4) the SwiGLU activation is fused into the epilogue of the gate and up projections. The kernels are tuned separately for each GPU, and all of them match eager execution bitwise or within BF16 rounding. The VAE encoder is compiled as well.

CUDA Graphs. We capture each request of SANA-Robot-AR as two CUDA graphs, one writing the last chunk into the memory and one prefilling the conditions and generating, both on the memory in static buffers. Under asynchronous execution, the memory of each phase is copied into these buffers before its request, so one set of graphs serves all phases. The compiled VAE encoder is captured as well. 

Prefix Caching. The conditions, including text prompt and observation, do not attend to the targets (§2.2), so their keys and values are the same in all 𝐾 denoising steps. Therefore, we pre-compute them before the denoising steps and reuse them during multiple denoising steps. 

Low-Bit GEMMs. On edge devices, the GEMM throughput is the main bottleneck once the remaining operations are fused. # 6. Simulation Benchmark Results 

On each benchmark, we post-train SANA-Robot-AR from the pretrained model on whole episodes of the demonstrations, which fill every GPU up to a fixed budget of chunks (§4.3). All runs use AdamW with 1,000 warmup iterations and a cosine schedule that decays to 1% of the peak learning rate, and each run stops before the end of its schedule. Baseline results are taken from the official leaderboards or from the papers that report them. 

6.1. RoboDojo 

The benchmark [11] contains 42 bimanual simulation tasks on the ARX X5 robot, grouped into five capability dimensions: generalization; precision; long-horizon execution; memory, whose tasks depend on information observed earlier in the episode; and open-vocabulary instruction following. Following the official protocol, we report the average score, which credits partial progress, and the success rate, each averaged over the tasks of a dimension and then over the five dimensions. In view of the small items in the scenes, we use the head camera at 384 × 480 and the two wrist cameras at 

192 × 256 in a T-shaped layout on the RoPE grid, and predict absolute end-effector poses in the robot base frame. The episodes span 4 to 49 chunks, and we pack them with task-balanced ordering (§4.3) into 142 chunks per GPU. We train with a peak learning rate of 1 × 10 −4 and a cosine schedule over 50k iterations with 32 GB300 GPUs. Table 3 compares SANA-Robot-AR with VLAs, WAMs and GPT-6 Astra, a frontier foundation model used directly as a policy. With 4.5B parameters, SANA-Robot-AR achieves the best average among them, 34.31 / 27.09%. Specifically, on the memory dimension, SANA-Robot-AR achieves a success rate of 52.33, outperforming GPT-6 Astra’s 38.67 and InternW0-Δ’s 34 by a large margin. In addition, SANA-Robot-AR achieves the best scores on the precision and long-horizon dimensions, demonstrating that our hybrid memory model supports both long-term history and precise control.

# 7. Real-World Experiments 

Beyond the benchmark, we design five tasks: three short tasks, Magic Cube, Three-Cup Shell Game and Air Hockey, and two long-horizon tasks, Make Coffee and Tower of Hanoi. We compare SANA-Robot-AR with baselines on Make Coffee, Tower of Hanoi and Magic Cube, and use Three-Cup Shell Game and Air Hockey to examine its memory and asynchronous control; on Tower of Hanoi and Air Hockey, we also compare inference with BF16, FP8 and NVFP4 GEMMs. 

7.1. Setup Hardware and Training. Four tasks run on a YAM Ultra robot, and Make Coffee runs on a Galaxea R1. For each task, we collect 100 episodes and train a separate policy on them, initialized from the pretrained SANA-Robot-AR (§2.2), for 10k steps on two H100 nodes; as in §4.3, each step fills every GPU with a budget of 48 chunks rather than a fixed batch of episodes. At deployment, the policy runs on an RTX PRO 6000 (Tower of Hanoi, Magic Cube, Three-Cup Shell Game and Air Hockey) or an RTX 5090 (Make Coffee). 

Evaluation. We evaluate every task over 20 rollouts, with the following metrics: 1) Three-Cup Shell Game: a rollout succeeds if the robot picks the cup that hides the ball; 2) Air Hockey and Magic Cube: each successful hit of the puck or turn of the cube counts as a success, and each failed one as a failure; 3) Tower of Hanoi: the number of rings stacked consecutively in the correct order, counted until the first misplaced ring and divided by the total of 7, averaged over the rollouts; 4) Make Coffee: the long-horizon task can be split into 7 sub-tasks, from picking up the capsule to handing over the coffee cup, and each rollout is scored by sub-tasks.

8.1. Memory Designs 

We compare our memory with those of two recent WAMs by post-training SANA-Robot-base on RoboDojo with each of them, with the same data and initialization as SANA-Robot-AR (Figure 9a): 1) VPP2 memory keeps the sink and 8 frames sampled backward from the current step at intervals of 1 s; 2) InternW0-Δ memory keeps the sink and a single frame 32 steps back. Both designs share three limitations. First, their memory has a fixed capacity, so all history other than the kept frames is lost. Second, sparsely sampled RGB frames are coarse, since they may miss the key motions or object states. Third, the memory frames are encoded and forwarded again at every request, so the inference cost grows with the length of the memory. SANA-Robot-AR instead uses a hybrid memory (§2.2): the GDN layers keep a global state over all past chunks, and the softmax layers attend causally to the sink and the last 𝑁 chunks through a sliding window, which carries earlier history forward, chunk by chunk, into the current window. The memory is chunk-level: each chunk stores the video latent of its full span of 32 control steps, so it keeps fine-grained information, such as every position the target cup passes through in the Three-Cup Shell Game (§7), which sparsely sampled frames may miss. Each chunk is encoded and written into the memory once, after it has been observed (§5.1), so the memory covers the whole episode, and our model predicts each chunk at a constant cost per request. This pays off in both performance and efficiency. On the memory tasks of RoboDojo, SANA-Robot-AR reaches 48.8% success, against 28.3% and 31.4% for SANA-Robot-base post-trained with the memory of VPP2 and InternW0-Δ, respectively (Figure 9b). Our memory is particularly strong on tasks that need a long memory span: on press-by-number, where the policy must count how often it has pressed each button, SANA-Robot-AR succeeds in 82.67% of the episodes in the official evaluation, against 3.3% with the memory of InternW0-Δ.

8.2. Conditioning on the Current Observation 

The current observation is an essential input of a WAM. In developing SANA-Robot-AR, we compared three ways for the target chunk to read it: 1) bidirectional: 𝑜 𝑐 and the targets attend to each other (Figure 10b); 2) w/o observation: the target chunk has no observation token, and the current frame enters only through the memory, as the last frame of the previous chunk 𝑣 𝑐 −1 (Figure 10a); 3) causal (SANA-Robot-AR): the targets read 𝑜 𝑐 , but 𝑜 𝑐 does not read them and is not written into the memory (Figure 10c). We evaluate them on the memory and the precision tasks of RoboDojo, which test the use of the history and of the current state, respectively (Figure 10d). We observe that each alternative fails at one of the two: the bidirectional policy ignores the memory, and the policy without the observation loses precision. With bidirectional attention, the policy takes a shortcut through the current frame and succeeds in only 9.1% of the memory tasks; it puts 14% of its softmax attention on the memory (45% without the observation), and removing the memory raises its action MSE by only 1.3× (249 × without the observation). Without the observation, the policy is forced to use the memory (49.6%), but it sees the current state only as part of the previous chunk, without the fine details of the current frame, so its precision drops to 21.3%. Our causal observation keeps both, with 48.8% on the memory and 30.1% on the precision tasks. It also allows prefix caching: the keys and values of 𝑜 𝑐 are computed once per request and reused in all 𝐾 denoising steps (§5.2).

8.3. How Softmax and GDN Layers Use Memory 

SANA-Robot-AR is, to our knowledge, the first WAM with a hybrid memory, which raises a question that does not arise in WAMs with a single type of attention: what do the softmax and the GDN layers each learn to remember, and how does this history reach the actions? We answer it offline, with teacher forcing on 140 RoboDojo episodes, using the intermediate checkpoints from 5k to 20k post-training steps. To measure how much the policy relies on a source of history, we cut it from the forward pass while keeping the current observation, and report the action MSE relative to the full model, as a geometric mean over the chunks 𝑐 ≥ 2, where 𝑐 is the index of a chunk within its episode (on the memory tasks unless stated otherwise). 

Each Memory Component Matters. Removing any component of the memory sharply raises the action MSE at 20k steps (Figure 11a): by 1.8× without the sink ( 5.3× at 𝑐 = 1 ), 1.6× without the GDN state, 3.4× without the sliding window, 7.2× without both, and 12 × with the previous chunk as the only history. The policy learns to use these components during post-training: from 5k to 20k steps, the action MSE of the full model falls by 2.4×, while without the GDN state and the sliding window it stays flat, so the gains of post-training come from the memory. The reliance holds in every category of RoboDojo, not only on the memory tasks (up to 19 × with the previous chunk alone). 

Softmax and GDN Layers Learn Memories of Different Granularity. The two types of layers carry the history beyond the previous chunk along two paths: the softmax layers pass exact latents forward chunk by chunk through the sliding window, while the GDN layers compress the whole episode into a fixed-size state. The policy relies on both, and increasingly so as the episode grows (Figure 11b). On the memory tasks, cutting the sliding window raises the action MSE by 1.6× for 𝑐 = 2 –3 and by 6.7× for 𝑐 ≥ 16 , and removing the GDN state raises it by 1.1× and 2.2×, with the same trend in every category. The coarse GDN state thus complements the fine-grained window over the long range. 

The Predicted Video Bridges the History to the Actions. In the softmax layers, the actions barely read the history directly: cutting these reads raises the action MSE by only 1.05 ×. Instead, the video predicted for the current chunk reads the history, and the actions read this video: preventing the video from reading the history raises the action MSE by 

3.8×, and cutting the read of the actions on the video raises it by 8.0×. Predicting the video is therefore not only an auxiliary objective but a bridge through which the actions recall the past, which is also why the memory stores only video latents.

# 9. SANA-Robot World Simulator 

Beyond acting as a policy, the FDM mode of SANA-Robot serves as a world simulator. We first formulate the simulation problem (§9.1), then describe how we post-train the simulator for long, few-step rollouts (§9.2), and finally evaluate it on WorldArena and on policy evaluation with DROID policies (§9.3). 

9.1. Problem Formulation 

Our simulator starts from the FDM mode of the unified model. Unlike the policy mode, which receives the real observations, the world simulator acts as the environment itself. Therefore, the continuous generation of the world simulator relies on its previous output as memory:

9.2. Long-Video Post-Training 

The world simulator is post-trained in two stages: (1) reducing the error accumulated with teacher forcing and resampling forcing; (2) improving the efficiency with few-step distillation. 

Stage 1: Teacher and Resampling Forcing. Starting from the pretrained SANA-Robot-base, we first adapt it to chunk-causal generation with teacher forcing, where every chunk conditions on the ground-truth history. We then continue training with Resampling Forcing [99] to improve the robustness to rollout errors. Specifically, we partially noise the ground-truth video latents and denoise them autoregressively with the current model, which yields a perturbed history. Then the perturbed history is adopted as the condition for future chunks, enabling the model to tolerate errors in its history. 

Stage 2: Few-Step Distillation. We freeze the Stage-1 model as the teacher and distill a 4-step student from it with continuous-time consistency distillation (sCM) [100]. The teacher provides the velocity at the sampled noise level, and the student learns to map every point on the teacher’s probability-flow trajectory to the same clean endpoint. After sCM, we apply Self-Forcing [47] to further reduce the accumulated error.

A useful simulator should not only produce realistic video but also reproduce the task success that a policy reaches on the real robot. We therefore evaluate it in two settings: action-conditioned video generation on WorldArena (§9.3.1), and policy evaluation with DROID policies following Ctrl-World [101] (§9.3.2).

𝜋 0-DROID, 𝜋 0-FAST-DROID and 𝜋 0.5-DROID, on seven tasks: pick and place, towel folding, drawer, stacking, tissue, closing a laptop and table wiping, which gives 21 policy–task pairs with known real-robot success rates. Each policy is rolled out in the world model on every pair, and human annotators label each rollout video as a success or a failure of the task; the annotators do not see which model generated a video, and all videos are re-encoded identically. For a fair comparison, we also roll out the public Ctrl-World checkpoint under the same protocol, 20 rollouts per pair, and mix its videos with ours in one shuffled pool, so that both models are annotated blindly in the same round. 

Implementation Details. We evaluate a policy with policy-in-the-loop simulation: the policy reads the generated observation and proposes the next action chunk, and the simulator renders its visual consequences. Repeating this process produces policy-in-the-loop rollouts entirely in imagination. We generate the rollouts in the same way as Ctrl-World [101]. The simulator is trained on DROID with three camera views at 320 × 192 on the 2 × 2 grid, and is conditioned on absolute end-effector poses and joint positions. 

Results. Figure 12 plots the world-model success rate of each pair against its real-robot success rate. A faithful simulator puts the points on 𝑦 = 𝑥 . Ctrl-World lies mostly below this line: its fit is 𝑦 = 0 .82 𝑥 − 10 .8, and its mean success rate over the 21 pairs is 32.4%, against 52.6% on the real robot. The fit of SANA-Robot, 𝑦 = 0 .93 𝑥 + 9 .4, is closer to 𝑦 = 𝑥 in slope, with a mean success rate of 58.3%. 

# 10. Related Work 

Robot Policy Models. Vision-language-action models (VLAs) adapt pretrained vision-language models to output robot actions [107, 85, 9, 10, 63, 54]; they inherit the semantic knowledge of web-scale image-text data, but learn how a scene changes under their actions only from robot data. A second line of work builds on video generation models, i.e. , world action models (WAMs), which predict actions aligned with the future video [108, 109, 110, 111, 4, 112, 113, 5, 7, 8]. Since WAMs inherit the cost of video generation, recent work makes them faster by decoding the actions without generating the video at test time [109, 6, 60, 7], by using a compact backbone or a lightweight action module [96, 77], by reducing the video to one or a few denoising steps [112, 8], and by system-level optimization such as low-bit inference [112]. SANA-Robot instead makes the backbone itself efficient: it builds on a hybrid linear video DiT [14, 114, 115], keeps generating the video, through which the actions read the history, and adds the deployment optimizations. 

Memory in World Action Models. Most VLAs and WAMs act from the current observation, although many manipula-

tion tasks depend on what is no longer visible. Therefore, history is crucial for some long-horizon tasks, but the cost of each decision grows with the length of the history. VLAs thus compress the history: they keep a bank of perceptual and cognitive memory tokens [116], aggregate features or compact tokens of past frames [117, 118, 119], or retrieve task-relevant keyframes [120]. Among WAMs, VPP2 [8] conditions on the first frame and eight past frames sampled at one-second intervals, and InternW0-Δ [7] keeps the first frame and a single past frame 32 steps back; both encode these frames again at every request. Autoregressive WAMs [112, 113, 121] attend to a cache of past chunks with softmax attention, whose cost grows with the number of cached chunks. SANA-Robot introduces a hybrid memory to WAMs, combining linear and softmax attention: the GDN state keeps a global memory of the whole episode at a constant cost, and the softmax window resolves the recent chunks in detail. 

# 11. Conclusion 

We presented SANA-Robot, a 4.5B world action model with a minute-level memory that runs in real time on edge devices. Built on a hybrid linear diffusion transformer and pretrained on 19.4K hours of diverse data, SANA-Robot serves as a policy, a forward dynamics model and an inverse dynamics model. Its memory pairs GDN layers, which keep the whole episode in a fixed-size state, with softmax attention over the first frame and the most recent chunks, so that every action chunk costs the same however long the episode runs. Around this memory, we built the training and deployment infrastructure: multimodal sequence packing with task-balanced ordering trains on whole episodes without padding, memory RTC extends real-time chunking to a policy with memory, and fused kernels, CUDA graphs, prefix caching and low-bit GEMMs bring a request of SANA-Robot-AR to 115 ms on an RTX 5090, which supports asynchronous control at 30 Hz. In addition to the efficient deployment, SANA-Robot achieves the best performance on several simulation benchmarks, outperforms 𝜋 0.5 and OpenWAM-𝛼 on real-world tasks and works as a simulator environment for DROID policies. In conclusion, SANA-Robot is an effective and efficient unified robotics foundation model.
