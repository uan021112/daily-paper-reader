## Abstract 

Household robots often need to operate appliances, and smart appliances offer both control panels and device APIs. Existing embodied AI simulation environments, however, model appliances solely as physical objects. We introduce PAIR, a smart-home simulation environment grounded in the Matter protocol 1, the industry standard for smart-home devices. PAIR provides 84 smart-device assets whose func-tional control panels and APIs act on a shared device state, with ambient conditions that evolve in response to both. From a survey of 1,443 requests, we construct a benchmark

1arXiv:2611.23070v1 [cs.RO] 17 Nov 2026 1. Introduction 

Building household robots that assist people with everyday tasks is a long-standing goal of embodied AI [10, 13, 31]. Performing these tasks often requires robots to operate household appliances by manipulating their controls, such as pressing buttons, turning knobs, and navigating touch-screens. Modern smart appliances, however, increasingly provide application programming interfaces (APIs), which allow external systems to read device states and send con-trol commands through software [1, 5, 7]. Household tasks often involve both physical actions, such as navigation and object manipulation, and appliance operations that can be performed through APIs. Therefore, household robots need to flexibly select and combine phys-ical actions and API calls to accomplish everyday tasks effi-ciently. For example, the request “Wash my shirt,” requires a robot to physically load the shirt into the washing ma-chine and close the door. Once the door is closed, the robot can start the cycle and monitor its progress through the API, without operating the control panel. Studying how robots execute such tasks at scale calls for a simulation environment where device states change over time and where physical actions and API calls op-erate on the same devices. Existing simulation environ-ments [13, 15, 18] provide rich physics-based environments for robot manipulation, but they treat appliances as objects to be physically operated and do not consider smart-home settings, where devices report their states and accept com-mands through APIs. To bridge this gap, we introduce PAIR (Physical-API Integration Environment for Robots), a smart-home simu-lation environment that integrates physical and API-based device control. In PAIR, device states progress over time and respond to both physical actions and API calls, and running devices in turn change four ambient conditions of the home (temperature, illuminance, humidity, and air qual-ity). We develop 84 smart-device assets , each with a func-tional physical interface and an API, across 14 appliance categories and four sensor categories that report these am-bient conditions. Device states, commands, and operational constraints are defined according to the Matter protocol [5], an industry standard for smart-device interoperability. To ground evaluation in what people actually want from such a robot, we surveyed 129 participants about device-related household tasks they would delegate to a mobile manipulator capable of handling objects, operating appli-ances, and remotely controlling smart devices, and retained 1,443 requests from 108 participants after screening. We la-bel each request with the skills it requires, using a taxonomy of robot skills in three categories, physical, perception, and human interaction (Table 1). More than half of the requests (58.4%) involve checking a device’s status or waiting for an event, and APIs alone could complete only 39.6% of them, while the remaining 60.4% also require the robot’s physical actions or perception. From these requests, we construct a benchmark of 40 tasks that cover the skills in our taxonomy and all device categories in PAIR. Every task requires ob-ject manipulation yet can be completed without API access, so the same task can be evaluated with and without APIs and across policy architectures. Using this benchmark, we investigate how well current vision-language-action (VLA) policies handle such tasks. To adapt them to our robot and tasks, we collect 120 task-level demonstrations (three per task) and 220 demonstra-tions of atomic skills, all performed without API access. We then evaluate these policies alone, with a high-level planner, and with a planner that has API access, comparing task success and execution steps and analyzing how perfor-mance varies with the skills each task requires. None of the six VLA variants completes an evaluation task. API ac-cess raises device-operation success, yet with oracle plans and API access, more than 90% of the failed rollouts still stop at a navigation, pick, or door subtask. Even with ora-cle physical execution, the best planner reaches only 57.3% Progress, and several planners choose the API in response to panel visibility more consistently than to the stated API delay. 

## 2. Related Work 

Household Simulation Environments for Robotics. Sim-ulation environments have been a cornerstone of embod-ied AI research, enabling scalable training and evalua-tion in household environments while reducing the cost of real-world experiments. Early examples such as Virtu-alHome [22], AI2-THOR [12], and ALFRED [28] estab-lished interactive 3D environments for household activi-ties, but largely abstracted low-level object manipulation. Recent environments have expanded task diversity, dataset scale, and the realism and interactivity of articulated as-sets [13, 17, 18], enabling increasingly complex and physi-cally grounded household tasks to be studied at scale. De-spite these advances, existing environments treat appliances only as objects to be physically operated and do not con-sider smart-home settings, where devices report their states and accept commands through APIs. 

Benchmarks for Smart-Home Agents. Smart-home agent benchmarks evaluate household request understand-ing and connected-device control. Earlier benchmarks es-tablished LLM-based smart-home control by evaluating how agents translate natural-language household requests into sequences of API-based device operations [11, 14, 24]. SimuHome [25] advanced smart-home simulation by adopt-ing the Matter protocol to model device states, commands, and operational constraints, while simulating their effects on ambient conditions over time. ## 3. PAIR 

We present PAIR, a smart-home simulation environment that integrates physical and API-based device control, building on OmniGibson [13] for physical simulation. Fig-ure 2 illustrates the overall system architecture. 

3.1. Smart-Device Assets 

To support the realistic physical operation of smart-home devices, we construct 84 functional smart-device assets across 18 device categories, 14 of appliances and four of sensors. We source one to three appliance bodies per cate-gory, primarily from high-fidelity ArtVIP assets [9], supple-mented with appropriately licensed third-party assets. In-spired by real-world household appliances, we manually de-sign and implement three functional control-panel variants (P1–P3) for each body, as exemplified in Figure 3. Each panel provides a control for every function and a display or indicator for every state of the underlying Matter-based de-vice model. Compared with our measurements of commer-cial appliances, its buttons and knobs are somewhat larger and its displays are of similar size. We further evaluate the perceived realism of the resulting assets through human evaluation, obtaining an average realism score of 4.63/5 (Appendix A.2). Details on asset sources, licenses, panel measurements, and device-specific physical interfaces are provided in Appendix A.1. 

3.2. Agent Interface 

Agents in PAIR interact with the environment through two channels: physical actions and API calls. For physical ac-tions, agents receive visual observations of the environment and execute actions such as navigation, object manipula-tion, and device operation. Device indicators, panel dis-plays, and sensor displays provide visual access to device states and ambient conditions. For API calls, we use SimuHome’s Matter-based device model [25] to represent networked device states and com-mands. Agents can identify target devices, inspect their available attributes and commands, query device and sen-sor states, and issue device commands with the required ar-guments through structured APIs. Commands that cannot be executed given the device’s current state and operational constraints are rejected without changing the device state. The full list of API tools is provided in Appendix A.3.2.

Updates from API Calls. When an API command is exe-cuted, it updates the shared device state, with corresponding changes reflected in the device’s physical behavior and ob-servable feedback, such as control-panel displays and indi-cators. We additionally model network communication as a configurable one-way delay d, set to 200 ms by default based on message-delivery delays of up to 200 ms observed in prior measurements of Matter in an indoor home envi-ronment [16]. Accordingly, a command takes effect after d,and the response returns to the agent after a total round-trip delay of 2d. A state query similarly reads the shared device state after d and returns the observed value after 2d.

Updates from Physical Operation. Physical operations update the shared device state locally according to the de-vice’s operational constraints, with the resulting changes re-flected in the corresponding API-exposed state and observ-able feedback. Unlike API calls, physical operations are applied locally rather than transmitted over the network, so we introduce no additional communication delay for them. For example, pressing the power button on a smart light up-dates its power state, changes the corresponding observable feedback, and affects the room illuminance. 

## 4. Survey of Smart-Home Requests 

Benchmark tasks are often designed by researchers, which leaves open whether they reflect what people would actually ask a robot to do. BEHAVIOR-1K [13] addressed this by drawing activities from time-use surveys and asking people which ones they would want a robot to do. Yet, its activities assume a conventional home, not a smart home in which appliances can also be controlled remotely. We therefore surveyed 129 participants, asking them to imagine a robot capable of navigating the home, manipulating objects, op-erating appliances, and remotely controlling smart devices. Each participant answered “What would you ask the robot to do?” by writing single-device requests for devices assigned to them and multi-device requests involving two or more devices of their own choice, drawing on PAIR’s 18 device categories (14 appliances and four sensors) and 124 household objects. For each request, they then marked the objects and device operations it involves, grounding the request in concrete objects and device functions. After ex-cluding empty or uninterpretable responses and those that did not follow the instructions, we retained 1,443 requests from 108 participants (Appendix B.2). To characterize the skills these requests require, we con-struct a taxonomy of robot skills (Table 1). ## 5. Benchmark Design 

5.1. Task Design 

Each task in our benchmark specifies the required ob-jects and devices, initial conditions, and goal conditions. Our benchmark focuses on how embodied agents combine physical actions with API access, and we therefore design all tasks around two principles: physical necessity and 

physical-only solvability . The first principle requires ev-ery task to include at least one step that no API can perform, such as loading dishes or closing a door, so that no task can be completed through APIs alone. The second principle re-quires every task to allow a complete physical-only solu-tion, so that API access changes how a task is executed and not whether it can be solved. Based on these principles, we keep the 871 survey requests (Section 4) that involve both a device operation and a step that no API can perform. After removing 327 that cannot be executed in the simulator and 148 by basic filtering, we select 40 tasks from the remain-ing 396 (Appendix D.1). Ten of the 40 tasks come from multi-device requests and involve two to four devices each, such as a washer and a dryer, or a sensor whose reading conditions an appliance operation.

5.2. Episode Instantiation 

For each task, we instantiate six episodes by randomizing the placement of task-relevant objects, the initial states of devices (e.g., open/closed, on/off), and the robot’s initial base pose. Three of the six serve as training episodes for demonstration collection, and the remaining three are held out as evaluation episodes, yielding 120 episodes of each kind. An episode’s subtask sequence is generated by in-stantiating the task’s template according to its initial state (e.g., omitting the door-opening subtask when the door is initially open). Each subtask applies one skill from our tax-onomy (Table 1) to a single target, such as navigating to the dishwasher or picking up a plate. Figure 5 shows one of the evaluation episodes. ## 6. Experiments 

6.1. Experimental Setup 

Low-Level VLA. We fine-tune π0.5 [4] and GR00T N1.7 [3] on the 340 PAIR demonstrations (Section 5.3). Each task-level demonstration is used both as a full trajec-tory with its task instruction and as subtask segments with their subtask instructions, and each atomic demonstration as a single subtask segment, so a policy can follow either kind of instruction, as in hierarchical VLA systems [4, 27]. Training details are provided in Appendix E. 

High-Level Planner. We use Qwen3-VL-8B-Instruct as the high-level planner unless otherwise specified. The planner is queried every 5 s of simulated time, between which the VLA follows the current subtask. At each query, it receives the task instruction, the head and wrist camera images, the elapsed time, and a memory of its past subtasks. The high-level planner chooses one of five actions: (1) issue a new physical subtask to the VLA, (2) continue the current one, (3) wait, (4) end the episode, or (5) make an API call. API calling is available only in the + HL (API) setting (see Ap-pendix F.2 for more details). 

Baselines. We evaluate each VLA in three variants. First, the standalone VLA executes the full task instruction with-out a high-level planner. In + HL, the planner instructs physical subtasks to the VLA without access to device APIs. In + HL (API), the planner is able to call device APIs. 

Evaluation Protocol. We run all variants end to end on the 120 evaluation episodes (three per task). An episode ends upon task success, robot fall, or exhaustion of an action budget set to 1.2 times the mean demonstration length for its task. Simulated time is paused during model inference so model latency does not affect the results. To measure the effect of API access without upstream failures, we also evaluate in isolation each subtask that ei-ther channel can complete. Each subtask starts from the state in which a training demonstration begins it, restored by replaying the demonstration (100 subtasks, 78 device operations and 22 status checks). The planner receives the request and the demonstration’s earlier subtasks, and each subtask must be completed within 90 s of simulated time, either with physical subtasks only (+ HL) or with API ac-cess as well (+ HL (API)). To diagnose planning and physical execution separately, we also replace one of the two with an oracle on one eval-uation episode per task (40 episodes). In VLA execution with oracle plans , the planner is replaced by the episode’s ground-truth subtask sequence (Section 5.2). We evaluate this setting both with and without API access, with the ora-cle generating the correct API calls in the former. In high-level planning with oracle physical execution , the VLA is replaced by scripted primitives that complete every physical subtask. Here we compare Qwen3-VL-4B/8B-Instruct [2], InternVL3.5-4B-Instruct [30], GPT-6 Luna [20], and Gem-ini 3.5 Flash-Lite [8] as planners.

6.3. End-to-End Evaluation 

Overall Performance. Table 3 presents end-to-end evalua-tion results. Although every task was completed by a human operator on its training episodes and by oracle physical ex-ecution of its oracle plan on all 40 diagnostic episodes (Ta-ble 4), none of the six VLA variants completes any of the 120 evaluation episodes (Task SR 0.0%). 

Why do models fail? The low success rate stems from the two challenges in PAIR tasks, (1) long task horizons 

and (2) fine-grained device control . We find that realis-tic user queries from survey participants (Section 4) require 9.9 subtasks on average, making failures in earlier subtasks consequential for subsequent ones. The low success rate of subtasks under the “Place” skill shows this challenge. To successfully place an object, the robot must first pick it up and, when placing it inside an appliance, open the door. However, in most of the times, models fail at these prereq-uisite steps, causing the “Place” skill to have a success rate of 1.2%, despite being required in 117 of the 120 episodes. Also, models struggle to operate the realistic device control panels in PAIR, which are modeled after those of commer-cial appliances (Section 3.1) and require fine-grained ac-tions such as button pressing. Effect of the planner and API access. We find that adding the planner without API access does not improve overall Subtask SR ( −0.7 points for π0.5 and −1.3 for GR00T N1.7). One reason is that the physical channel is limited by execution rather than planning. As shown in Section 6.5, even with the oracle plans, models fail to complete the tasks. Another reason is that the planner switches to a new subtask before the VLA finishes the current one. On the other hand, the standalone VLAs take a median of 22–24 s to complete a pick. 6.6. Channel Selection 

To study when a planner chooses the API, we give it a sin-gle device-operation or sensor-reading request (e.g., “Se-lect the microwave Defrost mode” ) with the robot’s camera views and the prompt and tools of the main experiment, and record the channel of its first operating decision without ex-ecuting it. Crossing 216 requests over all 84 device assets with three robot–panel distances (Figure 6) and three stated API round-trip delays (0.4, 4, and 16 s) yields 1,944 cases per model, 1,818 of them device operations. ## 7. Conclusion 

PAIR couples physical appliance controls and Matter-based APIs through a shared device state and provides a survey-grounded benchmark of 40 tasks and 340 demonstrations. Neither fine-tuned VLA completes an evaluation task: API access improves device operation, but picking, placing, and door manipulation block completion. Even with oracle physical execution, the best planner reaches only 57.3% Progress, and planners choose the API by panel visibility more than by its delay. We hope PAIR serves as a foun-dation for robots that act not only in the home but through it. 

## 8. Limitation 

Our survey asked participants to write requests for PAIR’s devices and objects, so the resulting tasks reflect smart-home delegation and not household activity in general, for which BEHAVIOR-1K activities [13] can be used in the same OmniGibson-based environment. We provide only 340 demonstrations (three task-level demonstrations per task), a small set for fine-tuning VLA policies that likely contributes to the low success rates in Section 6.3 and re-flects the cost of teleoperating a dual-arm mobile manipu-lator through long-horizon tasks with precise panel interac-tion (Appendix D.3). 8LLM Usage Statement

A.2. Panel Realism Evaluation 

Procedure. Raters judged whether each panel could plausibly appear on a contemporary commercial appliance of the same type. Each item showed a whole-device image for context and a close-up of the panel, both in the same operating state. Raters were asked to score only what was visible on the controls, display, labels, and panel surface; for sensors without controls, they scored the display and the surrounding face. The instructions asked them to judge realism rather than personal preference, expected usability, or similarity to a particular brand. 

Criteria. Each panel received three five-point scores. Appearance covers the shapes, colors, materials, finishes, and ren-dering of individual elements. Layout covers their placement, grouping, spacing, alignment, and relative size, including the display content. Information covers whether labels, icons, modes, values, units, and indicators suit the device and agree with one another. Raters assigned each issue to a single criterion and did not penalize features that were not shown. A score of 5 means that nothing looks unrealistic, 3 means clear flaws in an otherwise plausible panel, and 1 means a largely implausible panel. 

Coverage and results. Fifteen raters scored 90 panels, with each rater scoring 30 panels and each panel receiving five ratings. Six of these panels belong to two refrigerator bodies that are not among the final 84 assets, so Table 10 reports the remaining 84 assets with 420 ratings per criterion. Averaged over the three criteria, the realism score is 4.63/5. The study measures visual plausibility from static images only.

A.3. Agent Interface 

An agent can operate a device either physically or through the API. Physical control requires the robot to reach, identify, and actuate a control, whereas API control requires the agent to discover the device and name a valid endpoint, cluster, and 14 attribute or command. Both channels are subject to the same device preconditions, such as a closed door before a cycle can start. The API exposes only device and room state, so object poses and grasp states have to be observed through the cameras.

Physical preconditions, such as a closed door or a loaded object, are read from the scene whenever an operation is attempted, and they apply to API commands in the same way. A.3.3. Simulation Time and API Delay 

OmniGibson and SimuHome share one simulation clock: after each robot action frame, the device model advances by the same interval and updates its feedback. An API request is subject to a configurable one-way delay d, so it reads or changes the device state after d and its response arrives after 2d, with preconditions checked at the time the operation executes. Physical control involves no network delay, and the clock is paused during model inference. 16 B. Survey Details 

We surveyed what people would ask a household robot to do in a smart home. Participants wrote requests in their own words and marked the objects and device functions that each request involved. 

B.1. Survey Questionnaire 

The survey first introduced the robot’s appearance and capabilities: navigating the home, handling objects, operating appli-ance controls, and remotely accessing smart devices (Figure 9). Each item then showed a household scene together with the functions of the available devices, drawn from 14 appliance categories, four sensor categories, and 124 household objects, and asked “What would you ask the robot to do?” 

The survey had a single-device part and a multi-device part. In a single-device item, the participant wrote a request for an assigned device, selected the household objects involved, and marked the requested device operations (power, operating modes, numerical settings, status checks, and cycle operations such as start and stop). In a multi-device item, the participant chose two or more devices and wrote a request that used them together. Figures 10 and 11 show the interface. 

B.2. Survey Filtering 

We kept a request if it described an interpretable task that operates or checks the required device or devices. Requests were excluded if they were empty, did not operate or check the assigned device, involved fewer than two devices in a multi-device item, or could not be interpreted from their text and selections. Merely naming an appliance or using it as a support surface did not count as operating it; moving an object from a cooktop to a dishwasher, for example, operates neither appliance. Of the 1,644 collected requests, 201 were excluded under one of these four criteria, leaving 1,443 (Table 13). The retained requests include some that PAIR cannot simulate.

## C. Skill Taxonomy and Analysis 

We describe the capabilities that the requests require with a taxonomy of robot skills. The taxonomy captures what a request asks the robot to do, while a separate mapping (Section C.3) determines which physical skills a device function requires on a given panel. 

C.1. Skill Taxonomy Construction 

Skills fall into three categories: Physical skills change the world, Perception skills acquire information, and Human Interac-tion skills exchange information with a person. We took the physical skills from RoboCasa [17] and the category definitions from Pantano et al. [21], and added skills that the requests needed but neither source covered. Table 14 gives the definitions and examples, and an additional Other label marks requested work outside the 18 skills. 

Labeling unit. We labeled the skills that a request or its device-function selections express, without adding prerequisites that a robot would have to infer. Objects, destinations, modes, and numerical values are treated as parameters of a skill. A request to set a device therefore receives Device Operation whether or not it names a button or knob. Status Check refers to reading a state and Event Detection to observing until a stated change occurs, so a condition stated in a request is labeled as an observation.

C.3. Device-Function-to-Skill Mapping 

A Device Operation label does not say which physical skills a particular panel requires. We therefore map each selected device function to the controls and feedback of every body and panel variant that supports it. Selecting a program, for example, requires Pressing Buttons on one panel and Twisting Knobs on another, and reading the resulting feedback adds Status Check. Skills unrelated to device operation, such as moving a shirt, keep their original labels. For a request that involves several devices, a variant combination fixes one body and panel for each device. We expand the device functions within each combination and merge the resulting skills with the request’s other labels. In the skill distribution, a skill counts once per combination, and the combinations are averaged within the request. In the skills-per-request count, every requested operation adds its physical skills, so the same skill can be counted several times. One request, which asks to switch a refrigerator off, has no physical method on any panel and contributes only its other skills. 

## D. Benchmark Details 

The benchmark turns survey requests into executable tasks with explicit initial states and simulator-verifiable goals. Training and evaluation share the 40 tasks and use disjoint episodes, so evaluation measures execution on new instances of known tasks. 

D.1. Task Selection 

We started from the 871 requests that combine a device operation or observation with a step that no API can perform. We first removed 327 requests that cannot be executed in the simulator: 290 need objects, device functions, goal conditions, or skills that PAIR does not support, 10 ask for a device operation that PAIR offers through neither channel, and 27 require moving a device that is fixed in place. Basic filtering then removed 148 more: 38 contain no object-manipulation step, and 110 require handing an object to a person, notifying the user, or wiping a surface. The remaining 396 requests can be solved by physical actions alone and cover navigation, object transport, door operation, device control, status observation, and waiting for device or environmental events. From these we selected 40 tasks that span the supported devices and skill combinations, ten of which involve several devices. The selection aims for coverage rather than matching how often each kind of request occurs. Table 2 summarizes the skills and devices of the selected tasks. 

D.2. Episode Instantiation 

A task fixes an instruction and a goal specification, and an episode binds them to concrete objects, devices, placements, a robot base pose, and initial device and ambient states. We randomize these initial conditions within the limits set by the request, so that any starting relation it names holds and any environmental threshold is reachable within the episode budget. Each task has six episodes, three for training and three for evaluation, which gives 120 episodes per split. Because an episode also fixes the body and panel of each device, all methods face the same interface and initial state. Together, the 120 evaluation episodes use 54 of the 84 assets and cover all 18 device types. Each episode comes with an oracle plan , the sequence of subtasks that completes the task from its initial state. The plan is generated by instantiating the task’s subtask template for that initial state; for example, the door-opening subtask is omitted when the door is already open. The oracle plans of the evaluation episodes contain 9.9 subtasks on average (3–25), or 9.2 when device operations are performed through the API. These plans are used for scoring and diagnostics and are never shown to the learned planner. 

D.3. Demonstration Collection and Annotation 

For each training episode, an operator recorded one successful execution of the task by teleoperating XLeRobot’s base, arms, and grippers with Joy-Con controllers and operating the appliances through their panels. Each recording contains the head and two wrist images, proprioception, and actions, and is annotated with subtask boundaries and instructions. We also recorded 220 atomic demonstrations, each covering a single physical skill. Together with the 120 task-level demonstrations, 20 this gives 340 demonstrations and 5.7 hours of execution. Collecting them took a single operator about 100 hours, including failed and repeated attempts. Section E describes how the task-level, subtask-level, and atomic views are sampled during training. A device-operation subtask can contain several button presses or knob movements; setting a temperature, for instance, is a single subtask no matter how many inputs it needs. An inspection subtask, by contrast, acquires information without changing the device. 

Demonstration statistics. Table 17 reports the statistics of the task-level demonstrations. The task-level demonstrations account for 4.35 hours and the atomic demonstrations for 1.34 hours (21.9 s each on average). ## E. Training Details 

Both policies are fine-tuned in a single stage from their released base checkpoints on the same 340 PAIR demonstrations (about 5.7 hours): 120 task-level and 220 atomic demonstrations. We split the data by source demonstration into 305 train-ing demonstrations (108 task-level, 197 atomic) and 35 validation demonstrations (12 task-level, 23 atomic), and compute normalization statistics on the training split only. Each task-level demonstration provides a task-level view, the full trajectory with the original task instruction, and a subtask-level view, each annotated subtask interval with its subtask instruction; wait intervals are excluded. Atomic demonstrations are used whole with their own instructions. Each training sample pairs one observation (the head and two wrist RGB images and the 17-dimensional proprioceptive state) with the next 32 actions. Action windows never cross a recording gap or a wait, and subtask-level windows never leave their interval. Each sample first draws a view with probability 0.40 (task-level), 0.45 (subtask-level), or 0.15 (atomic) and then draws a window uniformly within that view. Both policies are trained for 15,000 steps with a global batch of 160 (2.4M sampled windows) on 5 ×H200 GPUs. π0.5 is fully fine-tuned. For GR00T N1.7 we follow the released post-training recipe and update the projector, the action head, and the vision–language layer norms (1.62B of 3.14B parameters) while keeping the language and vision backbones frozen. Peak learning rates are the released defaults scaled by √2 for the larger batch. Table 18 lists the hyperparameters. We evaluate π0.5 at step 12,000 and GR00T N1.7 at step 13,500.

F.1. Agent Execution 

Every VLA receives the head and two wrist RGB images together with the 17-dimensional proprioceptive state. The stan-dalone VLA is given the task instruction, whereas a VLA paired with a planner is given the instruction of the current physical subtask. Each query predicts 32 actions, and up to 16 of them are executed before the VLA is queried again. The simulation runs at 30 action frames per second with physics at 120 Hz. The planner is queried every 5 s of simulated time with the task instruction, the current camera images, the simulation time, and a memory of its past subtasks and delivered API results. The API-enabled planner can additionally discover devices, read their state, write attributes, and issue commands. At every query the planner also assesses its current subtask, but this assessment only updates its memory and is not used for scoring. Simulated time is paused during model inference, while API delays and device processes continue to advance on the simulation clock.

F.3. Subtask Scoring 

We report three metrics. Task SR is the share of episodes that satisfy the complete goal specification, including its ordering, conditions, and process completion. Subtask SR is the share of manipulation and device-operation subtasks in the oracle plan whose completion condition holds at some point during the rollout, regardless of order. Progress is the share of an episode’s plan that is completed before the first uncompleted subtask, averaged over episodes. The completion condition depends on the subtask. Navigation requires the robot to be within 0.8 m of the target’s bounding box while holding any object it has to carry, and a pick requires the object to be held at least 0.03 m above its last resting height. A placement requires the object to be released in the specified spatial relation. Door subtasks require the requested open or closed state, and device operations require the requested attribute values or the start of the cycle. A condition that already holds when the instruction is given is not counted, with one exception: the first navigation subtask counts if the robot starts within range. When a plan contains the same condition several times, each occurrence must be satisfied separately, at least 1 s apart. 

Common denominator. To compare methods fairly, we score all of them on the same plan subtasks. Subtasks that API access makes unnecessary, such as navigating to a panel, are therefore omitted for every method, as are 27 subtasks whose completion cannot be determined from the recorded traces of every method. This leaves 1,079 subtasks: 337 navigation, 182 pick, 170 placement, 128 door, and 262 device-operation subtasks. Completion is determined offline from physical traces sampled every 0.5 s and from recorded device events, so interactions shorter than the sampling interval can be missed. Status checks and waits are reported separately in Section F.4.

Without API access, every one of the 3,248 ( π0.5) and 3,149 (GR00T N1.7) decisions issues a physical subtask: the planner never selects the continue or wait action and keeps a subtask only by issuing the same instruction again. Counting consecutive decisions with the same instruction as one instruction, the planner later replaces 670 ( π0.5) and 582 (GR00T N1.7) instructions with a different one, and it does so at the very next decision, after a single 5-s interval, for 544 (81.2%) and 485 (83.3%) of them. A single interval is short compared with the time the VLAs need: measured from the moment a subtask becomes active to its completion, the standalone VLAs take a median of 22.3 s ( π0.5,24 completed picks) and 23.6 s (GR00T N1.7, five completed picks) to complete a pick. With API access, the planner selects continue 33 times and wait once. 

Recognizing completion. Without API access, the planner assesses its current subtask as not satisfied in 6,100 of its 6,397 decisions (95%) and as satisfied in only 57, even after subtasks that were in fact completed: of the 119 navigation and pick subtasks that the evaluator marks complete, the planner assesses only 9 as satisfied. Its assessment therefore carries little information about success. Reading displayed values, in contrast, is accurate, as 109 of the 111 values that the planner first reports from a display (timers, cycle states, temperatures, fan speeds, and sensor readings) match the device state. 

Persistence and verification. In 56 cases without API access, the planner issues a turn-on subtask for a device that never turns on. It abandons the attempt while the device is still off in 34 of these cases, 18 of them after a single 5-s attempt, and keeps retrying until the episode ends in the other 22. With API access, the planner attempts a physical device operation on 62 rollout–device pairs, and the device state remains unchanged in 57 of them. Across these 62 pairs, it reads the device state through the API before issuing an API command in only one; in 35 it switches to an API command without reading, and in 26 it does not use the API for that device again. 

API errors. Of the 317 API commands that return an execution error, the planner resends the same command in 211 cases (67%), switches to a physical subtask in 72, looks up documentation or the device structure in 25, and sends a different command in 9.

F.8. Channel-Selection Study 

This study isolates the choice of channel from physical execution. In each case , the planner receives one device-operation or sensor-reading request, fixed head and wrist camera images of the device, and the same prompt and tools as in the main experiment. Its discovery and state-read calls are answered by a SimuHome home whose device state matches the images, and none of its actions is executed. We cross 216 requests over the 84 assets with three robot–panel distances (0.45, 2.0, and 3.5 m) and three stated API round-trip delays (0.4, 4, and 16 s). Of the resulting 1,944 cases, 1,923 remain per model after we remove views that have no free stance, occluded targets, or targets outside every camera image. Decision and correctness. A planner may make up to six calls per case, which lets it discover a device before deciding.
