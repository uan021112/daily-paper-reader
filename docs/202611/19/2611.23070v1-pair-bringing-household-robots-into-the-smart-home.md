## 摘要
家用机器人通常需要操作家电，而智能家电同时提供控制面板和设备 API。然而，现有具身 AI 仿真环境仅将家电建模为物理物体。我们推出 PAIR，这是一种基于 Matter 协议\footnote{https://csa-iot.org/all-solutions/matter/}（智能家居设备的行业标准）的智能家居仿真环境。PAIR 提供 84 种智能设备资产，其功能性控制面板和 API 操作共享的设备状态，环境条件也会随两者的操作而变化。我们通过一项包含 1,443 条请求的调查，构建了一个包含 40 项任务的基准；这些任务都要求操纵物体，但无需访问 API 即可完成，并提供 340 个人类演示用于策略训练。无论单独运行、配合高层规划器运行，还是配合支持 API 的规划器运行，两种经过微调的视觉-语言-动作（VLA）策略在 120 个评估回合中均未能完成任何任务。机器人很少能推进到使用 API 的阶段：即使提供预言机计划和 API 访问权限，超过 90\% 的失败运行也卡在导航、抓取或操作门上。即便以完美预言机取代机器人的身体，表现最佳的规划器也只完成了其计划的 57.3\%。在选择按下按钮还是调用 API 时，若干规划器依据的是能否读取控制面板，而非 API 延迟。\footnote{我们将在论文发表后公开代码和数据。}

## Abstract
Household robots often need to operate appliances, and smart appliances offer both control panels and device APIs. Existing embodied AI simulation environments, however, model appliances solely as physical objects. We introduce PAIR, a smart-home simulation environment grounded in the Matter protocol~\footnote{https://csa-iot.org/all-solutions/matter/}, the industry standard for smart-home devices. PAIR provides 84 smart-device assets whose functional control panels and APIs act on a shared device state, with ambient conditions that evolve in response to both. From a survey of 1,443 requests, we construct a benchmark of 40 tasks that all require object manipulation yet remain solvable without API access, with 340 human demonstrations for policy training. Whether run alone, with a high-level planner, or with an API-enabled planner, two fine-tuned VLA policies complete none of the 120 evaluation episodes. Robots rarely get far enough to use the API: even with oracle plans and API access, over 90\% of failed rollouts stall at navigating, grasping, or operating a door. With a perfect oracle in place of the robot's body, the best planner still gets through only 57.3\% of its plan. When choosing between pressing a button and calling an API, several planners go by whether they can read the panel, not by API latency.\footnote{We will release our code and data upon publication.}

# 1. 核心问题与整体含义

- **研究问题：** 家用机器人执行日常任务时，既要完成导航、抓取、放置、开门等实体操作，也可能通过智能家电 API 查询状态或远程控制设备。现有具身智能仿真环境通常只把家电视为需要物理操作的物体，难以研究机器人如何在实体面板与设备 API 之间协同。
- **研究动机：** 智能家居任务往往不是单纯的设备控制。例如“洗衣服”需要先把衣物放入洗衣机并关门，之后才可通过面板或 API 启动程序、查询进度。要评估机器人能否完成这类任务，仿真环境必须让实体操作和 API 调用影响同一设备状态。
- **整体贡献：** 论文提出 **PAIR（Physical-API Integration Environment for Robots）**，将基于 Matter 协议的智能设备 API 与物理仿真中的家电控制面板联动，并据此建立用户需求驱动的任务基准和人类示范。论文也借此揭示：即使具备 API，机器人仍可能在接近设备、抓取物体或开关门等基础实体技能上受阻。

# 2. 方法论

## 2.1 环境与状态联动

- PAIR 基于 OmniGibson 物理仿真，并结合 SimuHome 的 Matter 设备模型。
- 环境包含 **84 种智能设备资产**，涵盖 **14 类家电和 4 类传感器**。设备具有可操作的实体控制面板，也提供结构化 API。
- 两种控制渠道共用一份设备状态：
  - **实体操作**（例如按键、转动旋钮）会更新设备状态，并反映到面板显示、指示灯及相关环境条件。
  - **API 调用**（例如读取状态或执行命令）也会更新同一状态，物理设备行为和可观察反馈随之变化。
- 设备遵守操作前提和约束。比如洗衣机启动可能要求机门关闭、内部有衣物；前提不满足时，API 命令会被拒绝，实体操作也无法绕过该约束。
- 设备运行还会影响房间环境状态，包括温度、照度、湿度和空气质量。
- API 延迟可配置，默认单程为 200 毫秒；实体操作不额外增加网络延迟。

## 2.2 用户需求与技能体系

- 作者调查了 129 名参与者，筛选后保留 **108 名参与者的 1,443 条有效请求**，包括单设备和多设备任务。
- 研究者建立了三类机器人技能分类：
  - **物理技能：** 如导航、拾取与放置、开关门、按键、设备操作。
  - **感知技能：** 如状态查询、物体识别、事件检测。
  - **人机交互技能：** 如识别口头提示、向用户报告信息。
- 请求由 GPT-6.1 Terra 辅助标注，并在 100 条请求上由三位作者独立标注验证；报告的微平均 F1 为 0.881，Cohen’s κ 为 0.856。
- 调查显示，58.4% 的请求涉及状态检查或等待事件；即使设备操作都能通过 API 完成，仍有 60.4% 的请求需要机器人进行实体操作或感知。

## 2.3 Benchmark 与示范数据

- 作者依据两项原则筛选基准任务：
  1. **必须存在 API 无法代做的实体步骤**，确保任务不只是远程设备控制。
  2. **必须可以完全通过实体操作完成**，使得有无 API 都能比较。
- 最终选出 **40 项任务**，覆盖不同设备和技能组合，其中 10 项涉及多设备；每项任务设置 6 个不同初始条件的 episode，3 个用于训练示范采集，3 个用于评估。
- 收集 **340 条实体操作人类示范**：120 条完整任务示范和 220 条原子技能示范，共约 5.7 小时的机器人执行数据。
- 任务平均包含约 9.9 个主要子任务；完整示范的实际采集工作约耗时 100 小时，包括失败和重试。

## 2.4 策略与评估流程

- 将两种 VLA 策略——**π0.5** 和 **GR00T N1.7**——在示范数据上微调，并在三种设置中比较：
  1. VLA 独立执行完整任务；
  2. VLA 接受高层规划器分解的实体子任务；
  3. 高层规划器还可调用设备 API。
- 高层规划器主要采用 **Qwen3-VL-8B-Instruct**，每 5 秒根据指令、相机图像、时间和历史子任务选择下一步行动，包括发布子任务、继续、等待、结束或调用 API。
- 另设“预言机诊断”来拆分规划与执行瓶颈：
  - **预言机计划 + VLA 执行：** 用正确的子任务序列替代学习得到的计划。
  - **规划器 + 预言机实体执行：** 用脚本化实体操作替代 VLA，专门考察规划器。
  - 还测试了多种不同的视觉语言模型规划器。
- 主要指标包括任务成功率、子任务成功率，以及任务首次遇到未完成子任务之前的计划进度（Progress）。

# 3. 实验设计与对比

## 3.1 场景与数据

- 实验场景为 PAIR 中的家庭环境，评估集包含 **120 个 episode**，覆盖 40 项任务；评估中使用 54 种设备资产，覆盖全部 18 类设备。
- 这些任务都要求物体操作，且可以在没有 API 的情况下完成，因此有无 API 的方法面对的是同一类任务目标。
- 除端到端评估外，作者还在训练示范对应的起始状态下测试了 100 个设备操作或状态检查子任务，用于单独衡量 API 对设备操作的影响。

## 3.2 对比方法与实验组

- **端到端对比：** 两种 VLA × 三种执行架构，共 6 个 VLA 变体；每种运行在 120 个评估 episode 上。
- **隔离子任务测试：** 比较 π0.5 和 GR00T N1.7 在有无 API 访问时完成设备操作和状态检查的表现。
- **预言机诊断：**
  - 两种 VLA 在有无预言机计划、以及有无 API 的组合下运行，共 160 个 rollout。
  - 规划器配合预言机实体执行，在 40 个诊断 episode 上比较 Qwen3-VL-4B、Qwen3-VL-8B、InternVL3.5-4B、GPT-6 Luna 和 Gemini 3.5 Flash-Lite。
- **渠道选择实验：** 研究规划器何时选择实体面板、何时选择 API。实验跨设备资产、机器人与面板距离、给定 API 延迟等条件，比较多个 VLM；并进行提示词跟进实验，例如向模型提供设备标识或明确两种渠道的预计成本。

# 4. 资源与算力

- **训练硬件：** 使用 **5 张 NVIDIA H200 GPU**。
- **训练规模：** 两种 VLA 均训练 15,000 步，批大小为 160；π0.5 全参数微调，GR00T N1.7 更新约 16.2 亿个参数（总参数量约 31.4 亿），其语言和视觉主干保持冻结。
- 论文没有报告训练所需的具体墙钟时间、GPU 小时数或总能耗，也未完整说明不同规划器推理实验的算力成本。
- 示范数据采集耗时约 100 小时，但这是遥操作数据采集工时，并非模型训练时长。

# 5. 实验数量与充分性、公平性

## 5.1 实验规模

- 端到端评估：6 种方法配置 × 120 个 episode，共 **720 次评估运行**。
- 预言机计划诊断：4 种 VLA 条件 × 40 个 episode，共 **160 次运行**。
- 预言机实体执行规划实验：5 种规划器 × 40 个 episode。
- 隔离子任务测试：100 个设备操作或状态检查子任务，在实体控制与 API 设置下比较。
- 渠道选择实验：主实验覆盖多种 VLM、设备、面板距离与 API 延迟；另有提供设备标识、提供成本、改变成功率假设、移除 API 指引等后续实验。

## 5.2 充分性与公平性评价

- **相对充分之处：** 实验不仅报告端到端结果，还用预言机替换规划或实体执行模块，将两类瓶颈分开分析；任务实例化时不同方法面对相同的初始设备、面板和场景条件。对 API 可跳过的步骤，作者也从所有方法的进度比较中统一排除。
- **需要谨慎解读之处：**
  - 每项任务只有 3 个评估 episode，且只有 40 项任务，结果对初始条件和任务选择的泛化仍有限。
  - 任务是覆盖性选择，而非严格按用户请求的真实频率抽样，因此不宜直接据此推断家庭任务中的总体成功率。
  - VLA 仅使用 340 条示范进行微调，数据规模较小，低成功率可能部分来自示范不足。
  - 有些规划器决策具有随机性，论文也报告同一输入重复运行和不同 GPU 硬件会造成部分结果变化，因此渠道选择等结果存在运行方差风险。
  - 预言机设置有助于诊断，但属于理想化组件，不能等同于实际部署表现。

# 6. 主要结论与发现

- **端到端任务成功率为零：** 两种微调 VLA 在单独运行、配合高层规划器或配合支持 API 的规划器时，均未完成 120 个评估 episode 中的任何一个。
- **API 能改善设备操作，但无法消除前置实体瓶颈：** 在隔离的设备操作和状态检查测试中，API 将总体子任务成功率从 24.0% 提高到 47.0%；设备操作成功率也显著提升。但在完整任务中，机器人常常尚未完成导航、抓取或开门，就无法推进到需要调用 API 的阶段。
- **计划正确不等于身体能执行：** 即便提供预言机计划和 API，失败仍主要集中在导航、拾取和门操作；论文报告，API 条件下超过 90% 的失败 rollout 卡在这些实体环节。
- **规划器自身也有明显限制：** 以理想实体执行替代机器人后，规划器表现仍相差很大；最佳规划器 GPT-6 Luna 的 Progress 为 57.3%，远低于预言机计划与预言机实体执行达到的 100%。
- **渠道选择并不总能基于成本：** 多个规划器选择 API 的倾向受到控制面板是否可见的影响，给定 API 延迟的变化通常影响较小；部分模型也没有稳定按照提示中提供的渠道成本选择更省时的一方。

# 7. 优点

- **把物理控制与智能家居 API 放进同一仿真闭环：** 设备状态共享，面板、API、设备运行和环境条件相互联动，比将家电仅当作普通物体更适合研究智能家居中的机器人任务。
- **任务设计兼顾两种控制方式：** 所有基准任务既需要实体操作，又可纯物理完成，避免 API 单独完成任务而掩盖机器人基本操作能力的问题。
- **基准来源有用户需求支撑：** 研究从大规模用户请求调查出发，并公开描述技能分类、筛选过程、任务实例化和示范构成，提高任务设计的可解释性。
- **诊断实验较有针对性：** 通过预言机计划、预言机实体执行和隔离子任务实验，区分规划、物理执行及设备控制问题，而不仅给出一个总成功率。
- **结果揭示了实际系统设计中的关键权衡：** 研究指出，增加 API 不等同于解决具身任务；在机器人接触设备之前，导航、抓取和门操作仍可能是决定性瓶颈。

# 8. 不足与局限

- **示范数据有限：** 340 条示范对于长时程、细粒度面板交互任务可能不足；作者也承认这可能是低成功率的原因之一。
- **任务覆盖范围有限：** 调查要求参与者围绕 PAIR 所支持的设备和物体提出请求，结果反映的是智能家居委托任务，而非全部家庭活动。40 项基准任务也只是从可执行请求中选择，未必代表真实任务分布。
- **仿真与真实设备仍有差异：** 面板由研究者设计，虽然静态视觉真实性评分较高，但这不等于真实硬件的触觉、摩擦、按钮力、传感误差和网络故障均得到准确模拟。论文还指出，PAIR 的按钮、旋钮和控制间距整体大于商业设备的测量中位数。
- **评估规模和泛化证据有限：** 每项任务只有 3 个评估实例，机器人、设备资产和场景种类仍有限；论文没有提供真实家庭部署验证，因此不能直接推断现实家庭中的表现。
- **低任务成功率的归因有多重可能：** 结果显示实体执行是主要瓶颈，但小规模示范、策略训练和任务复杂度也可能共同影响成绩，不能将失败完全归结为某一种能力缺陷。
- **渠道选择研究具有模型和提示依赖性：** 规划器的选择会随可见性、提示信息、模型配置及硬件发生变化，说明当前结论应理解为所测试模型和设置下的观察，而非所有智能体的普遍规律。
- **资源报告不完整：** 虽披露了 H200 的数量和训练步数，但未提供训练墙钟时长、GPU 小时或完整的推理算力账单，不利于复现实验成本。
