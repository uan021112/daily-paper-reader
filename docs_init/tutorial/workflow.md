# 推荐链路说明

## 每日推荐

日常流水线依次执行抓取、关键词召回、向量召回、融合、重排、LLM 精炼、选择和文档生成。配置完整的 Supabase 后端可直接完成两路召回，不必先下载整个论文池。

## 共享数据库不可用时

每日推荐及 1–30 天窗口在自动决定跳过抓取前，会对配置中的 arXiv 数据库做一次最多读取一条记录的可用性检查。查询成功但返回零条仍视为数据库正常，不会因此切换数据源。

若检查失败，本轮运行改用 arXiv 官方 API 获取元数据，并在本地候选池上执行关键词与向量检索。只临时关闭本轮 arXiv 数据库后端，不改写 `config.yaml`、订阅或历史阅读数据；下一次运行会重新检查数据库。embedding 和 reranker 仍遵循原模型配置，GitHub Actions 继续使用云端模型，不会下载本地模型。

- 官方 API 抓取在既有重试和窗口拆分后仍失败时，工作流报错，不覆盖已有原始结果，也不推进抓取水位线。
- 数据库召回失败、仍有未恢复的时间分片或缺少有效输入时，不能当作“没有新论文”继续发布空日报；只有已有有效本地输入时，arXiv 召回才能回退到本地候选池。
- 成功查询得到零条、或成功抓取得到空数组，是正常空结果，仍可生成零推荐日报。
- 其他论文源不会被替换成 arXiv；其检索失败会明确报错。
- 显式传入 `--skip-fetch` 时仍尊重该选择，不自动启用抓取；没有可用数据库或原始输入时会失败。

本恢复路径不适用于超过 30 天的专题回溯或会议检索；这些任务仍需要可用的数据库。

## 如何判断是否恢复

在 Actions 日志中确认实际完成了抓取、两路召回和后续文档生成，而不只看绿色状态或 Pages 部署成功。数据库故障后反复出现 `Failed to resolve`、`NameResolutionError` 或 RPC 失败，表示检索尚未恢复；正常的零结果必须建立在上游查询或抓取成功的基础上。
